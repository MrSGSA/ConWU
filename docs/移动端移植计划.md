# 移动端移植计划

状态：Android 从机测试 APK 已通过隔离验证，真机串流待验收；iOS 暂待构建条件。更新日期：2026-11-13。

将 ConWU 移植到 Android 和 iOS。用户暂不具备 Mac／Xcode 构建条件，因此优先 Android；手机仅作为从机，通过现有直连码加入 Windows 或 Linux 主机，再使用原版 Moonlight 串流。实现与使用说明见[Android 从机测试版](Android使用.md)。本项独立于桌面端传输优化，不据模拟器结果推断真实串流体验。

## 使用流程

1. 手机输入主机生成的 16 位直连码，保留每四位分组、粘贴和删除规则。
2. 主机批准加入，手机自动获取网络身份、虚拟 IP 和必要的连接配置。
3. 用户授权开启系统 VPN，仅将 ConWU 虚拟地址的流量送入隧道。
4. 用户切到原版 Moonlight，通过主机虚拟 IP 串流。

后续沿用已有入口订阅更新、PKARR 发现和可选协调发现。移动端自行保存配对凭据，地址变化后使用既有身份恢复连接；发现服务不保证主机入口可达或 TCP 打洞成功。

## 协议范围

| 能力 | Android 无 root | iOS 未越狱 | 初步安排 |
| --- | --- | --- | --- |
| 直连码、审批、配置继承 | 可适配 | 可适配 | 复用现有流程 |
| 已有入口、订阅解析和 PKARR | 可适配 | 可适配 | 适配移动网络与后台生命周期 |
| HTTPS 即 TLS 加 WebSocket | 可实现 | 可实现 | 优先验证 |
| 真实 TCP | 已接入测试版 | 可实现 | 与 HTTPS 一起验证 |
| 当前 FakeTCP 加 HTTP、Phantun | 标准 VPN API 权限不足 | 不能直接移植当前机制 | 不纳入首版 |

Android 的 VpnService 和 iOS 的 NEPacketTunnelProvider 提供虚拟网卡 IP 包收发能力，不授予当前 FakeTCP、Phantun 所需的真实接口 TCP 报文捕获、注入与拦截权限。不能用向 UDP 数据内添加 TCP 头的方式代替，因为物理网络看到的外层仍是 UDP。

同一网络两端需要使用兼容的传输协议。现有 FakeTCP 网络不能由手机使用普通 TCP 直接接入；需为手机建立 HTTPS 或 TCP 网络，并准备对应的可达主机入口。界面应明确提示不支持的协议，避免静默切换造成误判。

## 代码复用与平台改造

- 复用直连码格式、审批、身份认证、端到端加密、网络配置交换，以及 TCP 和 HTTPS 的协议实现；分别验证所用依赖的移动端兼容性。
- 通过现有 IPacketAdapter、IMeshTransport 边界接入移动平台。iOS 使用 Packet Tunnel 扩展，Android 使用 VpnService。
- 优先评估现有 C# 核心在 .NET for iOS 与 AOT 下的兼容性、内存和性能。根据实测决定是否抽取轻量原生核心，不预先要求全面重写。
- 将 Windows 与 Linux 二分的平台判断改为明确的平台实现；手机密钥分别使用 Keychain、Android Keystore，不沿用 Windows DPAPI 和桌面文件权限逻辑。
- 改造后台服务、进程通信和启动方式。iOS 数据通道运行于 VPN 扩展；Android 按平台要求管理前台服务及通知，不依赖桌面子进程或系统服务。
- 同一移动端 VPN 内统一管理多个逻辑网络的虚拟 IP 与路由，检查地址冲突，避免照搬桌面端每网独立适配器的模型。
- 处理 Wi-Fi 与蜂窝切换、网络唤醒、IPv6 与 NAT64。直连码保留 IPv4 表达时，外层连接也应正确处理 IPv6-only 网络，不能只强制 tcp4。

## 实施顺序

1. **多端更新检测**：Windows／Linux 设置页、Linux CLI 与 Android 共享正式 Release 检测；限定官方来源，按平台和架构选择附件，查询失败不占用连接操作，不自动安装或修改设置。
2. **Android 核心与系统 VPN**：接入共享从机核心、16 位直连码、主机审批、配置继承、TCP／HTTPS、Keystore 加密存储及精确虚拟地址路由；在隔离模拟器核验系统 IP 包、并行网络、进程重开与取消回收。
3. **Android 真机串流**：使用真实手机和原版 Moonlight 验证后台运行、入口更新、Wi-Fi／蜂窝切换、IPv6-only／NAT64、耗电及厂商省电限制，按约 50 Mbps 主机上行条件验收，不把握手和 ping 成功当作串流达标。
4. **Android 分发**：当前 APK 使用开发签名，仅作为测试版；正式分发前确定独立签名、versionCode 递增与覆盖更新的配置继承策略。
5. **iOS 后续**：具备 Mac、Xcode、签名与真机后建立 Packet Tunnel 扩展，验证共用核心的 AOT、依赖、资源预算、后台运行与实际串流，再确定发布渠道。

每一步依据结果调整下一步范围；基础链路或扩展资源预算不满足时，先解决核心适配问题。

## 验证与验收

- **连接与安全**：完整走通直连码加入、批准与拒绝；覆盖错误码、过期码、错误主机、未批准访问、身份隔离、重放防护和凭据持久化。
- **串流表现**：在主机约 50 Mbps 上行条件下，以 20、35、45 Mbps 为主要目标，50 Mbps 作为满载压力；计入封装及重传开销。记录有效交付码率、交互尾延迟、卡顿、CPU、内存、发热和耗电，由实际 Moonlight 使用验收。
- **后台与恢复**：覆盖切到 Moonlight、锁屏后的暂停与恢复、扩展或服务被系统回收、应用重开、主机重启、入口更新、Wi-Fi 与蜂窝切换。
- **路由与资源**：检查虚拟 IP 冲突、多网络并行、VPN 自身连接绕行、MTU、取消与资源回收；普通互联网流量保持正常。说明与其他 VPN 或代理软件可能存在的冲突。
- **平台覆盖**：使用真实 iPhone、iPad 和 Android 设备，覆盖拟支持的系统版本、IPv6-only 与 NAT64 环境。iOS 扩展内存按设备和系统实测，不预设统一固定上限。

## 构建与分发条件

iOS 构建需要 Mac 和 Xcode，可由 Windows 远程连接 Mac 构建；真机运行需要匹配的签名、配置描述文件和 Network Extension 权限。自用调试与公开分发分别规划。若按 VPN 类应用公开上架，需核对苹果当时的组织开发者要求和审核条款。

首轮实机验证前确认可用的 Mac、移动设备、系统版本和签名条件；发行方式在原型通过后确定。

## 首版范围之外

- 手机创建网络、提供协调服务及完整复制桌面设置页。
- 依赖 root 或越狱的 FakeTCP、Phantun 实现。
- 修改 Moonlight，或将其集成为 ConWU 内置播放器。
- 业务中继、内置 DDNS、自动 UDP 回退和外层 FEC。

扫码可以作为后续输入便利功能，保留手输直连码作为基础能力。
