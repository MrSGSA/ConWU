### 0.1 业务约束

1. 业务流量禁止经公网服务器或其他成员中继。协调、候选反射和有界连通性探测可以使用服务端；服务端不得提供业务载荷转发通道。
2. 保留已经满足需求的 udp2raw FakeTCP＋HTTP 承载。默认优先使用它解决本场景的 UDP 上行受限问题。
3. 保留无业务重传、无跨数据报按序等待的外层语义。内层应用自己的 TCP 行为不受这项约束替代。
4. 现有显式入口 P→Q 继续保留；它与新的双主动能力分别描述、分别验收。
5. Windows 产品应独立运行，不要求用户安装 WSL、Python 或开发版 .NET 环境；开发测试使用现有 .NET 10/Python 工具链可以接受。
6. 最大八成员，每对直接连接；允许并明确展示部分连通。没有找到符合策略的直连时，返回可解释结果，不暗中改成转发拓扑。
7. 不把 UDP 观察等同于 TCP 观察，不把 TCP SYN 握手成功等同于现有 FakeTCP 数据一定能通过。
8. 不承诺任意“严格 NAT”组合必通。目标是扩展可验证覆盖、降低连接成本与恢复时间，并准确识别已尝试范围内的失败。
9. 本计划不授权删除无关配置、关闭全局防火墙、卸载在用驱动或中断无关服务。生产部署沿用既有授权，不从“制定计划”推导出额外生产操作权限。

## 4. M1：端点资源连续性与真实 native 接入

M1 完成 PoC-1。现有回馈已经完成其中的本地资源子项，不应重新搭建另一套相同原型。

### 4.1 资源生命周期

在 Owner、Attempt、Path、排队/在途 I/O 引用之外，增加 NativeAttachment 引用。native 自获得有效授权起，到确认停止使用该源端点或被确认退出为止，必须持有该引用。

区分以下状态：

| 状态维度 | 示例 | 应有行为 |
|---|---|---|
| 资源寿命 | Open、Retiring、Closed | 退役后拒绝新 Attempt；已有合法引用仍可存活 |
| 辅助查询 | Healthy、QueryUnusable、PeerClosed | 不可复用的查询流不再承接新事务 |
| 原生接入 | Authorized、Armed、Started、Revoking、Detached | 未 Armed 不得发首个 SYN，撤销后不得再发 |
| 业务路径 | Checking、Authenticated、Active、Failed | 不由一次查询超时直接等同判死 |

现有“部分事务超时/取消后不复用该 STUN 流”的保守策略可以保留。必须明确：它是否保持 socket 打开、是否仍有路径引用、如何标记候选过期、如何尝试替代资源，以及辅助对端关闭时如何通知依赖者。不得为恢复查询而偷偷关闭重绑原来的 P。

若后续确有需求复用发生事务取消的 TCP STUN 流，应使用持续、单一的消息读取与事务分流实现，并测试半包、粘包和迟到事务；不在本次原生接入中顺手引入第二个竞争读取者。[S4]

### 4.2 父子接入协议

采用父进程创建、限制访问和继承范围的 IPC；可复用项目已有的受限管道。授权信息不能只依赖可任意设置的 skip-bind 环境变量。

建议交互：

1. 父端 AcquireAttachment，取得一个独立引用和 AttachId。
2. 父端从已连接 socket 读取实际 LocalEndPoint/RemoteEndPoint；不把 wildcard bind 地址直接当实际源 IP。
3. 父端发送 Attach：LeaseId、NetworkGeneration、AttachId、源端点、STUN 例外 tuple、允许的对端/角色、profile、有效期和控制会话身份。
4. native 校验控制会话，进入受管理模式，不再调用原来的 try_to_list_and_bind2 绑定 P。
5. native 安装匹配的捕获与 RST 处理规则，接收循环就绪后发送 Armed；回报实际源端点、捕获描述版本、角色和代次。
6. 父端逐项核对 Armed，发送 Start。native 仅从这时开始对等 SYN。
7. 正常撤销：停止新发送与新会话 → 停止并收敛所属 I/O/捕获 → DetachAck 或确认进程退出 → 释放 attachment 引用。最后资源持有者消失后才关闭辅助 socket。

所有控制消息有消息类型、请求编号、长度上限与协议版本。旧 AttachId 的 Armed/DetachAck 不得作用于新子进程。IPC 失联、父进程退出、授权撤销后停止注入；不要依赖父进程在崩溃时还能主动发送 ExitNotify。

同一个Lease同一时刻最多授权一个有效NativeAttachment。重启时先确认旧实例停止注入并退出或完成受控Detach，再授权新实例；仅有IPC超时不足以证明旧实例已停止。撤销前已经进入网卡/链路的包可能迟到，按旧轮次处理；这里保证不再新增授权发送，不声称物理网络瞬间清空。

若复用 Job Object 的 KILL_ON_JOB_CLOSE，验证 job handle 的所有者和继承关系。该机制是进程回收手段，不是任意崩溃下无 RST/无时间窗口的保证。[S3]

### 4.3 捕获所有权

PoC-1 首轮固定单 peer 的明确 tuple，先证明内核 STUN 和 FakeTCP 能分流。记录 layer、priority、flags、源地址、方向、STUN 例外和捕获描述版本。

正式多 peer 默认采用一个受管源端点一个 EndpointOwner：

- 端口独占与辅助连接的使用均受该 Owner 管理。
- 捕获范围局限于该源端点；STUN 辅助流按双向完整 tuple 排除。
- 在该范围内按授权 peer、Attempt、阶段和 tuple 分流。
- 同一本地IP:port、远端IP:port和TCP协议，同一时刻只允许一套有效TCP外形会话。Active/Candidate若落在相同四元组，刷新与再验证复用现有会话；确需新ISS/独立握手时另取EndpointLease或不同远端tuple，或待旧会话退役后串行重建。不同AttemptId不能让TCP包携带两套独立状态，不能覆盖仍在服务的ISS/IRS/seq/ack；新资源计入预算。
- 未认证来源只进入有界候选，不可修改 Active。
- 若采用固定端点捕获加用户态白名单，必须证明没有其他应用合法使用该端点；不捕获其他端口、不把捕获到报文视作身份成立。
- RemoteAllowlistVersion 的变化可以在 Owner 内更新；本地地址、捕获表达式、方向、priority/flags 或 helper tuple 改变，则按完整描述重建或有序迁移。
- 修复只按本地端口复用固定远端过滤器的逻辑。不要同优先级打开互相重叠的新旧处理句柄。
- NetworkGeneration不在TCP包头中；同一wire tuple不能因为“代次不同”而允许重叠捕获。范围需变更时，先受控撤销旧范围，再重开；候选变化优先只更新原子授权表。
- 故障时不能将被自己截住的辅助流静默丢弃，也不能把 native 数据又交给内核生成额外响应。

WinDivert 的 NETWORK 层没有 PID，重叠同优先级句柄的接收次序未定义，注入包可能被更低优先级句柄继续处理。因此进程和 Lease 归属必须由本地管理与实际过滤集合共同保证。[S1]

### 4.4 真实 I/O 分两层验证

**M1-A：真实 Windows LAN 验证。**

使用两台独立 Windows 网络栈，通过真实网卡/虚拟交换机网络通信。不能在同一个 Windows 内用另一个本机 IP 代替远端；那仍可能是 loopback。

在测试专用端点上持有辅助 TCP 流，同时建立既有单主动 FakeTCP 认证通信。并发查询 STUN 辅助流，核对 native 发出的真实源 IP:P。先排除 NAT，不把本地捕获失败与 NAT 失败混为一类。

**M1-B：公网端点连续性。**

使用可用反射端和已知可达的测试对端，记录反射观察 E(S)、对端实见 E(B) 与本机收包端点。受控 EIM 正例要求两种外部观察一致；真实环境出现差异时记录条件和范围，不虚报 EIM，也不简单判为 Windows 接入失败。

分别保留旧 P→Q 显式入口的成功证据与新源端点的证据。普通单主动连通只算 M1 的资源验证，不能计为双主动穿透。

### 4.5 M1 验收

- 受控正例 30/30 创建、接入、认证通信、退役完成。
- NativeAttachment 期间端点不被提前释放；跨进程抢绑定失败，原流继续有效。
- 单条辅助 TCP 连接保持可识别，迟到事务不被认成新事务。
- 从 Armed 到正常 Revoke 的有效运行区间，非预期内核 RST/额外 SYN+ACK 到达对端为零。
- 抓包计数、丢包统计和观察点有效；仅有“拦截器说自己丢了 RST”不足以证明线上没有 RST。
- 旧 AttachId、旧网络代次、重复撤销、父/子进程退出和取消不导致越权继续发送。
- 同端点其他受管会话与辅助流不因本轮故障被错误关闭。
- 正常关闭后的 TCP TIME_WAIT 单独记录，不算资源泄漏。
- native 崩溃使其业务路径失效是预期事件；退出后的 TCP RST 与运行期间意外泄漏分开统计。

**失败分流：** 先区分绑定、捕获、校验和/路由、原生握手、反射/对等映射差异。只有证明这条内核辅助共存路线本身不可行，才切换到原生 EndpointOwner 自有反射。该备选必须使用同一持有端点完成控制反射与对等会话，并限制服务器只做观测/探测；不引入业务中继。

## 5. M2：原生 FakeTCP 双主动，完成 PoC-2

### 5.1 实现边界与角色

复用现有 udp2raw 连接、加密、HTTP 和数据处理，只扩展建立阶段、所需捕获入口和状态关联。新能力命名应表达“同数据 profile 的 SO 建链扩展”，不能宣传为完整的内核 TCP 实现。

分别确定三种角色：

| 角色 | 决定什么 | 建议规则 |
|---|---|---|
| TCP 外形主动性 | 谁发送首个 SYN | SO 模式双方主动；旧显式入口按原模式 |
| udp2raw/HTTP client、server | 谁进入已有哪条应用握手分支 | 对已认证的双方身份排序，稳定决定 |
| 提名控制方 | 谁选择本轮获胜候选并发 Nominate | 身份与本轮 tie-breaker 共同决定，认证绑定 |

不要让“双方主动”变成“两端都运行旧 client 并等待对方执行 server 流程”。同样，不因业务数据来自内层 UDP 就选择 UDP NAT 映射。

### 5.2 握手状态机

TCP 标准允许 simultaneous open；NAT 的 TCP 行为要求也讨论了这种情况。但标准要求不等于每台实际校园网设备均支持，更不能证明后续非标准数据 profile 一定通过。[S5] [S6]

实现要求：

1. 每个有效 Attempt/候选对分配一次 ISS，记录对端 IRS；重传不得更换本次 ISS。
2. 首版 SYN 不带业务数据，按 SYN 占一个序号处理。
3. SYN_SENT 收到合法 bare SYN：记录 IRS，进入相应同步状态，以原 ISS 发 SYN+ACK，确认 IRS+1。
4. SYN_SENT 收到确认本次 SYN 的 SYN+ACK：走普通主动分支，发送所需确认并推进。
5. 交叉 SYN+ACK、重复 SYN、重复 ACK 幂等；依状态允许正确结束握手，不要求每个 simultaneous-open 轨迹都必须恰好六个包。
6. 使用正确的 32 位序号比较；覆盖回绕、错误 ACK、旧 ISS、旧 AttachId、旧候选版本。
7. 握手完成进入既有 HTTP/udp2raw 流程，再经 MeshLink 完成双向路径检查。单独的 TcpShapeEstablished 只能是中间事件。
8. RST/FIN 处理按所属状态和受管 tuple 限定。应用丢弃一个 RST 不能撤销上游 NAT 已经做出的状态变化。

TCP 包头中没有 AttemptId。对于交叉 SYN 或变化的源端口，只能依受管本地资源、当前授权 IP/端口窗口、ISS、时间窗和有限半开状态进行初步关联；后续认证才决定真实 peer。不得把命中一个 IP、端口或 seq 当作成员身份成立。

### 5.3 定时、并发与数据兼容

建议 SO 建链初值：单轮 8 秒；在状态仍需要时按约 0、0.5、1.5、3.5、6.5 秒发送重试，并加入小幅抖动。实际实现应基于已有 RTT 和全机预算调整，不把该表写成 RFC 的 TCP RTO 要求。正常连接已推进时取消过时定时器，不能继续盲发旧 SYN。

普通 UDP 轮次仍为 6 秒；现有 TCP 显式入口/映射流程原有的约 12 秒轮次另行保留和测量。三者不能共用一个含义模糊的 timeout。排队尚未获得资源时不消耗握手轮次，但计入用户总等待时间。

如果多个 peer 共享原生事件循环，现有 HTTP 等待改成逐会话定时状态，保留 HTTP→bare 的顺序和当前兼容间隔。禁止一次约 32ms 的阻塞等待暂停所有 peer 的收发。先用现有 C++ 协议回归确认序号关系，再用真机确认线上行为；不顺手改成“HTTP 数据必须推进 seq”的新 profile。

每个 peer 仍最多一个正式 Active 和一个 Candidate。若原生全局状态不能直接承载多会话，由唯一捕获 broker 分发到现有协议实例；不得用多个重叠 WinDivert 句柄代替隔离设计。

8秒是整轮共享期限，包含TCP外形握手、现有udp2raw握手及必要的路径认证；每进入下一阶段只获得剩余时间，不能分别再加8秒。

### 5.4 PoC-2 验收

先在真实 Windows LAN 的已知端点上验证，再在已明确支持相应行为的受控 NAT 正例上验证。拓扑必须独立于旧 P→Q 显式入口。

| 类别 | 最小覆盖 | 判定 |
|---|---|---|
| 正常交叉 | 同时启动，偏差 ±100ms、±500ms；不同 client/server 身份排序 | 每个确定性正例 30/30 双向认证 |
| 丢包 | 分别丢首个 SYN、SYN+ACK；在存在最终 ACK 的轨迹丢该 ACK | 有界重试恢复，不永久半开 |
| 重复与乱序 | 交叉 SYN+ACK、重复握手、延迟 HTTP/bare、seq 回绕 | 无重复晋升，无业务序号回退 |
| 负面身份 | 错误 ACK、未知源、旧轮次、过期控制 Start | 0 次错误认证，0 次替换有效 Active |
| 并发 | 两 peer 共存，一条取消/重启，另一条持续数据 | 互不释放资源、无错误分流 |
| 数据兼容 | 接入现有 HTTP＋seq-mode 3 后跑原 50Mbps/20s 顺序双向负载 | 满足原承载回归，不能只验 SYN |

在 RTT≤50ms、启动偏差≤500ms 的受控正例中，建议无损建链目标≤3秒、单次握手丢包≤8秒。统一从控制方“本地 Ready 且已收到有效对端 Ready，发 Start”起计，另报告首个 SYN 至 PathAuthenticated 的本机阶段耗时。超出测试条件时报告实际结果，不混用跨机未同步时间。

M2 Gate：真实 SO 建立、现有外层握手完成、MeshLink 同路径认证和实际业务四项均成立。纯协议回环或内核 TCP simultaneous open 成功均不能替代该 Gate。

### 5.5 UDP 已打通后能帮助什么

可以通过已经认证的 UDP_DIRECT 控制通道交换 TCP 候选、触发 Ready/Start、传递观测和加快重试协同，这能减少协调延迟。TCP 仍需自己的实际源资源、映射、过滤状态和握手；不继承 UDP 孔洞。RFC 7857 明确讨论了协议相关的 NAT 行为。[S7]

也不支持把内核 TCP socket 直接“接管”一个已建好的 FakeTCP 会话。它们的本地状态所有者和数据语义不同。若未来研究真实 TCP，应使用独立传输实现、独立候选与验收。

## 6. M3：控制协商、正式产品接入与资源调度

### 6.1 最小共同状态机

实现 Offer → Ready → Start → Check → Nominate → Confirm；可以复用现有公告字段和受认证控制消息，不要求照搬完整 ICE。

- Offer 指向双方身份、候选版本、能力和本轮尝试。
- Ready 表示源资源持有、所需捕获/接收就绪、预算已分配、角色明确。
- Start 带同一 AttemptId、候选对和本轮截止策略，重复执行幂等。
- Check 必须在候选实际承载上双向完成。
- Nominate/Confirm 指定候选对、路径代次和验证上下文。
- 取消、超时或新版本使旧完成结果失效；取消只释放自己的引用。

两端不能原子切换。新路径认证后保留旧路径接收引用，重发提名和确认直至双方收敛。初始接收重叠窗口可设 2 秒，并由共享 MeshLink 重放状态消除重复；丢 Confirm 的恢复必须可测试。发送端单一路径选择与接收重叠分开实现，不默认复制全部业务流量。

提名、确认和必要的切换证明共用本轮剩余期限，不能无限重发或重新获得6/8秒。候选认证完成只进入Prepared，不释放旧Active；取得与本轮NominationRevision绑定的有效Confirm后才允许切换。用有认证的PathCommit/CommitAck或等价状态证明对端也采用同一提名，不能把普通候选ping当作切换证明。

旧路径2秒接收宽限从“本端已切换且已获得对端采用同一提名的证据”开始，期满且在途引用收敛后释放。若本轮到期仍未完成所需确认/证明，发有界幂等取消并保留或恢复原有健康Active；新提名用更高revision，迟到消息不得复活取消项。暂时不一致通过有认证最终状态重同步或新Attempt收敛，不承诺分区中原子一致。Prepared/Candidate、正式Active及退役接收引用分别计数，全部占实际资源；取消不能释放其他peer的引用。

认证消息至少绑定 NetworkId、双方 NodeId/BootId、AttemptId、双方候选版本、传输 profile、角色和路径验证 nonce。对端已认证的 MeshLink 检查必须附着实际收包承载；在旧 Active 上收到挑战响应，不能自动证明 Candidate 可达。该设计借鉴 ICE 的连接检查、peer-reflexive 与提名原则，不声称自定义协议已成为完整 ICE/ICE-TCP。[S8] [S9]

### 6.2 正式模块接线

按照当前仓库定位相应实现，完成以下闭环：

| 范围 | 代码工作 | 产品 Gate |
|---|---|---|
| Core：Binding/Mapping/STUN | 提供 Lease、观察与实际资源描述；旧 P→Q 映射链保留 | 一个公网候选可追溯到所有依赖 |
| native：backend/filter/connection | 受管理 attach、SO、多 peer 分流、真实 tuple 和统计上报 | 正式二进制使用同一能力 |
| MeshTransport/PeerTransports | 将 FakeTCP loopback 适配为统一数据报承载 | 上层不以 loopback 端口充当路径身份 |
| MeshRunner/RuntimeServices | 候选创建、共同提名、保持、失败回收与服务重启 | 正式启动流程实际调用新逻辑 |
| Discovery/Registry | 能力版本、增量事件、预算与有效期 | 两端可互相发现且正确协商 |
| GUI/诊断 | 显示直连类型、质量状态、失败阶段及恢复进度 | 部分连通不显示为完整 mesh |

保留每成员一个 MeshLink，不在新适配器里重建密码对象。正式路径取得 Path 引用后再结束 Attempt。每条传输必须能回报实际外层地址族、协议、源/目的端点、资源身份和验证代次。

M1通过后，旧P→Q入口的P、Q也接入明确的唯一所有者：P由辅助流Lease持有，Q由相应native资源持有。保留入口行为，不保留用ReuseAddress或abortive close进行共享/快速交接的做法；每个资源仅由其唯一所有者bind。复用的组播发现socket等其他用途单独判断，不做全仓库不分用途的替换。

### 6.3 版本管理

分别记录 API 路径版本、meshProtocol、候选/控制消息版本、native ABI 和数据 profile；/v3 API 与 meshProtocol 4 不需要人为改成相同数字。

旧 peer 仅使用它明确声明的能力；旧单 Endpoint 可适配成 legacy 显式候选。新增 SO、UDP_DIRECT、IPv6、共同提名字段进入现有认证范围。不得因未认证字段缺失而悄悄降级安全语义；需要新语义的两端必须显式协商。

Codex 应给出兼容矩阵：当前旧客户端、当前新客户端、新协调服务、旧协调服务四者哪些组合支持什么。材料所述 0.3 与 0.4 不兼容，不在本轮默认为可混网。原生 ABI 不匹配时启动前报清楚原因，不能继续跑不同含义的参数。

### 6.4 每设备一条长轮询

当前八设备请求成本来自原材料：[P1]

| 场景 | 八设备 GET/分钟 | PUT/分钟 | 合计 |
|---|---:|---:|---:|
| 未全部连通、端点稳定 | 192 | 32 | 224 |
| 全部连通、端点稳定 | 96 | 32 | 128 |
| 端点持续变化、按最小间隔发布 | 192 | 192 | 384 |

512 请求/分钟/网络的限额还有目录、失败重试和新握手消息要消耗。不得给 28 个 pair 各建一个独立高频轮询。

实现建议：

1. 每设备最多一个挂起请求，初始 hold 25 秒，客户端专用超时 35 秒；普通请求保留现有 8 秒超时。
2. 游标、序号、幂等事件与重连补取；每设备队列初值最多 128 项，可合并状态，溢出返回需要重同步。
3. 候选语义版本与公告保活序号分开。15 秒一次内容不变的续存不得让所有设备的长轮询立即返回。
4. Ready、Start、取消等因果事件及时发送，不能被普通公告 2.5 秒节流无条件压住。
5. 全局挂起 waiter 初值 64；同时保留现有连接硬限制并为短请求留余量。连接数与 waiter 数分别监控。
6. 客户端每设备普通请求目标≤48次/滚动60秒，维护/恢复预留≤8次，所有模块共用账本。八设备目标≤448，给服务端512限额留64余量。
7. 对容量拒绝、429、断线使用有抖动退避；回退到受限轮询不能制造重连风暴。
8. 检查部署代理的空闲超时、HTTP 版本和连接复用；长轮询仅为控制面，不承载业务数据。

在没有语义变化唤醒的理想空闲条件下，25秒 GET＋15秒 PUT 约为每网络 51.2 请求/分钟；频繁状态变化时不承诺这个数值。验收同时记录真正请求数、事件延迟、429 和服务端队列。

最终序列化后仍遵守 4096 字符 cipherData 限制。设备级候选公告与成对握手事件分别编码，必要时有界分批；不要发布全部候选笛卡尔积，也不要靠任意扩大限制解决设计问题。

### 6.5 全机资源和公平性

默认资源上限维持公网 UDP socket 总计 8 个，含 Active、Candidate、探测和尚未释放的退役引用。七条活动 UDP 路径各占一个 socket 时，只剩一个额外资源；若改成共享 socket，也仍要保持唯一接收所有者和按 peer 鉴权。

受管理 TCP 端点建立独立账本，普通配置初值同样最多 8 个资源；多个 peer 优先共享一个已证明可安全分流的 EndpointOwner。旧 P→Q 的 P、Q、辅助连接及进程逐项列入总资源清单，不能因不属于新 Lease 类而漏算。若实际兼容配置超出新增池上限，使用明确的兼容资源配额并在报告解释，不强行关闭正常旧路径。

调度初值：

- 全机最多 1 个重型 native 建链/高成本探索，最多 2 个 peer 同时执行轻量候选检查；还须获得实际剩余资源。
- 全机可调度控制包60pps、burst8，控制字节初值64KiB/s；建链、探索和下述维护共用这个总账本。
- 普通 UDP 单轮最多 6秒、120包、64KiB；SO 为8秒且沿用120包上限。
- 每轮先预留24包用于完成认证、必要 PMTU 与提名；未用预留可动态回收，不能搜索耗尽后声称“孔已打通”。
- STUN、原生 SYN、重试、HTTP 建链和协议确认分别计账；记录本机可观测到的真实包数量，不能把一次函数调用当成一个包。
- 可调度报文走统一令牌桶；helper由内核产生的ACK等开销也进入线上统计，通过查询准入间接限制，不能为限速截断helper。若不可调度开销使实际值超预算，降低查询/尝试频率并报告，不声称本机控制器能直接限住所有内核包。
- 可调度保活、恢复探测、测量反馈共用Maintenance子账本，初值24pps、burst8，包含在全机60pps内；有维护等待时优先保证最多12pps的额度，剩余按需竞争。高成本搜索另受48pps上限；维护实际占24pps时搜索最多取得其余36pps。子类限额满时合并反馈、延后非必要探测，保护有效Active，不另开旁路。
- 与正常业务直接关联的协议ACK等计入WireOverhead和真实出口字节，不套进低速Maintenance限额，也不为满足该限额丢必要ACK。压测另有明确负载预算；业务包不占120包尝试限额。对于helper内核ACK按前述统计和查询准入处理。
- 优先维持 Active、处理硬故障、建立缺失 peer，最后优化健康路径；轮转并增加等待老化。
- 排队等待、资源获取、握手和业务稳定四种耗时分别显示。

七条路径同时按120包/6秒执行，需要约140pps，超过全机60pps。该算术必须进入调度压力测试。高成本实验扩池见 M5，默认配置不得悄悄扩池。

M3 Gate：八实例调度测试符合账本，正式 MeshRunner 完成两机建链、迁移、取消和兼容；随后进入 M9 的真实八设备验证。

## 7. M4：UDP_DIRECT 同 socket 正式接入，完成 PoC-3

### 7.1 唯一资源与接收所有者

保留当前 C# UdpTraversal 持有的独占、未 connect UDP socket。一个接收循环通过 ReceiveFrom 获得实际来源，分流 STUN、认证检查、提名和 MeshLink 数据。用适配器向 MeshLink 暴露 SendDatagram、ReceivedDatagram、Stats 和 Close/Release。

保持 SocketResourceId、地址族、接口、实际本地端点和出口代次。不要关闭获胜 socket 再绑定同一数字端口；不以 ReuseAddress 或另起 native receiver 实现“交接”。Windows 的端口复用不能替代确定的接收所有权。[S2]

接收分流必须验证长度、消息类型、版本、事务、来源和认证；协议头冲突或未知类型不能误交给另一解析器。池化缓冲区的归还时机与异步处理寿命明确。终止 Attempt、释放失败候选、暂停 STUN 查询都不得关闭仍由正式 Path 持有的资源。

如果日后要跨进程转移 socket，再单独设计唯一读取者和共享句柄生命周期；本轮无需以此增加首版复杂度。

### 7.2 peer-reflexive 接入

已认证检查来自公告之外的源端点时，创建有界 peer-reflexive 候选，并从实际收到该包的同一 socket 发起反向认证。认证通过后才能提名，不能仅以源地址更新 Active。

测试至少包括：

- 双边 EIM＋APDF，已交换外部端点且双方主动检查。
- 稳定EIM＋ADF一侧，对APDM＋APDF一侧：稳定侧先向hard侧公告公网IP发包以开放地址过滤；hard侧随后从实际持有资源向稳定端点发送，稳定侧收到变化源端口并反向检查。该正例要求hard侧实际公网IP仍是已开放的IP；只允许端口变化，不能漏掉ADF预热前提。
- 未知源被前置 APDF 丢弃的负例：应用根本没收到包时，不能靠 prflx 补救。

真实源端口学习与“在本机 loopback 中完成 challenge”是不同证据。TCP 的受限未知源接入也遵守先有限握手、后真正成员认证的原则。

### 7.3 封装长度与 PMTU

按现有内层 IPv4 MTU1280、MeshLink48、AEAD tag16计算：[P1] [P2]

| 层次 | UDP_DIRECT 无新增 framing 时长度 |
|---|---:|
| 完整内层 IP 包 | 1280B |
| MeshLink UDP payload | 1344B |
| 外层 IPv4 IP 包 | 1372B |
| 外层 IPv6 IP 包 | 1392B |
| 现有1400B UDP payload 探测对应外层IPv4 | 1428B |

任何新增 framing、IPv4 options/IPv6 扩展头均需另计。FakeTCP 的 udp2raw 头、加密填充、TCP options 等由实际序列化计算和线外抓包确认，不能套用上表。

先做小包认证，再探测实际所需长度。IPv4 使用 DF；IPv6 保证探测没有借助源端分片。接收端确认实际长度，处理 ICMP 缺失和大包黑洞。首版可对所需大小最多重试3次，并用稍小探测区分丢包与尺寸问题；双方向独立判定、消耗真实预算。DPLPMTUD 的要点是用报文层反馈确认尺寸，不能把 IP 分片后的送达当成未分片 PMTU。[S12]

1400B payload 作为余量探测，不是刚性准入条件：1344B稳定可达而1400B失败，仍可能满足当前业务。反之，仅一次1400B成功且未禁止分片，没有完成该 Gate。

首版不能承载约定虚拟 MTU 的路径标记 MtuInsufficient，保留已有合格 Active。不要为一个弱候选悄悄缩小所有 peer 的 Wintun MTU。若确有必须覆盖的低 PMTU 环境，再以独立版本实现有界分片重组或明确的内层 MTU 管理；有资源上限、超时和认证后分配，不能临时无限拼包。

外层 IPv6 最小 MTU1280 不足以直接容纳上述1392B报文；IPv6能力发布依实际路径测量。切网、路径代次变化以及“大包失败、小包仍通”触发重测。

### 7.4 PoC-3 完整验收

运行真实的 Wintun → MeshLink → UDP_DIRECT 链路，不只测试 UDP helper。

- 两类确定性正例各30/30；从STUN、检查、提名到业务的 SocketResourceId 一致。
- Path先retain，Attempt结束、失败候选释放后，获胜socket继续双向业务。
- 完整虚拟MTU报文通过，低PMTU正/负边界判定正确。
- 真正入站来源、选定候选对和MeshLink身份一致。
- 丢失Confirm、重复Nominate、接口变化、旧轮次迟到均不误释放或误提名。
- 新旧路径共用重放状态，重复内层包不重复注入Wintun。
- 严格负例按预算结束，socket与引用恢复到应有基线。
- 正式路径可承载普通IP业务；目标校园网UDP限速导致50Mbps不达标时记录质量不足，不把它误判为同socket实现失败。

M4完成的是可用直连承载能力；是否用它替换FakeTCP由M6的策略决定。

## 8. M5：严格 NAT 的独立观测与有界增强

### 8.1 先观察实际行为，再选择策略

每条观察记录 Protocol、TransportProfile、ResourceId、实际本地端点、接口/出口代次、观察目的、公网端点、时间、有效期、握手阶段和证据类型。

分别区分映射行为EIM/ADM/APDM、过滤行为EIF/ADF/APDF、TCP状态跟踪和目的/连接相关差异。“NAT4”“校园网”仅作用户场景标签，不能代替策略输入。未观察到的能力为Unknown，不从几次结果推断永久属性。[S6] [S7] [S10] [S22]

普通打洞并行进行，不等待完整分类。候选优先级依次为：可认证的LAN/真实原生地址、已验证显式入口、普通SO/UDP双向检查、实际到达触发的prflx、具备证据的小窗口预测、满足单稳定端前提的概率探索。

UDP完整行为发现需要具备两个独立公网IP及所需端口/来源变化的受控反射服务；可以是一台多地址服务器。过滤实验使用新鲜资源，避免先前外发已改变待测状态。只有一个IP时返回局部观察，不能伪报完整RFC5780分类。[S10]

### 8.2 TCP 观测必须使用实际端点

当前一条独占 TCP STUN helper 不能通过“再创建第二个普通 socket 绑定 P”扩展为多目的观察。内核辅助流结果和 native 到新目的的观察分别记录，并通过同一本地资源的真机证据建立关联。

新增可配置的控制专用 TcpShapeObserver。最小默认实现为受限只读SYN观察器＋现有HTTPS登记/取回，不要求先实现完整FakeTCP反射器。同一Native EndpointOwner对已登记目标发实际SYN；实现方式与可信归属要求见以下规则：

- 服务器只观察和回应有界探测，不转发业务，不持有生产MeshLink密钥或组网业务明文。
- 通过已有认证HTTPS控制会话申请短时ProbeTicket，限定目标地址/端口、数量和时间；响应关联ProbeId、观察点和实际来源。
- 两个公网IP×两个端口的四个探测目的均避开现有helper的真实远端tuple，否则raw与已建立内核流拥有相同四元组，无法同时排除helper又接管raw。登记实际ISS/目标/短时窗，重传去重；不为塞入ProbeId默认增加TCP option或SYN payload，避免改变被测profile。
- SYN级观察只能证明该探测的源端点和抵达情况。握手回程、完整FakeTCP profile通过、成员路径认证分别记录，不相互替代。
- 输出SynObserved、TcpHandshakeVerified、LegacyPayloadVerified三个独立证据级别；只读观察首版未做的层级标NotTested。观察组件必须位于真实公网入口且具备抓包能力，不能把CDN/L4代理改写后的来源当NAT观察，也不能把两个同IP域名算两个独立地址。
- 普通内核TCP/STUN监听器不能被假定理解当前HTTP/bare序号重叠的完整profile。若采用捕获式观察，明确服务器额外的抓包能力和部署依赖。
- TCP头没有ProbeId；只用ISS/目的端点/时窗关联的结果属于有限置信观察，存在冲突就返回歧义或重试，不能提升为成员认证。
- 拿不到该观察设施时实现配置、协议和受控测试，真实跨目的TCP行为保持Unknown；继续执行已有候选，不能回退为“用UDP结果代填TCP”。

候选端口在同一协议的反射目标间相同，也仅是该观察窗口的证据。TCP连接状态和实际FakeTCP业务仍以M1/M2的对等路径验证为准。

### 8.3 小窗口端口预测：实现、默认条件关闭

实现端口保留、固定步长、分块分配的简单可解释模型，记录支持样本和置信条件。不要一开始加入复杂机器学习。

建议启用门槛：

1. 同一协议、出口代次采集至少20个分离观察窗口，至少一半用作留出验证。
2. 下一次分配落入至多8个预测端口的留出覆盖率≥90%。
3. 模型含背景连接干扰实验；只会解释训练样本不能启用。
4. 预测年龄初值≤2秒；源资源和必要映射保持存活。
5. 两次连续真实预测失败立即停用当前模型；出口变化无条件失效。
6. 每轮仍服从全机与Attempt预算，过期预测不反复扫同一窗口。

90%是局部模型开关标准，不是端到端打洞成功率。共享分配器、多层NAT、并发端口消费和非顺序分配会破坏预测，标准文献也指出了这些限制。[S11]

当前“若干STUN IP结果不同且无固定差值”只支持这些样本呈目的相关差异，不能据此证明所有未来分配完全随机。

### 8.4 单稳定端概率探索：实验默认关闭

仅在一侧该协议公网IP/映射稳定，另一侧能同时保持多个到该稳定端点的映射时启用简化模型。所有探测限定为已认证对等方声明并允许的公网IP，不扫描无关地址。

这里“稳定”要求easy从同一实际资源向hard全部被猜端口发包时，公网源端点始终等于hard各映射此前所指向的固定easy端点。只证明对一个STUN服务器结果不变不满足前提；同一本地端口也不等于该公网不变量。证据不足则不自动启用该策略。

设hard侧有N个同时存活、互不相同的外部映射，easy侧对同一hard公网IP猜M个不同端口；端口空间大小为R。在均匀、无放回且其他条件满足的理想模型中：

P(端口相交) = 1 − C(R−N, M) / C(R, M) ≈ 1 − exp(−NM/R)。

这是端口相交机会，不是连接成功率。重发同一端口不增加M；IP变化、状态过滤、握手、时序和映射过期都会降低真实成功机会。只有两边都能获得正确信息、报文确实被放行并完成认证，才算成功。[S21]

| 理想模型参数，R=65536 | 相交概率近似值 | 本轮用途 |
|---|---:|---|
| N=8、M=120 | 1.45% | 说明原小预算不能支撑高成功率宣传 |
| N=8、M=96 | 1.17% | 预留24包后的粗略上界示例，仍忽略其他开销 |
| N=32、M=256 | 11.75% | 条件实验规模参考 |
| N=64、M=1024 | 63.21% | 只作成本对照，不作为默认扫描计划 |

R=65536仅为演算。实际支持的端口范围、保留端口、分配分布及样本相关性必须据证据修正；Windows本地临时端口范围不能直接当公网NAT的R。

实验初值采用统一且可执行的上限：N≤32、M≤256、单轮≤512个本机控制包、≤256KiB、≤12秒；搜索最多使用48pps，给同账本内的认证/完成等流量留下12pps。目标协议资源池实验上限40，包含已有Active、Candidate、退役和探测资源；实际N按剩余槽位降低，不能同时把N=32和七个活动路径之外的全部资源忽略。默认关闭的该profile显式调整对应池上限，不能通过“额外临时socket”规避总数统计。

硬预算先到即停，因此实际M常低于256，报告actualN/actualM/报文数，不能代入配置上限计算“本次成功率”。TCP每个被猜tuple还需有限的SYN状态与确认处理，不可以用UDP一次到达模型证明TCP成功。

开了N个本地socket不等于确认了N个外部存活映射。测试fixture可读取映射表核对N；真实环境无法确认时，分别报告N_requested、N_sources_sent、N_confirmed/Unknown，只给注明前提的相交机会估计，不把源资源数伪报为确认映射数。

一次仅允许一个高成本探索；同pair/出口代次失败后初始冷却5分钟，新可靠观察或网络变化可重新评估。目标路径已有足够质量的Active时不启动高成本实验。默认8个UDP资源配置保持不变，只有显式实验profile能扩池。

### 8.5 双端随机严格 NAT 与停止条件

双边目的相关、不可预测时，不套用上面一维公式。首版交付能力诊断、有限普通尝试和可复现模型；复杂双端概率算法保持实验关闭，不能用无限重试补成功率。

停止结果分别为NoDirectPathWithinBudget、PredictionNotSupported、ObserverUnavailable、BudgetExhausted等。没有找到路径不等于数学上证明所有方法都不可能；它准确表示本轮在当前方法、证据与成本约束内未找到直连。

M5 Gate：观察来源和协议正确；预测有留出验证；概率模拟使用至少1000个独立种子并报告区间；受控网络核对实际映射和包计数；真实校园网结果单列。模型、受控NAT和真实网络三种证据不合并成一个“成功率”。

## 9. M6：UDP QoS 场景的选路、发包与组网效率

### 9.1 本轮质量路线

当前FakeTCP＋HTTP效果已经满足用户需求。因此本轮首先让有效承载更容易建立、更稳定地保留、更快恢复；不以研究另一种伪装格式替代已有效的路线。

至少提供以下策略：

| 策略 | 行为 | 默认 |
|---|---|---|
| PreferFakeTcp | 合格FakeTCP优先；健康期间不因UDP先通或空载RTT低而抢占 | 是 |
| FakeTcpOnly | 只允许合格FakeTCP承载；找不到则明确直连失败/质量不足 | 可配置 |
| AutoQuality | 仅对已有足够负载证据的合格路径，按统一目标和迟滞切换 | 实现，实验关闭 |

PreferFakeTcp下，若FakeTCP不可用而UDP_DIRECT已认证且MTU合格，可按明确配置提供Degraded直连；界面说明未满足目标串流质量。用户选择FakeTcpOnly时不做该回退。任何模式都不引入业务中继。

路径资格分层：

1. Reachable：有报文到达。
2. Authenticated：双向同路径、成员和轮次验证成立。
3. MtuQualified：可承载当前约定报文。
4. QualityObserved：在相应负载、方向和新鲜度范围内有质量证据。
5. Selected：符合当前业务策略并完成提名。

不会从小包 RTT 推导50Mbps容量，也不会从FakeTCP SYN成功推导数据profile可穿过整条路径。

### 9.2 质量数据与测量成本

按方向记录：

- 发送应用字节、接收有效字节、物理线上字节和封装开销。
- 丢包、迟到、重复、乱序距离、连续丢失长度。
- 空载/加载RTT分位数、发送队列年龄、队列丢弃、CPU/分配成本。
- 首包时间、首次恢复和持续稳定恢复。
- 测量窗口、流量等级、目标速率和时钟误差，防止跨条件比较。

可在认证维护消息中加入有界接收计数或ACK位图供测量，但不据此重传业务，也不等待缺包后再交付后续包。接收观察不应变成另一套外层可靠传输。

优先使用已有业务样本。无真实负载证据的备用路径只标QualityUnknown；不能为每个候选同时跑50Mbps。主动压测必须明确时长、速率、总字节和出口共享额度，且不影响已有目标串流。不同方向分别判断，避免下行正常掩盖上行限速。

公网观察只能支持“该时间窗UDP上行表现不足，FakeTCP表现较好”；缺少网关规则或受控对照时，不把全部丢包归因于特定QoS设备或DPI。

### 9.3 切换迟滞与恢复

建议AutoQuality初值：至少3个连续5秒窗口出现稳定收益，最短驻留30秒，普通切换冷却60秒；候选必须有同等负载条件下的新鲜证据。评分先执行身份/MTU/策略硬门槛，再比较时限送达、加载延迟、丢失和资源成本，不用一个未说明权重的“质量分”覆盖失败原因。

硬故障允许跳过普通驻留/冷却，仍需新路径认证和有效资源。若没有满足业务目标的替代路径，降低状态并上报，不在低容量UDP路径持续堆积原速率数据。

健康判定必须验证双向性。收到对端认证数据只证明其中一个方向；对端收到本机数据的反馈或往返challenge证明另一方向。负载期间复用认证业务统计，空闲时有界保活，避免全速数据加无谓心跳。

恢复工程目标按条件区分：

| 场景 | 建议目标 | 限定 |
|---|---|---|
| worker进程退出 | 本机发现≤250ms | 依实际进程通知和服务负载验证 |
| 已有合格备用路径 | 有效稳定区间起点≤3秒 | 备用已认证、MTU/质量合格；稳定确认发生在随后观察完成后 |
| 无备用的单轮SO重建 | 共享本轮8秒截止 | 不含之前排队和资源初始化 |
| 无显式退出的网络黑洞 | 初值约6秒发现，温启动总恢复目标≤10秒 | RTT≤50ms、资源可用且拓扑支持；超出条件报告实际值 |
| 两机完整服务冷启动 | 对原17—19秒结果提出≤15秒优化目标 | 可比环境的工程目标，不是八节点全网或所有网络硬保证 |

空闲2秒一次检查、连续3次失败可作为黑洞检测实验初值；先保留原约12秒健康窗口作为对照，验证误判率后再启用。不要把100ms调度周期当成100ms故障检测。

恢复记录三个时间：FirstBusiness为任意首个成功包；StableBusinessStart为随后被证明稳定的区间起点；StableBusinessConfirmed为连续3秒业务无新增中断且10次连续探测成功后的确认时刻。验收探测初值每300ms一次并计入预算；确认后回溯记录稳定区间起点。表中3秒目标指StableBusinessStart，不要求在同一个3秒内再凭空多观察3秒。首个ping后又中断的区间不能计为稳定恢复。

恢复探测属于Maintenance子账本；八设备同时恢复时按真实剩余额度调度并报告确认延迟。没有实际业务负载时只能记StablePath，不能伪造StableBusiness。黑洞≤10秒目标同样以回溯得到的有效稳定区间起点衡量，确认时刻另报。

### 9.4 pacing、有限队列与公平调度

先按出口聚合，再按peer/业务类别公平调度；七个peer不意味着一个50Mbps上行可以同时提供七份50Mbps。

第一版实现可配置pacing，先A/B验证再决定是否默认启用：

- 速率来自用户配置、已有发送预算或经过验证的容量反馈，不凭一次ping估计。
- 初始burst最多4个完整外层数据报。
- 队列目标约20ms发送量，并加每出口1MiB初始硬上限，先触及者生效；在50Mbps时20ms约125KB。
- 按真实发送字节计令牌，包含外层开销；区分应用50Mbps与线上50Mbps。
- 控制/恢复流量有小额度优先权，但不能无限抢占业务。
- 测量队列age和溢出；拥塞时及时反馈或丢弃，不无限缓存。
- 通用IP模式不猜视频帧边界。只有应用明确提供deadline/类别时才做按截止时间丢弃，不能把所有内层TCP包当过期视频。
- 不增加业务重传，不做跨包等待，不改HTTP和seq-mode以迁就pacing。

实现要核对实际定时粒度：固定每1ms只发4个常见MTU报文可能达不到50Mbps目标。4报文是A/B初值；根据实际唤醒、批量和CPU成本调整，不能靠长期忙轮询占满一个核维持指标。

pacing限制突发，不等于拥塞控制。RFC8085区分了IP隧道、已有端到端拥塞响应和未受控发送的场景。本项目应保留内层应用的拥塞响应，对未经控制的UDP负载加入速率反馈/过载断路保护；不能只因外观是TCP就假定网络容量问题已解决。[S13]

ECN/DSCP作为独立明确策略：先记录现有行为，避免在新外层上错误声明拥塞能力；实现支持时遵循IP隧道的ECN传播规则。不要把设置DSCP当成获得保证带宽。若本轮不实现完整ECN传播，保持当前已验证配置并列明该兼容边界，不伪报ECN支持。

### 9.5 有收益证据再做热点优化

对正式原生后端及C#数据路径采样，优先处理：

- 每包多次分配、复制和跨进程消息。
- 全局锁、所有peer共用的阻塞HTTP等待。
- 不必要的Wintun重建、串行等待协调完成后才初始化本地资源。
- 长轮询、STUN、网关发现和原生启动的重复工作。
- NAT资源查询/续租风暴、进程反复启动造成的端口抖动。
- 发送批处理造成的尾部延迟；批大小和等待时长均有上限。

在资源独立且不破坏来源选择的前提下，并行Wintun准备、目录拉取、候选收集；有效Active存在时复用其资源。温路径与冷启动分别优化。

记录每核CPU、单位流量CPU、allocation/packet、working set、句柄数和native进程数。原包51.5MiB是分发大小，不能写成运行内存指标。

### 9.6 其他绕过 UDP QoS 的方法如何处理

| 方法 | 本项目判断 |
|---|---|
| 现有FakeTCP＋HTTP | 已有本场景效果证据，继续作为主线；新增SO只解决建链 |
| UDP内换协议、端口或QUIC/H3 | 外层仍可能是UDP；不能据此保证避开按UDP分类的限制。QUIC本身运行在UDP上。[S16] |
| 真实TCP/TLS/WSS | 可改变外层协议，但需要不同的可靠、有序承载与失败语义；本轮不作为默认回退 |
| MASQUE/CONNECT-UDP | 外层取决HTTP版本与具体承载，不能一概说始终UDP；若通过外部代理承载业务，就不满足禁止中继约束。[S17] |
| IPv6 | 真实端到端路由可能提供另一条可达路径；不自动解除UDP限速，见M7 |
| FEC | 只在有剩余带宽、损失以可恢复丢包为主且deadline允许时才值得单独实验；硬上行瓶颈下额外冗余会消耗预算 |
| 多流/多端口条带化 | 可能只对某些按流策略有效；需重新验证顺序、NAT资源和总出口限速，本轮默认关闭 |
| DSCP、端口443等 | 只能作为已知网络的配置线索；需实际可用映射，不抢占其他服务，不视为带宽保证 |
| 其他raw IP/协议伪装 | 当前没有本项目收益证据，新增后端的NAT、平台和质量验证成本独立，不进入主线依赖 |

本轮不需要为这张表实现全部后端。要交付的是正确的选择策略、扩展接口、现有承载兼容，以及可证明的队列/恢复改进。

### 9.7 M6 验收

同设备、同路径、同配置对比当前有效udp2raw基线和新版；每次只改变被评估因素，记录测试顺序与背景负载。

1. 原50Mbps/20秒、双向顺序用例继续通过，保留它的历史口径。
2. 在原承载能提供目标带宽的环境补60分钟目标串流，采集加载RTT、抖动、队列和冻结/中断。
3. 标准质量档案初值：50Mbps应用目标，总体有效吞吐目标≥49Mbps；加载RTT p95相对空载增量目标≤20ms。具备可证明的应用deadline或单向时钟测量时，期限内有效吞吐另要求不低于同条件基线95%；不具备时该项标不可测，不能用最终到达量替代。
4. 若测试具备单向时钟误差界≤2ms，可增加50ms期限、迟到加丢失≤0.1%的目标；否则使用可证明的RTT、本地排队和应用播放统计，标记单向deadline项不可测。
5. pacing单独A/B的吞吐下降超过2%，或尾部延迟/恢复变差，则不默认启用，修正原因后再测。
6. 主动限速UDP上行、维持FakeTCP可达的受控测试中，健康FakeTCP不被抢占；降级状态、容量不足与恢复均正确显示。
7. 满载时新peer入网、候选失败、协调重连不拖垮已通链路；验证出口公平性，而不是要求七peer各自满速。

所有目标是本计划的工程验收初值。不要通过降低负载、延长末尾等待或删除失败窗口使统计看起来通过；需要调整口径时附原结果和依据。

## 10. M7：显式映射与真实 IPv6 扩展

### 10.1 保留现有入口，扩展候选来源

保留现有TCP STUN＋UPnP P→Q的已验证路线。将辅助TCP流、第一层网关的实际映射、外层观察和native入口作为映射链记录。第一层网关成功不自动代表外层CGNAT开放。

新增PCP和NAT-PMP Provider，接口返回实际端点、协议、租期、所有权、网关及状态；失败不阻塞主打洞流程。它们是候选来源，不是“映射成功即Active”。

- FakeTCP申请TCP映射；UDP_DIRECT申请UDP映射。
- PCP记录MAP nonce、实际分配端点、租期和服务器epoch；续租和删除只操作本软件确实拥有的映射。
- NAT-PMP按适用网关发现和请求顺序处理，验证响应来源、操作类型、实际端口/租期与epoch。
- 优先支持PCP，按协议响应处理NAT-PMP兼容；不向任意公网地址穷举网关控制协议。
- 使用协议规定的重传/续租机制作为基础，在后台异步执行；前台候选机会窗结束不等于武断判定网关永不支持。
- 网络变化清理旧可用性缓存；旧映射过期或网关重启导致相应候选失效。
- 所有公开候选仍需远端通过真实目标资源完成认证检查。

PCP与NAT-PMP提供网关控制能力，其适用范围和返回结果由实际服务器决定。NAT-PMP通常面向本地默认网关，PCP也不能凭内层网关响应推导外层设备已授予入口。[S14] [S15]

初值可以请求180秒租期，但以返回值为准；PCP/NAT-PMP续租按各协议要求，不机械复用现有UPnP的约60秒节奏。旧UPnP180/约60和STUN约10秒保活先保持，观察到可靠收益后再调整。

### 10.2 原生 IPv6：完成整条能力链后发布

先维持虚拟网络内部IPv4，只扩展外层地址族。软件能够启用系统已具备且被关闭的IPv6栈，但不能仅凭本地设置产生运营商前缀、上游路由与远端可达性。没有真实路由时明确IPv6Unavailable。

实现内容：

- 枚举实际地址、有效期、接口和路由，处理暂定、失效及地址更换。
- UDP_DIRECT支持对应地址族、来源、校验和和PMTU。
- FakeTCP支持IPv6包解析、构造、伪首部校验和、WinDivert过滤、源地址选择、native ABI与候选编码。
- Link-local仅用于同链路并携带正确scope，不能发布为跨公网可达候选。
- 各方向做实际认证检查；没有NAT仍可能存在状态防火墙。[S19]
- 按M4验证实际完整报文尺寸，不能用“IPv6至少1280”代替1392B及更多开销的验证。
- IPv4/IPv6候选有限竞速，遵守资源预算；健康FakeTCP不因IPv6小包先通而自动被抢占。
- IPv6出口UDP质量仍独立测量，不假定能避开同一网络的QoS策略。

不把Teredo、外部隧道代理、VPS转发或第三方下一跳列为本业务的“硬开IPv6”实现。网络本身没有原生IPv6时，继续执行IPv4直连路线。

M7 Gate：代码与受控测试完成；实际网关/IPv6环境不可用时，Provider状态和原因正确、不阻塞主线、不发布虚假能力。面向用户默认开启某项能力前，需要该地址族/平台的真实业务证据。

## 11. M8：会话安全、切网与服务生命周期

### 11.1 保持已成立的密码不变量

回馈已经表明Active/Candidate共用每成员MeshLink的序号和重放状态，并且重建有新epoch。本轮保留该实现，不因新承载另起同密钥计数器。[P2]

必须随新功能验证：

- 同方向、同密钥下nonce唯一，重启和候选迁移不能重置到已用序号。
- 候选与Active共享重放判断，同一包经两条路径到达最多注入一次。
- RetainPath只持有资源，不是认证；旧会话/旧候选不能凭迟到确认复活。
- 新协商的身份、方向、BootId、AttemptId、能力、角色与候选版本进入认证上下文。
- 内层源虚拟IP归属于发送peer，目的地址为本机受允许地址；不能让一个成员冒充另一个成员。
- 撤销取消该成员所有Attempt，并执行明确的数据授权失效规则。
- 外层解析在认证前即做长度、状态和资源上限检查；内层AEAD不替代外层安全解析。

AEAD要求调用方保证nonce使用规则；它本身不能替代完整的重放保护或成员授权。[S18]

当前创建者生成成员私钥、缺少PFS、网络级外层共享密钥等是既有信任与密钥管理范围。本轮不扩大这个范围，也不暗中声称已改变。若要更改成员密钥生成/PFS/外层轮换，另立明确密码协议版本和迁移任务；它们不是证明M1/M2可行性的前置阻塞项。

### 11.2 生命周期分离

| 生命周期 | 到期/变化影响 | 不能直接推导 |
|---|---|---|
| 公告有效期，当前120秒 | 新候选不再可靠 | 已认证业务一定中断 |
| 映射租期，当前UPnP180秒 | 对应入口需要续租/重建 | 协调在线就等于映射有效 |
| 路径存活窗口，当前约12秒 | 触发实际健康判定 | 一次STUN超时就关闭全部路径 |
| 成员授权/撤销 | 是否允许继续业务 | 永远离线仍能得到即时撤销信息 |
| Native AttachId | 本次原生使用源资源的授权 | PID或端口号相同就属于同一次实例 |
| 出口/接口代次 | 观测和Attempt适用范围变化 | 任意网络通知都应立即销毁健康链路 |

真实出口变化使相关观察过期并触发重新验证；无关接口事件不应无条件中断Active。旧异步结果携带原代次，不能覆盖新状态。存在相同wire tuple时，generation仍只是本地控制信息，不能替代M1的捕获互斥。

STUN查询不可复用、辅助连接关闭与端口资源失去可持有性分别验证。仅查询失效且源资源仍有效时，持续业务由路径健康决定；若端点已无法保证所有权，就撤销相应native接入，不能继续冒充有效Lease。

### 11.3 控制中断与恢复

增加双端协调HTTPS都不可达至少6分钟的测试，覆盖当前120/180秒边界。说明STUN、网关、现有业务peer在该测试中哪些仍可访问，不能把“仅屏蔽协调”描述成“所有外部依赖均断开”。

默认遵循已有合法成员授权：公告过期不单独杀死正在认证通信的路径；授权本身有绝对到期则照常执行。该测试必须处于合法授权时段，不为通过测试临时延长安全时限。控制恢复先获取最新目录与撤销，再处理迟到事件。

分别再测反射服务不可用、网关续租不可用，报告每条路径真正依赖什么。控制故障时业务可以持续，不等于新的严格NAT peer一定能加入。

### 11.4 Windows 服务、驱动与资源恢复

覆盖worker被杀、父服务被杀、GUI退出、服务重启、机器重启未登录、休眠/唤醒、NIC断开、Wi-Fi/有线切换、IP变化。

- GUI和服务对同一网络拥有一个有效资源管理者；二次启动不能抢占端口或Wintun。
- 验证服务账户的DPAPI/ACL访问、配置路径、工作目录和驱动装载。
- native关联JobObject，父子IPC失联触发停止注入；验证句柄继承和异常时序。
- 同一broker承载多peer时，把进程故障作为共同故障域验收，记录全部受影响peer和公平恢复顺序。
- 根据实际backend处理WinDivert接收/注入方向、checksum offload、路由和接口选择；观察网卡上真实包，不只看本地截获副本。
- 回收只针对自己的端口、映射、Wintun、路由和进程。TIME_WAIT依据socket正常状态解释，不使用Linger(true,0)或强制重绑把它伪装消除。[S20]

正式冷启动必须通过独立可达的协调HTTPS/DNS链路完成，不借旧EasyTier虚拟网络。既有Wintun就绪8.414秒等数据用于定位初始化成本，不能当新网络独立bootstrap证据。

### 11.5 禁止中继必须进入实现检查

对本机Wintun发出的包，只为目标peer选择直接承载。对peer入站的业务，只向本机协议栈交付符合该peer授权的报文；目的为第三名成员时拒绝转发。

至少测试A—B、A—C可通而B—C不通的拓扑：B发往C不能经A成功，GUI显示局部连通。协调/反射服务器检查API、缓冲与线路统计，不存在承载任意业务载荷的转发入口。

这项约束适用于创建者、管理员设备和所有未来传输后端；不能在M5失败时将创建者默认为网关。

M8 Gate：受影响安全不变量、生命周期和恢复测试通过后，对应功能才能在正式配置启用。不存在“先全部上线，最后再补身份和资源检查”的阶段。

## 12. M9：联合验收、打包与交付

### 12.1 前三个最小 PoC 的固定顺序

| PoC | 唯一主要问题 | 最小真实环境 | 通过后进入 |
|---|---|---|---|
| PoC-1 / M1 | 独占helper端点与native按授权收发能否共存，谁持有和回收资源 | 两台独立Windows网络栈＋反射流；先LAN，再可用公网正例 | 正式Lease/attach/捕获所有者 |
| PoC-2 / M2 | 保留现有数据profile时，原生双主动能否完成握手、认证和业务 | 两台Windows＋明确支持SO的受控拓扑 | 正式native SO与协商 |
| PoC-3 / M4 | 既有UDP打洞的获胜socket能否一直承接真实Wintun业务 | 两台Windows＋明确的NAT/PMTU正负例 | 正式UDP_DIRECT与质量策略 |

PoC-1不同时引入SO或大范围未知来源；PoC-2不同时改HTTP序号；PoC-3不顺手迁移socket所有权到native。这样能在失败时定位原因。三个PoC通过后仍须完成M3—M9对应产品工作，不能作为最终停止点。

### 12.2 分层验证矩阵

| 层级 | 能验证 | 不能替代 |
|---|---|---|
| 纯状态/模型 | 引用、期限、幂等、预算、概率假设、协议状态 | Windows驱动、真实NAT和校园网 |
| 真实C++协议回环 | 当前HTTP/bare与udp2raw事件循环 | WinDivert、实际端口、内核RST |
| 真实Windows LAN | 所有权、捕获、注入、原生握手和实际应用链 | 公网映射/过滤行为 |
| 受控NAT | 指定映射、过滤、状态、丢包和PMTU条件 | 所有真实运营商设备 |
| 真实WAN | 该时间、出口、设备组合下的实际效果 | 任意NAT4总体成功率 |
| 安装后运行 | 正式包、服务账户、驱动、冷启动及升级恢复 | 只有开发机执行的测试结果 |

受控NAT fixture必须记录实际映射/过滤状态和抓包。给规则文件起名“symmetric NAT”不是验证；需要确认TCP和UDP实际行为，尤其是SYN状态与映射分配。

最低组合覆盖：

- 无NAT/LAN、EIM不同过滤、单边目的相关、双层NAT。
- SO允许正例与状态防火墙拒绝的明确负例。
- 固定步长/端口块/随机模型，加入背景连接竞争。
- 大包可达、1372B可达但1428B不可达、ICMP被过滤的PMTU黑洞。
- 同公网IP的两个peer、接口多地址、旧tuple迟到。
- 两节点、三节点和八节点；同时入网、单困难peer、已有串流时新增peer。
- A—B和A—C可通、B—C不可通，确认没有成员转发。
- 单worker故障、共用broker故障、服务重启、未登录冷启动、休眠与出口变化。
- 双端协调不可达超过6分钟，以及协调恢复后的旧事件。

每个确定性机制正例采用30轮初始验证；已由同一机制覆盖的笛卡尔组合不盲目重复30轮。新增复测仅为具体剩余风险或必需发布Gate。概率模型至少1000独立种子，真实WAN按已执行次数给分母和环境，不将模型轮数并入实测样本。

### 12.3 性能与规模门槛

- 两设备复现原有承载回归，再完成60分钟质量测试。
- 八个隔离实例/虚拟运行环境先验证协议、调度和资源压力；八设备发布等级需要八台真实Windows终端，在明确记录的实验网络中检验28条无向直接关系。不要求八个不同校园网出口；缺真实终端时该发布Gate保持Blocked，其余交付继续。
- 在故意部分不可达的拓扑中，显示正确的局部连通，困难pair不能长期占满资源。
- 每设备验证7个peer的预算、公平性和资源释放；不要求它们各自同时达到单设备的全部上行带宽。
- 冷启动/温恢复分别报告成功数、总数、p50/p95、稳定恢复和失败成本。
- 负载试验记录抓包丢失、计数器位置和offload状态；抓包自身丢包不能直接算网络丢包。
- 密钥、明文和长期全量业务pcap不进入默认诊断包；用于特定测试的抓包按授权范围保留。

不存在真机、指定NAT或外部观察设施时，继续完成可独立进行的实现、受控测试、打包与说明，并准确标记对应Gate为Blocked。不能把“环境不可测”写成“已通过”，也不能把它写成代码已被证明不可行。

| 每设备请求额度 | 普通48＋预留8/滚动60秒 | 八设备目标448，服务器硬限512仍有效 |
| 长轮询waiter | 每设备1、全局初值64 | 与服务器总连接128分别计数 |

| 公告有效期 | 120秒，现值 | 与数据存活/授权分离 |
| UPnP租期/更新 | 180秒/约60秒，现值 | 其他协议按实际返回和协议规则 |

| pacing burst/队列 | 4报文/约20ms、出口硬限1MiB | 按实际wire字节，A/B后决定默认 |
| 控制中断试验 | 双端至少6分钟 | 授权合法，明确其他依赖是否可用 |
| 长时间串流 | 至少60分钟 | 同条件旧承载对照 |

60秒机会窗到期，应结束该前台操作并输出本轮结果。后台重试是新的、可见且受冷却的操作，不因每次发现候选就无限延长同一个Attempt。八设备加入时记录每pair排队和全网完成分布；两机≤15秒冷启动目标不能套到所有28条关系。

“最多两轮”按LegacyExplicit、FakeTcpSO、UdpDirect等明确方法/profile分别计数，全部仍共用60秒及全机资源。剩余时间不够完成新轮次就不启动，不能让方法数乘出更长前台等待。30秒退避用于前台机会结束后的后台重试，不无条件插在同一机会内的有界策略推进之间。

任何调参都保存调整前后值、实际环境和结果。不要以提高默认扫描预算替代资源正确性，也不要以缩短所有超时来伪造建链效率。
