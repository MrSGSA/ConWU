# 协调服务可靠性与迁移

2026-11-06。基于 `93aa0aac` 继续修改。**本轮仅修改源码、补充回归和做静态检查；按用户要求未编译、未打包、未部署。下列新增功能尚不能视为已完成运行验收。**

## 范围

延续统一设备角色：一台 StreamLink 设备可以提供协调、参与组网或同时承担两种角色。协调默认关闭，提供协调不自动获得成员管理权。成员平等管理仍使用单一权威 Registry 的原子提交；本轮未实现多副本复制、选举、自动接管或脱离协调服务。

DDNS 更新客户端可以运行在普通电脑或路由器，不要求用户租服务器；DNS 服务商提供第三方地址公告。DDNS 不会使 CGNAT 后的设备变得可达。接受连接仍需可达公网 IPv4/IPv6、有效映射/已有洞，或可达的代理。Cloudflare Tunnel 可以暴露内网的 HTTPS 协调，仍依赖 Cloudflare 和运行中的源站；它不会自动承载 FakeTCP＋HTTP 视频业务。STUN 发现映射，也不代替设备之间交换候选地址。

## 本轮源码改动

- 协调宿主清理使用独立异常边界，失败不应终止普通成员停机流程；观察宿主停止信号并重新启动，启动失败每 15 秒重试并显示下一次重试时间。协调角色不调用网络数据面的重建流程。
- 本机协调设置增加 `PublicUrl`、`PublicCertificatePin`，默认均为空。保存外部检查地址不会重启监听或丢弃正在等待的配对房间，也不会改写当前网络绑定的协调地址。
- 监听 HTTPS 证书在启动时检查私钥、有效时间；状态显示到期时间，并在 7 天内提醒。更换监听证书文件后需关闭并重新启用协调角色，目前不做证书自动热加载。
- 外部 HTTPS 检查使用新随机 challenge 和当前进程随机实例 ID，拒绝缓存响应或指向其他源站的健康响应。检查最长 8 秒，完成后间隔 60 秒再检查；取消/切换设置时丢弃旧检查结果。限制响应 16 KiB，禁止重定向和系统代理，不发送成员凭据。
- DNS、连接、TLS、HTTP 错误、协议不符和源站实例不符分开显示；HTTP 403 指向访问策略检查，5xx 指向代理/源站检查。错误后检查恢复会更新当前提示，不保留旧错误。**本机经外部地址自测成功不等于所有远端网络都可达，也不等于串流可用。**
- 协调记录读取、写入上限为每文件 64 MiB、每 Registry 2048 个网络。读取时拒绝空/null、重复网络键、非法认证摘要及损坏的成员签名；不静默以空库覆盖损坏文件。
- 写入先写唯一临时文件并刷新，再替换目标。旧 v1 注册/Slot 写失败会回滚内存；Mesh 原子成员变更的既有回滚和重发幂等语义保留。存储上限返回 507，其他存储访问失败返回 503，不把本机路径或系统异常内容返回公网请求者。
- 已确认成员表持久保存；短期配对房间仍在内存中，重启后要重新生成配对码。客户端错误说明增加此原因，已确认成员身份不会因此删除。
- WebUI 新增外部诊断与证书提示。后台状态更新只替换诊断区域，不替换正在输入的设置字段，继续使用全局保存/恢复。

## 离线备份与恢复

Linux 统一 CLI：

```sh
# 先通过 config apply 或 WebUI 关闭本机协调角色；普通成员角色可以继续运行。
sudo streamlink coordinator status
sudo streamlink coordinator backup /安全目录/coordination.slcoord
sudo streamlink coordinator inspect /安全目录/coordination.slcoord

# 显式确认：旧备份可能回滚后续审批、移除、退出和解散记录。
sudo streamlink coordinator restore /安全目录/coordination.slcoord --confirm-rollback
```

`backup`/`restore` 可追加 `--data /原独立协调的数据目录`。备份/恢复命令无需后台运行；`status` 从后台读取当前角色状态。原独立协调启动器也接受同样的维护子命令：`StreamLink.Discovery coordinator backup|inspect|restore ...`，默认数据目录沿用 `STREAMLINK_DISCOVERY_DATA`。

维护和协调宿主使用同一 `coordinator.lock`，不能恢复或备份正在被本版协调使用的数据目录。**旧版程序可能没有此锁，迁移前仍必须停止旧写入者。**

备份只包含 `networks.json`、`mesh-networks.json` 和版本/长度/SHA-256 清单，不含设备私钥、TLS 私钥、本机设置、订阅令牌、短期配对房间及在线候选。读取先限制归档/解压大小，再校验清单、校验和及成员签名；不将 ZIP 路径直接解压到磁盘。备份不加密，应私下保存；校验和用于检测损坏，不代替对备份来源的信任。

恢复先完整校验输入，再保留当前记录到 `before-restore-*.slcoord`，最后替换两份 Registry。当前记录即使已经损坏，也保存其原始字节，允许有效备份修复；这种恢复前存档可能无法通过成员校验，仅供保留与排查，不应误认为可直接恢复的有效网络。

恢复期间留下 `restore-in-progress.json`。若进程中断，新宿主拒绝启动，避免混用两代权限记录；显式重做恢复可完成操作，并保留第一次恢复前的存档。不要通过删除标记来绕过检查。本轮尚未验证真实磁盘掉电和文件系统故障，不宣称具备这类灾难恢复验收。

## 从独立协调迁到统一设备

1. 停止旧协调服务，备份其真实数据目录；记录原 HTTPS 域名、代理目标和证书指纹策略。
2. 保持统一设备的协调角色关闭，用 CLI 校验并恢复到 `/var/lib/streamlink/coordination`。协调恢复不会复制或改写 `profile.json`，本机设置和成员私钥独立保留。
3. 配置新监听。通过 Tunnel 提供 HTTPS 时可监听 `http://127.0.0.1:47822`；直接 HTTPS 则设置 PEM 文件。不要把本机管理 WebUI 端口作为公网协调入口。
4. 启用新协调角色，将**原 HTTPS 地址**的代理转发到新监听，在 `PublicUrl` 填入该地址。保持对外地址和既有成员的证书校验策略兼容；备份不会自动更新所有成员保存的 URL/指纹。
5. 运行 `coordinator status` 核对本机及外部检查，并在另一设备确认配对/成员变更及原直连。失败时停用新写入者后再处理回退；不能并行使用两份未同步的 Registry。
