## 已实现的修正

| 边界 | 先前源码行为 | 当前实现 |
| --- | --- | --- |
| 旧入口资源回收 | `releasing` 失败被记录后清空；原 mapping 引用已丢弃，随后仍可发起新入口创建。 | 保留释放任务及 `retiringMapping`。只有成功完成才清除；失败只观察一次并阻止重新创建此入口，已有直连和其它候选仍可继续。退出时将真实 owner 交给现有隔离机制。 |
| 回收被取消 | 停止阶段按普通操作取消忽略了 `OperationCanceledException`，即使它来自释放任务。 | 释放任务取消也视为退出未证实；HTTP、测速和维护任务的普通取消仍与资源回收失败区分。 |
| 网卡创建后、Router 接管前 | 工厂返回后即清空 `opening`；描述/日志/Router 构造异常可能遗漏网卡，构造失败时的单独释放异常也可能没有进入隔离。 | 使用 `pendingAdapter` 显式保留启动所有权，Router 成功接管后才转移；任何中途异常都走统一清理和失败 owner 保留。 |
| Router 启动前校验 | 部分地址、socket 与成员初始化异常未清理已分配的本地 socket、取消源或会话密钥。 | 数据泵启动前的准备阶段统一回收 Router 自有资源；构造失败不擅自关闭调用方仍拥有的网卡。 |
| 无效成员公告 | 已认证公告内的 JSON 解码异常会跳到整批读取的错误处理，剩余设备和控制消息无法继续处理。 | 对空公告、认证/格式/JSON 解码错误按单成员拒绝，其它公告继续；空 Nodes 按无公告处理，成员目录仍必须完整验签和校验版本。 |
| 并发成员目录更新 | 本机添加/撤销与协调响应没有共用完整的版本检查/安装边界；启动前依靠 pendingDirectory 延后处理，旧快照存在覆盖新意图的窗口。 | 使用同一个 Runner 锁完成版本检查、Router 应用和目录替换；Router 创建也在该边界内。关闭开始后不再调用关闭中的 Router，但有效目录变更仍写入运行配置，供后续新的 Runner 使用。 |
| Runner 重用 | 同一个实例没有重复执行保护，可能重复创建网络资源。 | 同一 Runner 只允许一次 Run；服务现有每次恢复创建新 Runner 的路径保持。 |

UI 对入口回收失败采用固定提示：暂停入口重建、已有直连继续、保留诊断后处理后台。该提示不把“网关删除未确认但本地 owner 已释放”混同为本地资源未退出；只在释放任务本身异常/取消时触发，不改变原网关租期和删除范围。
