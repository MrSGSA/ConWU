# rc.3 控制通道与卡顿修复

此候选针对本目录《卡顿与断线日志调查》记录的 rc.2 故障。实际双机串流是否改善仍待更新两端后验证；不能把下面的故障注入和回环结果解释为历史 `-1` 的唯一根因已经查明。

第一次冻结 `86ce397a` 的完整核心检查在 LegacyControlTests 的持续负载用例失败，因此该二进制不交付使用。用户随后报告的反复打洞问题和这次失败一并修正，保留原候选与失败记录。后续候选必须关联新的提交，详见《反复打洞与资源耗尽》。

## 最终改动

- 默认未启用出口整形时，系统路由诊断移出控制发送许可路径。全进程只有一个诊断查询工作任务、最多 32 个待处理查询，每个传输最多 32 个源/目标记录；相同查询合并，过期代次和已退出对象的结果不再发布。查询阻塞不消耗保活包的 250 ms 有效期。
- 启用可选出口整形时，仍要求先取得当前代次、实际源/目标的路由证据。该模式的同步强制查询未改成无证据放行，本轮不宣称解决其慢查询风险。
- 原生控制管道记录失败阶段、Windows 错误码、序号与拒绝类别。默认 1000 ms I/O 等待、认证、预算、250 ms 控制包期限均未放宽。
- 原生客户端和监听端的定时器也检查控制通道失败；不再依赖下一次原始网络收包才能退出。故障注入实际发现并复现了旧行为：已记录 ReplyRead 超时，进程仍继续重试 SYN。
- Runner 将确认退出的传输立即通知 Router。只撤销该客户端端点或已归属该共享监听入口的路径；独立客户端和新路径保留。旧端点迟到的认证数据不能重新建立健康状态，新的路径仍需完成自己的挑战往返。
- 传输失败原因写入主日志；控制许可阶段耗时、拒绝分类和路由观察耗时加入资源状态。子进程 stdout/stderr 均读到 EOF 后才关闭日志文件，避免丢失退出前最后几行。

业务仍为 FakeTCP＋HTTP 前导＋MeshLink 数据报。没有修改普通业务排序/重传语义、反重放窗口、12 秒双向证明、Wintun/WinDivert、协调/STUN 配置和配对格式。

## 第一轮：正确性与安全复核

已分别核查许可、代次和生命周期边界：诊断队列满时只省略诊断，不复制或绕开发送预算；过期捕获代次仍拒绝。后台结果不能覆盖新代次或退出后的状态。强制路由查询失败仍拒绝许可，未将入站业务当成出站健康证明。

管道仍验证父/子进程身份、随机授权值、请求序号和回复结构。新日志仅输出固定阶段名、异常类型/错误码与计数，不输出授权值、会话密钥或包内容。原生超时、断管、错误序号均保持失效退出。

故障传播按实际本机端点归属处理，不通过“任一传输失败就断开所有成员”恢复。对应回归覆盖旧候选失败不影响新 Active、共享入口失败不影响独立客户端、已失效入口的迟到包不能恢复健康，以及原有客户端排队、撤销、重新验证与网卡保留。

## 第二轮：产品与质量复核

rc.3 / MSI 1.0.9 作为可安装的修复候选。升级保留配对和配置，使用现有 WebUI；修正随包说明中“协调域名不存在”的过时文字。此前 rc.2 冻结包保留，不覆盖其二进制、源码归档或失败证据。

本轮原始证据在 `artifacts/control-repair-20261031/`：

- `baseline-route-failure.json`：使用 rc.2 固定安装包内的 Core.dll，真实 Windows 管道加阻塞路由观察器，控制许可响应超时可复现。该受控实验说明旧同步路径存在问题，不证明实机历史故障都来自这一因素。
- `legacy-control.json`、`legacy-control-2.json`：原生故障注入早期失败，揭示无后续收包时未及时退出；保留失败记录。
- `legacy-control-3.json`：真实 MeshTransport、原生进程、Windows 管道和 Router，路由观察每次延迟 1300 ms；持续双向 60 秒，实际每方向约 5.09 Mbps，29832 包/方向全部收到，最大收包间隔约 36 ms。
- `legacy-control-4.json`、`legacy-control-5.json` 和后者的 `.pressure.json`：提高负载后出现缺包。实测约 38.97 Mbps/方向；本地路由/控制丢弃为 0，原生注入无失败，但中间测试转发器仅收到约 40.3 万个原始包，少于两端合计约 45.7 万次注入。其默认接收缓冲只有 64 KiB，位于产品外的额外回环转发环节。
- 测试转发器随后将缓冲设为 1 MiB，与产品本机桥接一致；没有因此扩大产品缓冲、降低投喂负载、放宽完整交付断言或抹去前述失败。复验及冻结后的最终状态见候选目录的验证结果。
- `legacy-control-6.json`：修正测试转发器后，实际每方向 39.21 Mbps 持续 60 秒，229760 包/方向全部收到，最大收包间隔约 39.7 ms；两端控制许可最长排队年龄 16 ms，控制拒绝、过期和管道故障均为 0。路线查询仍注入 1300 ms 延迟。此结果与前述失败分别保存。

持续负载用例经过真实控制管道，每个 IP 包携带序号并核验载荷，同时检查保活回复持续推进、无本地健康路径丢弃、两端原生进程存活。实际投喂速率与最大收包间隔写入证据，不用名义目标代替实测速率。

这些仍使用内存 IP 网卡和原始包回环承载，未覆盖物理 Wintun/WinDivert、WAN、Sunshine/Moonlight 帧质量或正式八机独立系统。Wintun 4319 历史问题也不因本次修复而声明解决。

## 冻结与交付门

候选源码固定后，构建 MSI、ZIP 和源码归档，运行必要核心与受影响回归，并将最终产物哈希及结果放在候选目录。若冻结后还改源码，相关验证必须关联新的提交。

E1：提供用于两端复测的修复候选；E2 的真实多机质量、E3 的长期实机及正式发布门继续未通过。安装/升级的实际执行、30–60 分钟真实串流和卡顿后的新诊断日志仍是后续验证内容。

本轮准备安装包，不自动更新两台日用实例或重新部署协调服务。实际复测步骤见 `docs/aq1/实机测试.txt`；出现问题先保留两端日志，再按 `docs/aq1/使用与回退.txt` 回退。
