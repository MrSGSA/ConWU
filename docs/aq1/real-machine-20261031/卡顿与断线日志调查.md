# 2026-10-31 实机卡顿与断线日志调查

本轮日志确认了两个故障现象：Thinkbook 的原生传输进程因本地控制通道故障退出；Akane 多次因往返保活超时而停止业务发送、在本地丢弃数据。两者分别与 Moonlight 的 `-1` 断线和多次短卡顿时间吻合。控制通道失败的底层原因、保活在哪一环节丢失尚未完全确定，不能把所有卡顿归因于同一个原因，也不能把 Moonlight 的丢包显示直接当成物理网络丢包率。

本轮完成日志调查与代码核对，未修复或替换运行程序。当前候选存在实机稳定性阻塞，不能作为已通过长时间串流验证的版本交付。

## 范围和证据

- 用户描述：本机运行 Moonlight，Akane 运行 Sunshine；多次卡死后恢复，恢复瞬间显示约 40–50% 丢包；一次报 `-1` 断开，具体时间未记录。
- 两端安装版本均为 `1.0.1-rc.2`，源码提交 `2ca559efc7d0ddf8156ac1d0885355eb0aa3c45e`。调查时仓库 HEAD 为 `b00c052`，后者仅补充交付文档。
- 原始日志、状态和只读观察保存在仓库内 `artifacts/user-trial-freeze-20261031-1806/`；该目录不纳入 Git，不上传原始运行日志。该目录的 `evidence-manifest.json` 保存证据快照的 SHA-256。
- Thinkbook：`streamlink-initial.log`、`native-logs/raw-*.log`、`moonlight-current.log`、`status-initial.json`。
- Akane：`akane-logs/streamlink.log`、`akane-logs/raw-0f65c3ba0b4e4243af22bb4e04c3b16b.log`、`akane-logs/sunshine-current.log`。必须使用 `sunshine-current.log`；同目录 `sunshine.log` 是历史归档的同名副本，不能替代本轮日志。
- `correlation.json` 和 `analyze-logs.py` 保存时间关联和解析方式；`route-query-timing.json` 保存系统路由查询耗时。
- 以下时间均为 2026-10-31、UTC+8。Moonlight 相对时间以进程启动时间 `16:26:17.334160` 对齐，原日志分辨率为一秒；跨机日志未做专门时钟偏差测量，因此关联按秒级解释。

## 1. `-1` 断线前发生本地控制通道故障

| 时间 | 证据 |
| --- | --- |
| 17:04:27 | Thinkbook 原生日志 `raw-1ebecb25ef5b4505afd05a5a184df5cc.log:4351`：`[FATAL]legacy control owner lost` |
| 17:04:32.865 | Sunshine 当前日志第 832–833 行：`CLIENT DISCONNECTED`，`reason=control_disconnect` |
| 约 17:04:36 | Moonlight 第 2322 行：`00:38:19 ... Connection terminated: -1` |
| 17:04:37–43 | 两端记录往返/接收超时，随后新路径通过双向验证 |
| 17:04:44 | Thinkbook 新进程 `raw-1992381c275c441a85523735217a5712.log:39` 再次报相同 fatal |
| 17:05:01–02 | 再次建立路径后，两端健康状态恢复 |

第一次退出的最终原生统计为 `pipeFailures=1`、`CaptureQueueDrops=0`、`SendFailures=0`，退出前后的统计仍显示有入站包进展。第二次退出也有 `pipeFailures=1`。启动阶段 16:28:09 还有一次相同 fatal，但不将其与本次 `-1` 混为一件事。

`native_legacy_control.cpp` 的 `fault()` 会将控制通道标为失败；`native_backend.cpp` 检查后主动退出进程。当前 fatal 文案不能区分父进程真正退出、命名管道读写失败、等待超时、元数据或回复校验失败。`exact()` 默认每次异步 I/O 等待为 1000 ms，但日志没有证明这次一定是等待超时。

因此可以确认这次断线有 StreamLink 本地控制通道失效和传输进程退出，不能仅用外网断线解释；尚不能确定触发 `fault()` 的具体分支。

## 2. 多次短卡顿与保活超时、业务停发对应

Akane 对 Thinkbook 的路径在仍有认证入站流量时，因最近一次往返证明超过 12 秒而进入 `ReturnPathTimedOut`。`MeshRouter.Transmit()` 此时拒绝业务发送，增加 `NoHealthyPath` 丢弃计数。1–3 秒后收到有效往返回复，路径恢复。

| Akane 超时 → 恢复 | 超时时最近入站年龄 | 两条状态采样间新增本地丢弃 | Moonlight 音频丢包时间（约） |
| --- | ---: | ---: | --- |
| 17:01:44 → 17:01:46 | 17 ms | 6,788 | 17:01:45 |
| 17:02:35 → 17:02:37 | 4 ms | 2,979 | 17:02:35 |
| 17:22:55 → 17:22:58 | 4 ms | 11,353 | 17:22:57 |
| 17:29:27 → 17:29:29 | 45 ms | 4,298 | 17:29:28 |
| 17:30:20 → 17:30:21 | 6 ms | 3,418 | 17:30:20 |
| 17:31:45 → 17:31:47 | 3 ms | 6,043 | 17:31:45 |
| 17:42:19 → 17:42:21 | 58 ms | 6,189 | 17:42:20 |

这些增量是失败和恢复两条日志之间的计数差，不是每次故障全过程的精确丢弃量。Akane 捕获末尾累计 `NoHealthyPath=59078`，`SendRejected`、`AuthenticationRejected`、`ReceivePolicyRejected`、`AdapterWriteRejected` 均为 0。Thinkbook 在 17:27:05–06 也记录过入站年龄 5 ms、往返年龄 12288 ms 的同类超时。

已证实的是“保活超时 → 软件停止业务发送并丢弃 → 串流缺包”。仍收到入站流量不等于双向路径健康，不能据此直接称为误判或取消往返验证。保活未及时返回的初始原因仍需区分本地控制发送、远端处理和物理网络丢失。

用户观察的 40–50% 峰值未完整写入本轮 Moonlight 日志；日志中另有约 18:04:35 的 `Loss 25.76%`。不能把该值替代用户报告的峰值，也不能用应用缺包率推断运营商物理丢包率。

## 3. 本机控制发送存在大量拒绝和过期

| 进程快照 | 入队数 | 队列拒绝 | 父进程拒绝 | 原生过期 | 管道故障 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Thinkbook 17:04:27 退出的进程 | 6,997 | 0 | 657 | 108 | 1 |
| Thinkbook 17:04:54 后运行的进程 | 11,311 | 0 | 1,640 | 230 | 0 |
| Akane 当前服务进程 | 19,663 | 0 | 5 | 0 | 0 |

各行统计窗口不同，不能按行直接计算两端相对丢包率。父进程拒绝合并了不同原因，控制统计也未按保活 nonce 分类；不能把 1640 次拒绝全部算成丢失的普通保活。

Thinkbook UI 状态同时记录普通保活 `Attempts=2626`、`LocalAccepted=2626`、`FreshReplies=2256`、`PendingEvicted=363`、`Pending=7`。这里的“本地接受”只证明 Router 的 socket 接受，不能证明控制包已由原生组件注入或被远端接收。

静态代码核对得到一条明确的待验证风险链：

1. `LegacyControlChannel.Run()` 串行处理原生请求，先同步执行 `LegacyRouteEvidence.Prepare()`，再向 governor 申请发送许可。
2. 路由结果缓存仅 1000 ms。即使未启用出口整形，诊断用的路由查询仍位于该发送许可路径上。
3. `EgressRouteSnapshot.Bound()` 调用系统选路并枚举网卡/IP 信息。本机 12 次只读观察耗时 69.9–194.7 ms，结果均 Ready。
4. 原生队列最多 8 包，入队后 250 ms 过期；governor 也按入队时刻执行 250 ms 期限。同步诊断会消耗同一个有效期，排队和调度延迟还会叠加。
5. 普通业务可绕过该控制队列，MeshLink Ping/Pong 被分类为 maintenance 并经过控制许可，因此可能出现业务仍有进展、保活却无法及时完成的情况。

这证明同步路由诊断的成本显著；本轮观察未复现超过 250 ms 或 1 秒的查询，也未把某次查询与历史 fatal 或保活 nonce 对上。因此它是优先修复和验证的方向，尚不是已证实的唯一根因。

另一个诊断缺口：`MeshTransport.ControlFailure` 已保存部分托管异常，但正式 Runner 未把它记录到退出/恢复日志；原生 `fault()` 也缺少细分原因。现有健康日志主要在 12 秒证明超时后体现故障，需要补齐传输退出与 Router 路径失效之间的关联。不能仅凭这段时间线声称恢复代码完全没有检查子进程退出。

## 4. 其他范围和限制

- 本机官方 Wintun 已打开，快照 `RingFull=0`、`Truncated=0`，未见 Adapter 写入拒绝。本轮没有 Wintun 缓冲溢出的证据，不代表排除了所有驱动问题。
- Thinkbook Router 最大维护延迟 119 ms、最大锁等待 16 ms、最大维护工作 46 ms，没有本轮秒级维护饥饿的计数证据。
- 两端原生快照未见捕获队列丢弃或注入 API 失败；网卡错误计数也未显示错误。这些计数不能排除 WAN/QoS 丢包。
- 当前状态报告 `ExplicitEntry`、`FakeTCP+HTTP`；本机系统选路证据指向 Ethernet。协调服务不是该业务流的转发节点，现有证据没有指向协调服务中断。
- Akane 系统日志另有 16:38:27 的 Tcpip 4227、17:45:43 的 Tcpip 4231 事件。18:25 快照共有 415 条 TCP 项，没有持续端口耗尽证据，也未归属到 StreamLink；保留为待关联线索，不据此修改系统 TCP 参数。
- 上轮 600 秒 RawLoopback 通过使用包内 Core DLL、内存网卡和原生测试回环，实际投喂约 13 Mbps/方向；没有覆盖本次真实 MeshTransport 控制管道、Wintun/WinDivert 与 WAN 完整路径，不能用它否定实机失败。

## 后续修复与验证边界

优先补齐控制管道失败原因、请求排队/路由查询/许可耗时、拒绝分类和传输退出关联，再将非强制诊断查询移出限时控制发送路径。启用出口整形时所需的路由约束、父子进程身份验证、控制发送预算、FakeTCP＋HTTP 语义和 12 秒双向证明应继续保持。

受影响回归需覆盖真实控制管道、慢路由查询、管道失败、持续双向业务下的保活和多成员公平；修复后再冻结新候选做完整产品路径验证。当前仅凭日志不足以宣布上述修复已完成，也不能用延长健康期限掩盖保活交付问题。

本次没有改产品源码、重启服务、更换安装包、修改两端网络/协调/STUN 配置或运行压力及故障注入。两端原始快照、解析结果和哈希已保留，便于后续修复前后对比。
