# 反复打洞、辅助连接寿命与资源耗尽

本轮运行中的 Thinkbook / Akane 都仍是 `1.0.1-rc.2+2ca559e`。未安装修复版、未重启日用后台，也未更改协调服务、STUN 配置、网关或现有远程管理路径。以下修复继续并入未发布的 rc.3，不能据此宣称实机串流已经恢复。

## 证据与归因

本机日志在 16:29–16:46 期间出现 8 次 Windows DNS 取消错误 `WSALookupServiceEnd`，随后一直出现“打洞资源已满”。管理员只读统计显示 `OpenResources=8 / Created=33 / Queries=27`，读取当时的系统连接却已无该服务的 STUN TCP socket；仅采集线程栈又看到 8 个辅助观察任务仍在接收。诊断未导出进程堆、配对私钥或完整 Profile。

源码中 `TcpBinding.Connect` 已经选出成功的固定端口连接，却在 finally 中等待备用筛选清理。Windows 取消 DNS 可返回 `SocketException(10111)`，原代码只吞掉 `OperationCanceledException`，于是 finally 的错误覆盖成功返回值；调用方拿不到连接，观察器及资源配额也无人释放。实际回环 STUN 加可控 Windows 取消错误在旧路径上复现了同样的异常。修复后连续 10 轮能够保持成功连接并归还全部配额；意外清理异常与调用方取消也必须释放尚未移交的赢家。

Akane 的 `212.18.0.14:3478` 辅助连接约每 62 秒重建。两机各做一次独立、临时源端口的普通 TCP STUN 检查，每 10 秒发送合法查询，无 UPnP 操作或业务承载；Thinkbook 在 62.86 秒、Akane 在 63.64 秒收到连接重置。说明该现象在独立于 StreamLink 映射续租的连接上也出现，支持反射端点或其网络路径限制连接寿命的判断；没有抓包证明 RST 具体来自哪台设备。不能把它解释为产品设置了“一分钟主动拆洞”。

业务日志中另有 `ReceiveTimedOut` 与 `ReturnPathTimedOut`，其中既有同一路径短暂恢复，也有新的路径被选中。WebUI 的连接计时随状态恢复而重置，不能单独证明物理映射更换。业务卡顿仍需结合新控制管道诊断和实际串流复测。

原始证据在 `artifacts/user-trial-reconnect-20261031/`：两端主日志、脱敏服务状态、`thinkbook-service-stacks.txt`、两份 `*-stun-lifetime.jsonl`、`tcp-selection-before.log` 与 `tcp-selection-after.log`。独立 STUN 探测失败是调查结果，不是新版产品回归失败。

## 实现

- 备用筛选的预期取消错误不再覆盖成功返回；如果清理仍意外失败或调用方已经取消，关闭未移交的赢家。TCP 总配额仍为 8，没有增加容量掩盖泄漏。
- 已有健康路径且其余在线成员均已连接时，暂停可选的本机入口探索。离线成员不触发重复探索；新成员上线、健康路径失效、显式重试或网络变化仍能恢复探索。不会因为抑制探测而关闭已有传输或网卡。
- 健康 STUN 连接继续同 socket 保活，没有固定轮换周期。失败服务在该映射内冷却 5 分钟，优先选择其他已配置服务；只有一个或全部都失败时仍保留退避重试，不自动注入新的公共服务器。
- 网关租约续期与 STUN 辅助恢复分开。UPnP 的外层观察未知时撤回可发布候选，继续维护已有租约和监听入口；辅助连接甚至整个服务器选择失败，都不能自行删除该规则。PCP/NAT-PMP 的真实外部候选仍只由其网关租约决定。源地址确已消失时仍退出旧映射，交由 Runner 发现新源地址。
- STUN 日志区分远端关闭、连接重置和查询超时。保持 10 秒正常查询、60 秒 UPnP 续期与 180 秒租期；60 秒连接机会窗仅是未连接尝试预算。12 秒双向业务健康证明未放宽。

## 压力失败的补充修复

`86ce397a` 完整核心运行的 `LegacyControlTests` 在双向约 31.55 Mbps、60 秒中，一向缺 1319 个完整 IP 包。发送 Router 无本地拒绝，缺包已出现在对应原生发送计数之前；另一向完整，原生接收队列、注入失败和控制拒绝均为零。该轮中间 Proxy 已使用 1 MiB 缓冲，因此没有继续扩大缓存或放宽完整交付断言。

Windows 原生回环 UDP 读回调原来每次 select 只读一个包，反向原始包回调却能读 64 个。现在两端回环回调也最多处理 64 个已就绪数据报，之后交还事件循环，保持计时器和其他成员有执行机会；未增加队列、业务重传或排序等待。定向复验 `native-batch-control.pressure.json`：60 秒、实际 42.057 Mbps/方向，246464 包/方向全部收到，最大收包间隔分别 29.1/26.5 ms。仍然是内存网卡和回环原始包承载，不能替代物理 Wintun/WAN 质量。

## 第一轮：正确性与安全检查

检查了资源移交与 finally、调用方取消、单次绑定、固定端口筛选结果复核、现有八资源上限。新增失败冷却只作用于当前配置中的服务器；不改认证、成员撤销、HTTP 数据格式、反重放域或控制预算。UPnP 观察失效时不发布过时外部候选，也不把辅助重连当业务已恢复；明确停止仍只删除本对象拥有的规则。源码检查额外发现“源地址消失后可能永久重试旧 IP”的风险，已加重新发现分支。

原生批处理是非阻塞、有上限的读取；保留原解析、拒绝与发送路径，无未授权注入或无界循环。新增日志只保留固定原因和已有资源身份，没有报文内容、授权值或配对秘密。

## 第二轮：产品与质量检查

界面继续使用纯 WebUI；修复不要求用户手改 STUN 或重新配对。出现辅助连接故障时日志明确指向辅助观察，重复无效入口探索有暂停反馈；用户主动重试仍有效，多成员新上线仍可探索。测试跨过真实 60 秒租约续期验证同一辅助连接保留，并验证全部 STUN 不可用时规则仍在、明确停止才删除。

定向回归与最终冻结后的完整核心、最终包 DLL、MSI 载荷比对分别记录。`86ce397a` 失败证据不覆盖，新候选目录中的最终验证结果才决定是否可交本人复测。MSI 仍为 1.0.9，从已安装的 rc.2 / MSI 1.0.8 更新；旧 rc.3 从未安装或发布，旧候选目录标记被替代。

本次目标仍是可安装的修复复测候选。真实连续串流、Windows 设备创建 4319、正式八机及长期质量没有因为这些隔离检查而自动通过；尚不具备 E3 正式发布结论。
