日期：2026-11-07，执行更新：2026-11-08。状态：已按用户“开始构建”指令实施，正在进行回归、包验证及三端更新准备。实际实现、与初始建议的差异及验证状态见[实施记录](双机多网络实施记录-20261108.md)。尚未发布 GitHub。

目标是让用户以尽量少的配置建立稳定的双向串流通道。一个网络只包含一台网络主机和一台从机；一台设备可以同时创建、加入多个这样的网络。概览汇总全部网络，协调能力和 DDNS 配置尽量共用，网络权限、地址和运行状态保持独立。

用户准备切换到 sol 与 terra 共同执行。本计划覆盖推进顺序、接口决策、分工、待修缺陷、验收与交付条件；实际代码和测试状态以执行记录为准。

## 必须先固定的产品和接口约定

### 一个网络只有两台设备

- 网络主机是创建和批准这一对关系的设备；从机是获准连接的另一台设备。Moonlight/Sunshine 的角色和串流方向不受此划分限制。
- 同一台设备可以在网络甲作为主机，在网络乙作为从机，也可以同时连接多个对端。
- 一个邀请只交付给一个获准对端。第三台设备请求加入已占用的双机网络时不能替换原从机或扩成三人网络；引导建立另一条独立关系。
- 公共可达入口可以承接多个申请，每次批准创建或绑定明确的双机网络，不能由裸地址猜测要加入哪个网络。主机与邀请身份必须经过认证。
- 网络名是显示名称；稳定的 `NetworkId` 是授权、操作和存储边界。设备名、IP、端口和域名均不能代替身份。
- 同一对设备重复加入要先识别已有关系；重试、应答丢失和重启不能生成重复网络/对端。重新加入和身份更换仍需正确审批，不能恢复已撤销授权。
- 没有网络间转发，不开放从机之间的隐式访问，不开启系统级默认 IP 转发。

### 共用设备设置和独立网络配置

初始建议使用 `device.json`、`networks/<NetworkId>.json`。实际沿用受保护根 `profile.dpapi`／Linux `profile.json`，每网在 `networks/<本机配置ID>/` 单独保存配置和索引；本机配置 ID 与两端共享的网络 ID 明确区分。

| 配置层 | 内容 | 变更范围 |
| --- | --- | --- |
| 设备共用配置 | 设备身份/名称、自启、服务、本机接收端口、协调模式及监听、协调连接配置、DDNS 根域名/提供商和凭据引用、创建网络默认值 | 明确列出受影响网络；不能因页面切换自动改动 |
| 单网络配置 | 网络 ID/名称、主机和对端身份、角色、入口来源与发布归属、连接协议、已有入口/自主策略、虚拟地址、协调与 DDNS 共用配置引用及必要覆盖 | 只影响这一网络；允许复用设备默认配置，无需逐网重新填写 |
| 运行状态 | 实际路径、解析结果及有效期、连接阶段、统计、待处理操作、重试时间 | 不反写用户保存的设置；重启按明确恢复规则处理 |

- 敏感凭据不在每个网络明文复制，网络只保存安全引用；Windows 使用既有 DPAPI/ACL，Linux 使用私有文件权限。
- 默认值用于新建关系。修改默认值不暗中改写已保存的单网络覆盖项；修改共享配置则提前展示引用它的网络及影响。
- 全局保存收集实际全部草稿，明确哪些设备/网络设置会改变。切换网络和设置分区保留草稿，撤销/恢复默认的作用范围明确。
- 每个网络的保存采用原子替换；设备索引、网络配置和待审批记录跨文件变化要有可恢复事务，避免断电或写盘失败留下半个网络。
- 新版不能把旧配置校验失败当成空配置覆盖。此次重装可以重新配置；其他旧配置至少识别版本并提示不兼容。

### 协调共用但不自动成为成员

- 开启协调模式的 ConWU 设备为多个双机网络提供发现、申请转交和候选交换；用户通常只填一次共享 HTTPS 协调地址。
- 每个网络绑定自己的身份、权限与记录空间。协调服务不占每个网络的虚拟 IP，不自动获准进入，也不转发串流业务。
- 协调设备如需参与串流，按普通设备单独创建或加入双机网络；协调运行与参与网络的启停互不错误联动。
- 允许网络引用另一份协调配置，但改 URL 不能自动迁移网络权威或接纳别的服务返回的同名网络。切换需核验网络身份及记录连续性。
- 不把多台设备启用协调解释成多副本已经同步；本轮不实现分布式协调一致性。
- 本机管理 WebUI 保持本机授权边界。启用协调不自动公开管理接口或配置密钥。

### DDNS 共用域名并区分更新记录

- 一个根域名、一套提供商凭据可以服务多个网络。记录使用稳定 `NetworkId + DeviceId` 区分；网络名用于界面展示，不能直接作为唯一更新键。
- 优先延续当前 `e-设备ID.n-网络ID.根域名` 第三方候选记录与 `d-设备ID.n-网络ID.根域名` 签名发现记录的独立命名。有必要调整格式时在接口约定中版本化，不随页面文案变化。
- 不把所有设备更新合成一条共享 TXT 再各自整段覆盖，避免并发丢失别的网络地址。子记录由软件管理，用户无需申请多个域名。
- 多网络使用同一物理入口时，内部复用同一入口来源及刷新结果，再映射到获准网络，避免重复 STUN、订阅查询和 API 写入。真正不同的端口/来源分别维护。
- 已有入口模式可以消费 Lucky 等更新的候选和手动/HTTPS/TXT 来源；候选记录没有授权能力。第三方不能覆盖 ConWU 的签名记录。
- 发布/查询缓存、过期、版本和迟到回包按网络及设备隔离；退出一个网络只停止其记录维护，不删除其他网络、第三方或共享域名记录。
- 地址变化更新候选，不因 DDNS 刷新主动拆除仍健康的连接。界面区分“解析成功”“发布确认成功”和“实际直连”。
- 六位配对码目前仍依赖 HTTPS 协调。DDNS 提供地址不等于短码定位协议已经实现；无协调短码单独留在后续任务中。

### 虚拟地址和共享资源

- 本版采用每个双机网络独立的 IPv4 /24，沿用现有地址认证和撤销逻辑。创建侧自动候选避开本机已知冲突；加入侧和固定地址冲突会拒绝并提示，不静默修改其他网络。双方自动重新编号协商尚未实现。
- 一台设备参与多个网络可以有多个本机虚拟 IP；概览不能继续假设只有一个本机虚拟 IP。每个对端显示对应可连接地址，本机地址在网络详情中列出。
- 初始建议优先共享适配器；本版为保证生命周期与故障隔离，每网独立官方适配器，兼容网络共用物理接收器和接收端口，各自保留独立源端口。退出一条只回收其所有资源，最后一条退出才释放共享接收器。共享适配器留作后续优化。
- 同端口复用必须能够按认证后的网络与会话分流；不同协议或冲突的自主/第三方端口所有权不得强行共用。不兼容的配置在保存前报错并引导设置独立接收端口。
- 不偷偷改变用户已对外公布的端口来掩盖占用错误；允许自主分配的端口要完成本机绑定、候选发布和对端确认。
- 物理连接复用是后续可优化项，不能为节省一条通道混用网络密钥和撤销状态。先保证正确隔离、无重复工作线程和有界预算。

### 统一概览

- 默认显示全部网络汇总，不以“当前选中的网络”决定后台运行哪些网络。
- 顶部显示已连接/连接中/离线的网络和去重设备数量，以及全部实际业务的上下行速度、累计流量。
- 设备卡显示设备名、主机/从机关系、所属网络、对端虚拟 IP、实际连接协议/入口、延迟、上下行速度与流量、直连持续时间（天时分秒）。
- 同设备重复出现时按已认证身份归并展示关系，不按同名或相同公网 IP 合并身份。双向数据和多个统计层不能重复累计。
- 一条网络失联只标记这一条；后台健康、协调可用性、DDNS 可用性和业务直连分别判断。
- 配对码在加入页排第一；收到的申请独立为左侧“加入申请”，每条标明对应新关系/网络。已确认的加入方式只说明当前路径。

### P2 和 P3 的关键代码边界

- `DeviceProfile`/`ProfileStore`：设备配置、网络集合和独立文件；安全存储、并发写入和恢复。
- `ControlWorker`/`ControlWorker.NetworkUi`/`ControlWorker.Membership`：操作必须明确网络 ID；取消、超时和结束操作按网络生效，不能再复用一个全局 `End()` 清掉其他网络。
- `MeshRunner` 与原生接收/适配器所有权：多个受限上下文，共享资源但独立授权；状态回调绑定网络 ID 和运行代次。
- `UiControlProtocol`：设备汇总、网络列表、单网络详细状态和异步操作；不让 UI 当前选择成为服务端隐含目标。
- `CoordinationHost`/Registry：同服务多双机网络，单次申请/审批幂等，协调角色不占成员。
- `MeshDdnsSession`/`MeshThirdPartyDdns`：网络命名空间、共用来源去重、过期和发布确认；只停止目标网络的维护。
- `StreamLink.Host/Program.cs`：多网络 CLI 支持列表、状态、明确目标的加入/退出/删除；只存在一个网络时可以提供无歧义兼容快捷方式，多个时不得猜测目标。

两轮检查分开保存：正确性/安全；产品/质量/安装。修复后只重跑受影响项；共享协议、路由或资源生命周期变化需要扩大回归。冻结候选后再跑必要完整核心验证。

大码率验证先记录物理带宽、MTU、两端 CPU、实际出口和原版本基线，再确定可支持的码率档。建议覆盖 50/100/150 Mbps 中物理链路可承受的档位，并在目标高码率下持续至少 60 分钟，记录实际吞吐、延迟分位、丢包、卡顿和恢复。超过物理能力的压力结果与产品缺陷分开，不能事后降低目标掩盖失败。实际 Moonlight 与合成流量结果分别列出；缺少人工应用测试时准确标注。

真实设备不足时，多实例/namespace 可以验证授权、调度、隔离和资源释放，但不能冒充八台物理设备、校园网 NAT 或真实应用表现。新抗 QoS 方案继续先独立实机实验，不混入这次架构改造。
