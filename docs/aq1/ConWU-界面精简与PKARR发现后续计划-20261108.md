## 界面决定

1. 概况第一行：左侧显示本机设备名及各网络的虚拟 IP，右侧显示上传／下载实时折线图及对应累计流量。第二行是统一设备表，本机置顶，右侧合并区域标明“本机”；其余设备显示所属网络、主从关系、虚拟 IP、连接状态、延迟与流量。不保留“管理”跳转列。协议、已直连时长和实际入口保留在连接状态中。卡片、表格边距、边框与间隔采用统一尺寸。
2. 创建网络：标题后直接显示网络名称与简洁的创建表单，去掉嵌入的配置编辑器及主页面配置选择。名称下方放明显的“网络设置”入口，打开独立模态浮窗。协议、已有入口／自主打洞、协调、虚拟 IP、端口、STUN 与证书放入浮窗。设备名不出现在网络设置中。第二版决定：收窄创建表单放左侧，“本机创建的网络”与其并列放右侧；“接下来怎么连接”放到两者下方，默认折叠。已创建网络提供设置与删除入口，点击网络名称可查看其配对信息；不能因概况去掉“管理”而失去管理路径。
3. 加入网络：保留配对码／直连邀请及申请状态，不显示“本次使用的配置”、本机名编辑或虚拟 IP 输入。通过审批后，自动接收并应用主机可共享的网络参数。显示等待、取消、收到授权、应用设置与连接完成的连续反馈。首次查找主机缺少线索时才展开补填地址，不要求填写整套网络配置。第二版决定：加入表单放左侧，“本机加入的网络”并列放右侧，显示查看设置与删除网络；“当前连接方式”“怎么加入”移到两者下方。主机提供的设置通过只读浮窗展示，不能在从机编辑；虚拟 IP 显示本机实际获配地址。删除加入的网络只退出并删除本机记录，确认框必须说明不会删除主机的网络。
4. 导航与加入申请：退出网络紧接在“加入网络”之后；“加入申请”仍为独立页面，位于退出入口之后、协调服务器之前。申请页显示数量、所属网络、申请设备、预分配 IP 与校验码。同意在左为绿色，拒绝在右为红色，视觉强调一致。重新加入时更新原设备的身份关系，不生成重复设备行。
5. 协调服务器：独立放在“加入申请”之下。管理默认的协调发现地址及“本机提供协调”的独立角色。两种角色可以同时开启，保留独立开关，不改为互斥选项；本机监听处理其他设备的配对请求，与本机访问远端协调服务相互独立。改变默认发现地址不静默改变现有网络身份或健康连接。网络仍可保留自身必要的协调信息。保存与恢复按钮移至页面标题右侧，保存前后状态必须准确；修改地址后不能继续展示对旧地址的成功检查结果。
6. 设置：只保留“启动与服务”“本机设备名”“日志设置”。本机名称供所有网络统一使用。保存、恢复刚才设置和恢复默认设置移至页面标题右侧，并准确反映草稿是否变化。
7. 延续 ConWU 现有倾斜 45° 图标及 Tokyo Night 配色，不增加新的产品等级或开发标识。图表、导航、模态浮窗适配宽屏和窄屏；没有实时刷新替换表单内容、重置输入或关闭展开区域的行为。

## 后续实现必须处理的边界

### 加入后继承哪些内容

主机授予的是经过认证的网络身份和可共享连接参数，而不是把主机完整配置文件复制给从机。协议、网络策略、目标主机入口和必要发现信息可以随授权下发；入口归属必须从“主机的本机入口”转换为“从机的目标主机入口”。从机源端口、实际接收绑定、网卡资源与本机虚拟 IP按本机环境与网络分配处理。

本机设备名、开机启动、日志偏好、协调服务监听角色、管理密码、主机私钥、DNS 写入凭据及订阅写入令牌不得由这一流程覆盖或下发。需共享的只读入口凭据仍遵循已有审批和加密邀请约束。自动获取设置必须在验证主机身份及授权后执行，拒绝、取消、超时或无效授权不能留下半应用设置。

### 第一次申请的发现与协议

六位配对码本身不包含完整主机地址与协议。已有保存的协调服务或入口可以用于初次联系；直连邀请可以携带发现线索。没有任何线索时仍须用户提供一项目标入口或协调地址。审批后的自动继承不能反过来解释首次如何到达主机，也不能为了让 UI 看似一键而偷偷在业务侧回退到其他协议。

实现使用现有配对控制交换，审批后校验并应用协议对应的白名单设置。默认继续 FakeTCP＋HTTP；使用非默认协议首次直连时应使用携带明确协议的完整邀请，裸入口加短码不通过回退猜测协议。自动配置的实现与隔离验证事实以实施记录为准。

### 已有配置与多网络

此轮先调整界面，不为演示拆散现有共享配置引用。正式实施时保留兼容迁移：浮窗修改若影响多条网络，必须显示实际影响范围；只有用户明确选择独立设置时才解除共用。退出、删除、加入失败或恢复 UI 草稿不应改写本机设置或其他网络配置。过往关于配置共用的要求没有因去掉页面上的配置选择器而自动取消。

全局设备卡要展示多网络虚拟地址，不能让一个网络的 IP 代表整台设备。设备表按设备和网络关系组织，角色在每条关系内成立；同机可在网络甲为主机，在网络乙为从机。不同网络之间继续不转发业务。

## DHT／PKARR：后续独立发现验证

目标是自动重新找到地址变化后的目标主机，减少用户自建协调服务及 DNS 配置。PKARR 基于 Mainline DHT／BEP44，以持久公钥定位可更新的签名记录；每台发布设备独立保管发布密钥，与 ConWU 网络身份建立可验证绑定，不让所有设备共享一把发布私钥。

候选流程：首次可信邀请交付发现公钥与网络身份；主机解析已有入口，发布少量候选地址及端口；从机查到候选后仍完成 ConWU 身份认证和授权检查。已配对设备在主机重启后用同一公钥重新查询。删除／重建网络仍使用新的网络身份，旧发现地址不能让旧授权自动获得新网络权限。

先用于已有可达入口的发布／查找。自主打洞的候选交换、同步时序和映射维护单独评估，不能仅因查到地址就宣称完成穿透。原生 DHT 使用 UDP，校园网需验证其可用性；PKARR HTTP 网关只处理发布／查找元数据，不承载串流。使用公共 DHT 或网关仍依赖外部基础设施，不称为完全没有第三方。

重点验证：校园网直达 DHT 及通过 HTTPS 网关的可用性、首次启动耗时、变更 IP／端口后的传播与重新发现、缓存和签名旧记录、时钟回退与持久序列号、多主机身份区分、全离线后的重新发布、网关限流／故障，以及公告隐私和密钥丢失。公告容量约 1 KB，不能承载完整配置或高频同步；网络秘密不以明文发布。签名不等于加密，过期与防回滚需要应用层策略。

用户随后已授权加入本轮候选，默认关闭；先完成隔离网关和协议验证，公网传播与实际串流不冒充已经验收。现有协调、已有入口、直连邀请和串流路径保持可用，不把额外研究全部变成交付前置条件。

参考：[PKARR 官方介绍](https://pubky.github.io/pkarr/)、[HTTP 网关协议](https://pubky.github.io/pkarr/design/relays.html)、[集成与重新发布](https://pubky.github.io/pkarr/docs/integration.html)、[BEP44](https://www.bittorrent.org/beps/bep_0044.html)。
