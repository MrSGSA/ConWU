# ConWU：PKARR 与协调角色收敛

## 本轮决定

候选 `1.1.0-preview.5`，Windows MSI 版本 `1.1.4`。延续当前真实 HEAD 的双机多网络与审批后自动获取配置，不恢复历史研究任务。

协调服务器页保留“使用协调服务器”和“本机提供协调服务”两栏，两种角色可同时开启。提供侧移除重复的外部 HTTPS 输入，监听、证书和反向代理设置保留。旧外部地址不被清空。

下方增加说明：“未使用其他协调服务器时，默认协调服务器为自身。”实际联动以能确定 HTTPS 访问地址为前提：沿用保存的本机外部地址或明确的 HTTPS 监听 IP；已有其他协调地址不被覆盖。不从 `0.0.0.0`、回环或反代的本机 HTTP 监听猜测公网入口。无法推断时，界面说明须在使用侧填写反代的 HTTPS 地址；仅开启提供服务不会虚假启用短码发现。

从机没有使用协调服务器时，只显示直连邀请。使用协调服务器时可输入短码，也可粘贴邀请。服务器必须实际存在、可被双方访问，目标主机须向同一协调服务登记短码；提供角色本身不是目标发现信息。

网络设置按策略显示：

| 策略 | 所显示的发现栏目 | 首次申请 |
| --- | --- | --- |
| 只使用已有入口 | 已有入口 | 完整直连邀请 |
| 自主打洞＋协调 | 协调服务器、STUN、证书 | 协调短码 |
| 自主打洞＋直连邀请 | 直连邀请、STUN | 完整直连邀请 |
| 自主打洞＋PKARR | PKARR、STUN；PKARR 固定启用 | 完整直连邀请，携带发现公钥 |

默认固定 FakeTCP＋HTTP，不回退 UDP；已有入口不同时自主打洞。协调与 PKARR 不承载串流，也不自动把协调设备加入网络。

## 配置及权限

新增可选 `UiNetworkSettings.DiscoveryMode`，空值代表旧配置，保持兼容。新保存的策略明确为 `existing/coordinator/direct/pkarr`；后台验证互斥关系，不仅依靠前端隐藏字段。已有入口新策略关闭旧备用协调与 PKARR。更新本身保留旧配置原有行为。

暂不使用的协调、入口、STUN 输入保存在偏好中，不作为当前运行参数。网络配置保存、直接设置 API、退出后的设置恢复使用一致的规则；隐藏的未完成输入不会阻止另一种有效策略保存。

审批白名单增加发现方式。主机发布能力与从机查询能力分开：从机获得发现公钥和网络身份，不获得发布 seed，不发布主机公告。自动获取设置仍为只读，本机监听资源、设备名、启动、日志、管理设置不被覆盖。新 PKARR 网络应更新两端。

## PKARR 实际改进

1. 自主主机发布已准备的真实候选，不使用隐藏的第三方入口。映射对象发生地址变化后同步更新待分享入口，后台更新同一个发现公钥。
2. 修复自主从机收到发现线索后未进入入口解析的问题。首次邀请、审批、已批准身份与后续查询串联，重启保留发布 seed、序列号和从机发现线索。
3. 解析结果携带签名到期时间；订阅间隔过长时 PKARR 最长一分钟查询一次。失败不继续以旧缓存启动新连接，独立认证的健康通道不受查询失败影响。
4. 每个网关的时间预算覆盖响应体读取，避免 `ResponseHeadersRead` 后无限等待。拒绝相同序列号的不同签名内容，保持验签、协议、时效与当前进程内的最高序列检查。

当前范围是签名地址发现。没有经 PKARR 实现双方候选交换与同步打洞，也不提供原生 UDP DHT 客户端；公开网关可用不代表严格 NAT 必然可通。接收端最高序列号尚不跨进程保存，公告时效仍会验证。

## 两轮分离检查

### 正确性与安全

检查公开公告内容、密钥归属、签名及过期、并发网关冲突、响应体超时、审批边界、配置应用与恢复的一致性。发现并修复：自主模式忽略已批准入口、映射变化未同步到分享入口、过期公告缺少运行时期限、响应体没有独立超时、隐藏设置被当作运行参数、直接设置 API 未采用新策略规则等问题。

定向回归包含 `--pkarr-only`（29 项）、`--pkarr-publisher`（19 项）、`--pkarr-pairing`、`--autonomous-invitation`、`--existing-invitation`，及自动配置、协调配对、兼容备用入口、配置库、设置保留、后台配对优先级与邀请审批等 13 组。隔离配对使用真实本地 MeshLink 与注入的物理传输、映射和 PKARR 网关，不冒充真实 NAT 结论。

收尾追查纯自主直连邀请发现：解析邀请后未保留签名入口，从机批准后可能只剩身份而缺少首次建连地址。已把本次核验过的邀请入口纳入审批成功后的持久线索；无效、取消或未批准申请不持久化。新增纯邀请完整配对／重启测试，同时收紧 PKARR 测试中的模拟映射：变更后的旧物理地址实际不通，必须查到并使用新地址才能通过重连检查。发现此项后的首个预打包候选已废弃，最终源码重新冻结。

第一轮冻结核心保留于 `frozen-core-9fd86543/`，66 项中有两项失败，未改写为通过。其中兼容审批测试发现，已经签名绑定主机的邀请入口被标记成通用网络入口，覆盖了同地址的主机归属。现仅对裸入口使用通用标记，签名邀请继续保留其主机槽位；原有兼容断言保持不变，退出、重进和重连定向回归已通过。另补已有入口完整邀请／自动配置／重启测试，确认两端都不启动自主打洞。

公开试验 `--pkarr-public` 使用临时随机密钥及文档保留地址，没有读取或发布在用设备的入口、私钥或配置。2026-11-09 的两个默认 HTTPS 网关均接受首发与更新，同一公钥下取得并验签了更新的地址；原始结果为 `artifacts/pkarr-modes-20261109/public-gateways.json`。此项不放入离线核心门禁。

### 产品与质量

真实 WebPanel／隔离服务浏览器检查 26 项；正式资源配合确定性慢 API 检查增加至 35 项。检查模式栏目、PKARR 无关闭开关、无协调时仅邀请、默认自身与不猜测 HTTP 公网地址、已有外部服务保留、草稿、恢复、只读、保存锁、后台取消、窄屏与脚本错误。截图在同目录的 `real-browser-final/`、`ui-states-pin-preservation-final/`，冻结核心运行也会重新保存同类证据。

默认自身的证书处理统一按所选服务身份匹配：保存提供服务的选项，仍保留当前所选服务的既有证书指纹；首次选用本机服务则使用本机已知指纹，不沿用已移除服务器留下的孤立指纹。另修正协调表单的刷新签名，后台只改变提供服务字段而不改变服务地址时，未编辑的表单同步刷新，未保存草稿仍独立保留。新增三项回归均通过。这一收尾界面修改后的源码需再次冻结；进行中的旧提交验证不作为最终冻结通过记录。

中间验证 `frozen-core-fbf0cccb/` 保留一次重启恢复单包未送达的失败；同一二进制独立复查通过。其发送前条件只检查主机显示直连，没有等待从机确认。组网、协调、兼容入口及重启恢复夹具现统一等待两端就绪，各自原有的等待时限保持不变，不增加业务包重发，不放宽单包送达门槛。重启恢复定向连续三次通过，其余关联用例和真实 C++ FakeTCP 回环多网络用例通过。中间运行还遇到界面收尾修改后的提交变化，完整保留其 `SourceDirtyAfter=true` 结果，不改写为冻结通过；最终结果以新冻结提交的独立证据为准。

修正窄屏测试的过时条件：精简后栏目能放下时不必强制出现滚动条，仍要求标签不挤压、浮窗不溢出。

第一轮核心的另一项失败是托盘合成 Enter 检查；相同二进制单独复查通过。测试原先调用 `PreProcessMessage`，会把合成消息与真实桌面当前的修饰键合并。测试现调用实际 WinForms 对话按键处理，提供明确的按键上下文，不释放或注入用户的系统按键。保留原有绘制、无障碍、命中区域、上下键与 Enter 的全部 14 项断言，定向连续三次通过；没有据此改动产品托盘逻辑，也不将此检查描述为普通账户的完整交互验收。

## 冻结与交付

两轮检查和受影响定向回归之后冻结源码，执行一次 `CandidateCore` 核心回归，再提供独立的新 Windows／Linux 候选包。最终源码提交、完整核心结果、包哈希及未覆盖范围记录于包外交付记录；不覆盖 preview.4 的证据，不以单轮核心声称三十轮长期验收或正式发布全部通过。

不运行 Moonlight 或真实高码率串流压力。本轮构建包不自动替换当前三台在用实例，实际串流结论继续由用户确认。
