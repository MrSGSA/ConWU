# ConWU：PKARR 与协调角色收敛

## 2026-11-10 后续计划：统一直连码与默认提供协调能力（未实施）

用户确认先计入计划。本节记录下一轮目标，不代表界面、监听默认值或三端程序已经修改；下文的开发记录及各 preview 决定保留为历史依据。本节的新目标取代其中关于保留六位短码入口、独立协调服务器页面和本机提供服务默认关闭的产品决定。

### 已确认的产品方向

1. 首次加入统一使用 16 位字母数字直连码，按 `XXXX-XXXX-XXXX-XXXX` 显示。保持 80 bit 长度及版本、协议、IPv4、端口、临时会话编号与输入校验这些字段，不再研究缩短；新增协议时通过格式版本明确区分旧码含义。首次联系、核对双方校验码、主机审批及授权后的配置交付均在两端完成。
2. 取消创建、加入页面中的六位短配对码方式，以及为短码首次查找而设置的协调服务器／已有入口填写框、切换按钮和说明。删除短码流程不能删除已批准成员的身份、既有网络或保存的订阅；旧短码接口与进行中会话的退役兼容需在实施时明确。
3. 默认网络设置为“自主打洞＋PKARR”。首次直连码配对后自动取得并保存双方发现身份，后续由自主打洞模块产生、维护候选入口，PKARR 负责发布和查询更新。打洞成功率与同步打洞调度属于自主打洞模块，不能用 NAT 不一定可通来认定 PKARR 发现功能未完成。
4. “已有入口”只保留用户提供的地址／订阅。主机批准后，从机继承必要的入口来源、订阅与身份信息，后续直接刷新原订阅。此模式移除仅用于短码的协调设置，不启用 PKARR，不启动自主打洞或隐藏回退。
5. 自建协调服务作为自主打洞的高级可选后端，产品职责收敛为自行掌控的地址发现与更新服务。主机选择后，从机通过已批准配置自动取得所需地址及信任信息，不再要求从机额外填写服务器。PKARR 与自建发现后端按所选策略运行，不因本机提供服务而自动切换后端。
6. 删除左侧导航中的“协调服务器”入口及整个独立页面，包括原提供服务开关。安装并运行 ConWU 后，设备默认具有、提供协调能力；是否能从外部访问取决于实际网络。提供角色不等于使用角色，不自动把本机选为网络的协调服务器，也不使设备加入其他网络或承载串流中继。
7. 本机协调监听参数归入设置的端口／高级区域，保留必要的监听状态与错误反馈。内网设备使用可达的内网地址，具备公网可达条件的设备可通过 IP＋端口或自行配置的域名访问；不要求软件保证公网可达，也不额外要求注册域名。监听端口的默认值、绑定范围和协议在实施时结合现有端口占用与安装策略确定。
8. 网络创建、审批、退出、删除与配置保存不再被发现服务的在线状态绑定。发现服务临时不可达只影响取得新入口，不能关闭健康直连、锁死本机网络管理或清空设置。配对仍须实际到达对端，并完成身份核验与主机批准。

### 2026-11-10 协议精简补充：普通 TCP 替代外层直接 UDP（计划，未实施）

用户指出软件的主要目标是抵抗 UDP QoS，建议将“直接 UDP”换成普通 TCP。按这一定位收敛用户可选的外层传输；本次仅记入计划，不修改正式程序或在用配置。

- 目标选项为“FakeTCP＋HTTP（默认）”和“普通 TCP”。继续由用户明确选择，失败时提示原因，不自动切换协议，不恢复 UDP 回退。普通 TCP 是补充路径，其是否适合正式提供，以实际高码率串流结果决定，不能仅因名字含 TCP 就视为已经解决 QoS。
- 退役的是公网业务通道的“直接 UDP”选项。Moonlight 的内层 UDP 数据、本机必要的数据报接口及发现／打洞所需协议分别保留、按职责评估；不能把整个代码库的 UDP 支持一并删除。TCP 外层需要准确封装与还原原有报文边界，继续使用现有设备认证与数据加密。
- 当前正式传输策略仅支持 `faketcp`／`udp`，现有 TCP STUN、端口租约和 FakeTCP 的 TCP 形态不等于普通可靠 TCP 业务通道。需新增实际 TCP 传输实现，处理连接生命周期、消息分帧、读写取消、有限队列和背压，再接入路径验证、统计与恢复；不能把 `udp-only` 改名成 TCP。
- 普通 TCP 的可靠、有序重传可能使后续报文等待丢失报文，产生串流延迟尖峰或冻结。先建立独立测试链路，与现有 FakeTCP＋HTTP 比较高码率、轻度丢包、抖动及 UDP 限速环境中的实际表现，不提前宣称其优于现有默认传输。
- 16 位直连码当前版本的协议位表示 FakeTCP／UDP，不能把旧码的 UDP 位静默解释成 TCP。为新协议设计清晰的版本兼容规则，并同步审查配对、批准配置、入口标签、PKARR 公告、CLI、状态显示及持久配置中的协议校验。旧 UDP 网络的迁移或重新配对需要明确提示，不能在升级时单方面改变协议使两端失配。
- 核对 Windows／Linux 普通 TCP 的监听与防火墙行为，隔离现有 FakeTCP 的 WinDivert／nftables 拦截、TCP STUN／租约资源和多个网络的端口归属。普通 TCP 的监听、断线和退出不得影响正在使用 FakeTCP 的其他网络。
- 验收以用户的实际高码率需求为主，记录吞吐、端到端延迟与尾延迟、冻结及恢复时间、输入响应和资源占用，覆盖重连、地址更新和两种外层协议的多网络并行。先验证独立链路，再决定产品集成；实际 Moonlight 串流结论继续由用户确认。

### 2026-11-10 HTTPS 独立实验记录（用户要求本轮测试到此）

用户补充：普通 TCP 在网络波动较少、码率不顶满时已有良好体验，TCP 打洞及进一步软件优化放在后续，先尝试 HTTPS。之后明确暂缓正式版代码与 UI 改动，待补充细节；保持现有 UI 主体，仅按最终确认做必要精简。本轮只新增独立实验 `tests/ConWU.HttpsPoc`，没有向正式网络策略加入新协议，也未替换三端程序。

实验使用真实 TCP＋TLS 1.2／1.3＋HTTP/1.1 WebSocket Upgrade，不使用 HTTP/3、伪造 TLS 握手或第三方业务中继。两端复用生产 `MeshLink` 的认证加密报文格式，载荷为 1280 字节合成数据；实验访问令牌与证书指纹独立生成，不读取在用网络的身份、配置或密钥。原型尚未接入正式直连码审批、证书身份绑定、TUN 或 Moonlight。

实际协议检查覆盖证书指纹拒绝、错误访问令牌拒绝、64／1280 字节报文、WebSocket 分片、过大消息限制，以及 TLS 接入后仍必须通过内层认证。实际协商到 TLS 1.3。发送器初版在 Windows 上按固定 10 ms 周期计量，受约 15.6 ms 的调度影响导致负载不足；已改为按实际经过时间计量并限制突发积累，初版结果保留，不用请求码率冒充实际吞吐。

原始日志与结构化结果保存在 `artifacts/https-poc-20261110/`。已收回 12 份服务器证据，确认无存活实验进程，服务器临时目录及其中的独立凭据已删除，80／8443／44743 端口已释放；原有 xray 443 监听保留，未改防火墙或重启生产服务。本地构建目录、压缩包及临时令牌文件的清理先后被自动审批阻止，工具只返回 `blocked by policy`，因此保留这些本地文件；该令牌对应的临时服务已经销毁。后续正式版等待用户补充细节，再以已确认的去协调依赖方案推进；新的抗 QoS 传输继续在独立链路验证后评估集成。

### 实施顺序与需要处理的边界

1. 先检查旧协调模式对网络创建、目录存储、审批、退出和删除的实际依赖，区分“当前已有实现”和“新职责目标”。把网络授权和管理逻辑留在设备端，再收敛发现后端，不能只删除界面后留下后台强依赖。
2. 统一创建／加入的直连码流程，调整批准配置的白名单与继承规则，再移除短码相关的前端入口和旧注册／查询依赖。保持每个网络独立的身份、设置、虚拟 IP 和端口归属；同一物理入口承载多条网络时，临时会话必须准确对应目标网络。
3. 调整本机协调宿主的默认提供行为，迁移必要的监听、证书和反向代理设置，最后移除独立页面。保留已保存的监听地址、证书、反代及远程管理配置；明确退役开关的迁移规则并提供更新说明，不用默认值覆盖用户仍适用的配置。
4. 当前实现仅允许 HTTP 协调绑定回环地址，HTTPS 监听需要证书。因此“公网 IP＋端口即可访问”必须完成协议与认证／加密接入设计和验证，不能仅把监听改成 `0.0.0.0` 就宣称支持。默认提供协调能力不得同时公开本机 WebUI、管理凭据或未授权的远程管理接口；已有域名 HTTPS、反代／Tunnel 和服务器 `/admin/` 路径须保持兼容。
5. 默认提供服务采用监听驱动，不持续扫描远端、不把外部探测当成网络可用性的前置条件。端口占用、监听启动失败或其他设备无法访问时，独立显示状态并合理重试，不影响 PKARR、已有入口、数据接收器或本机网络操作。

### 验收范围

- 创建与加入界面仅展示 16 位直连码，无六位短码或首次查找地址弹窗；从机批准前不能获得网络授权或完整网络配置。
- 分别验证“自主＋PKARR”“自主＋自建发现服务”“已有入口＋订阅”三个流程，以及从机自动继承、重启、地址变化与多网络隔离。
- 验证发现后端不可达时的创建、直接审批、本机退出／删除、配置保存及健康通道保持，区分真实对端不可达与后台误报。
- 验证默认提供服务的空闲资源占用、端口冲突、监听失败恢复、LAN／公网 IP＋端口访问和域名 HTTPS 访问，管理接口仍按原授权规则工作。
- 验证升级、保存、恢复和退出不丢失设置；旧网络、旧短码退役与旧邀请兼容必须有明确结果，不能静默清空配置或改变主从关系。
- 两机真实 NAT、长时间公共网关可用性与实际高码率串流独立记录；实际串流结论继续由用户确认，不以本计划或隔离测试代替。

## 开发中：双向 PKARR 与稳定性补全

延续双机多网络及 16 位直连码。新建网络默认自主打洞＋PKARR，自建协调服务器保留为明确选择的高级方式，本机提供协调服务默认关闭。已有网络及配置库不自动更改发现策略；已有入口仍只使用原订阅，不启动另一套打洞或 PKARR。

主从两端使用独立的签名发现身份。批准后把公钥固定到网络、设备及成员签名身份，之后通过已认证的 MeshMetadata 协商双向支持；旧端继续按旧方式查询。配对双方使用现有 ECDH 密钥派生独立的 AES-GCM 状态密钥，绑定网络、发送者、公钥、协议、地址及到期时间。加密状态携带本次启动、入口版本、对端入口确认和设备名，不能用于入网授权或业务传输。入口确认绑定具体内容与启动，不把网关接受 PUT 当作对端或直连成功。

发布身份及递增序列号持久保存。接收端新增独立的受保护检查点，先落盘最高序列与包摘要再交付地址；配置事务不能回退检查点。查询设定整轮预算，收到有效响应后有限等待其他网关并取消、等待剩余请求结束；每三轮复核其他网关，避免旧缓存一直抢先返回。单网关故障、全网关中断、查询失败与恢复均单独报告，健康业务通道不被发现错误关闭。未建立通道时较快查询，已确认健康通道后降低频率；地址、启动和确认变化触发更新。

发现并补修的生命周期问题：首次身份写入的异常原先会使发布任务退出，随后停止服务也会传播该错误；现按有界退避恢复。地址变化后的持续失败原先会每轮重新触发更新，覆盖退避时间；现仅对内容变化调度一次，保留后续指数退避。设置回滚等待资源退出后重新合并最新运行观察。保存草稿不能覆盖最新发布 seed、序列或绑定；发布前后复核当前网络、策略和接收器，晚到结果不能重新启用已经关闭的发现状态。新网络不继承旧网络的对端绑定或协商版本。主机及从机只读设置均提供实时状态，手动刷新仅针对所选网络。

隔离验证已覆盖签名与加密绑定、防回退持久化、网关迟滞／中断、双向确认、两端同时重启与地址同时变化；旧物理地址实际丢弃，必须重新发现才能恢复单包双向交付。公开网关验证使用临时身份与文档保留地址，两个默认网关接受双方记录、返回更新后的地址并通过加密确认；记录在 `artifacts/pkarr-duplex-20261109/public-duplex.json`。这些结果不代表真实 NAT 或串流测试。首次身份写入和退避缺陷的失败复现原样保留于 `lifecycle-before.log` 和 `backoff-before.log`。

首次受影响矩阵保留两项失败及测试修改后的 `sourceChanged=true`。完整邀请夹具原先只等从机通道后就停止，并立即要求后台已发布；现等待双方通道及双方独立记录，再用主机的精确公钥检查更新，避免把从机记录拿去按主机公钥验签。双重启夹具原先要求两端各自发起到新地址的拨号；日志已有双方健康通道和新入口确认，未再发起冗余拨号是正确行为。现保持原时限，核验双方的新入口确认、至少一方使用新地址发起连接，以及原有双向完整 IP 包交付，旧地址仍实际丢弃。这两项复查记录为 `*-fixtures-final.log`，不把原失败矩阵改写为通过。后续产品退避修改完成后的最终受影响回归单独留存。本轮未自动替换三台在用程序，未发布新 release。

## preview.7：邀请方式与数据发现分离

已有入口设置新增可选配对协调地址及其独立证书指纹，只用于短配对码申请，不修改网络的 `Pair.Direct`、数据发现策略或运行时协调目标。公开批准配置允许下发这两项公开信息；成员密钥、本机服务和管理凭据仍不共享。配对偏好修改属于元数据，不重启健康的数据接收器。

配置了配对协调服务时，创建页可选择配对码或直连邀请；无服务时只生成邀请。协调自主网络也支持完整直连邀请，邀请的新版签名绑定原网络协调地址和证书身份，批准后仍保持原数据发现策略。无协调邀请保留原签名域及格式兼容。按需准备自主入口使用独立请求标记，不触发已有入口打洞，也不重置健康通道。明确选择的新无协调配置不再自动生成隐藏的数字配对房间，旧 API 行为保留兼容。

活动数字码保存实际登记的服务身份。修改未来配对偏好后，界面不显示或复制旧服务上的码；已有会话的批准配置继续绑定原服务，避免审批期间设置变更导致凭据不符。加入侧增加折叠的自签名证书指纹设置，支持旧地址缓存迁移，保留本次地址和信任，不改本机提供服务的信任或系统证书库。

| 策略 | 所显示的发现栏目 | 首次申请 |
| --- | --- | --- |

## 配置及权限

新增可选 `UiNetworkSettings.DiscoveryMode`，空值代表旧配置，保持兼容。新保存的策略明确为 `existing/coordinator/direct/pkarr`；后台验证互斥关系，不仅依靠前端隐藏字段。已有入口新策略关闭旧备用协调与 PKARR。更新本身保留旧配置原有行为。

暂不使用的协调、入口、STUN 输入保存在偏好中，不作为当前运行参数。网络配置保存、直接设置 API、退出后的设置恢复使用一致的规则；隐藏的未完成输入不会阻止另一种有效策略保存。

审批白名单增加发现方式。主机发布能力与从机查询能力分开：从机获得发现公钥和网络身份，不获得发布 seed，不发布主机公告。自动获取设置仍为只读，本机监听资源、设备名、启动、日志、管理设置不被覆盖。新 PKARR 网络应更新两端。

## PKARR 实际改进

1. 自主主机发布已准备的真实候选，不使用隐藏的第三方入口。映射对象发生地址变化后同步更新待分享入口，后台更新同一个发现公钥。
2. 修复自主从机收到发现线索后未进入入口解析的问题。首次邀请、审批、已批准身份与后续查询串联，重启保留发布 seed、序列号和从机发现线索。
3. 解析结果携带签名到期时间；订阅间隔过长时 PKARR 最长一分钟查询一次。失败不继续以旧缓存启动新连接，独立认证的健康通道不受查询失败影响。
4. 每个网关的时间预算覆盖响应体读取，避免 `ResponseHeadersRead` 后无限等待。拒绝相同序列号的不同签名内容，保持验签、协议、时效与当前进程内的最高序列检查。

当前范围是签名地址发现。没有经 PKARR 实现双方候选交换与同步打洞，也不提供原生 UDP DHT 客户端；公开网关可用不代表严格 NAT 必然可通。接收端最高序列号尚不跨进程保存，公告时效仍会验证。

## 两轮分离检查

### 正确性与安全

检查公开公告内容、密钥归属、签名及过期、并发网关冲突、响应体超时、审批边界、配置应用与恢复的一致性。发现并修复：自主模式忽略已批准入口、映射变化未同步到分享入口、过期公告缺少运行时期限、响应体没有独立超时、隐藏设置被当作运行参数、直接设置 API 未采用新策略规则等问题。
