# M6：原生退出检查的热路径开销

本次以 `b7defe1` 为基线。仅改变 `NativeAttachment.Exited` 的实现：业务收发读取退出事件维护的标志，避免每个数据报多次调用 `Process.HasExited`。启动时注册退出通知后的单次 OS 查询、销毁时的实际退出确认均保留。HTTP、SEQ、原生协议、队列容量与现用部署未改。

## 可重复的本机负载

新增 `EndpointPoc --broker-load <native> --mbps 50 --seconds 10 --rounds 3 --output <json>`。它在同一 Windows 上运行三组 MeshRouter、四个真实 C++ worker、认证管道和回环 UDP 桥；A-B、A-C 分别直连。原始 IP 由内存网络传递，IP 适配器也是有界内存实现，没有 WinDivert、Wintun、WAN 或运营商 QoS。

每个方向合计请求 50 Mbps，使用 1280B 内层 IP 包，记录实际提供速率、源队列/内存网络/捕获队列丢弃、接收唯一序号与延迟。两个发送端共同向 A 发包时仍是合计 50 Mbps。收尾限制为 500 ms，延迟来自同一个主机单调时钟；不能据此报告公网单向延迟。`Completed` 只表示完成采样与清理，不代表质量达标。

| 构建/方向 | 轮次 | 接收 Mbps | 丢失 | p95 延迟 |
|---|---:|---|---|---|
| A 基线，A→B/C | 3 | 29.14 / 34.53 / 24.00 | 41.63% / 30.85% / 51.92% | 271–287 ms |
| B 事件标志，A→B/C 与 B/C→A | 各 3 | 全部约 49.92 | 全部 0 | 2.76–2.93 ms |
| A 基线回跑，A→B/C | 1 | 34.38 | 31.13% | 206.79 ms |
| A 基线回跑，B/C→A | 1 | 49.98 | 0 | 101.26 ms |

基线的丢失可定位到测试源适配器积压；该受控测试没有复现真机捕获队列溢出。父进程在每十秒样本中的 CPU 时间从约 18–21 CPU 秒降到约 4–6 CPU 秒，但这包含三个逻辑节点及测量工具，不能当成单个产品实例的资源占用。

原始证据在 `artifacts/m6-broker-{baseline-load,event-exit-load,baseline-recheck}-20261011.json`，含 Core/native/harness 哈希。A、B 的 native 二进制一致。独立保存 A 构建后进行 A/B/A 回跑，减少暖机顺序造成的误判。

## 生命周期与正式接线回归

- `m6-broker-exit-notification-20261011.json`：真实 worker 强制退出 30 轮，630 检查通过；事件使路径失效的最慢时间 29.8619 ms。另一 peer 保持工作，独占源端点在最后引用释放后关闭。此为本地无持续负载用例，不是公网恢复时间。
- `m6-event-exit-runner-20261011.json`：正式 Runner TCP/UDP 各一轮、共 43 检查通过，含三组共享源实例、准入及过滤检查；内存 IP 适配器不代表真机网卡。
- `m6-event-exit-timeout-20261011.json`：原生取消、共同期限和失败分类 14 检查通过。
- 应用 Release 构建：零警告、零错误。

反向仍未达标。2735 次是明确的本地捕获队列丢弃；注入端总量与捕获端总量也不一致，剩余丢失需要分阶段观测，不能全部归因该队列或运营商。下一步需继续定位实际收包突发、管道消费与调度，再确定 pacing 和队列策略。

结果：`artifacts/m6-broker-wintun-{local,remote}-20261011.json`。清理与全包关键哈希：`m6-broker-cleanup-{local,remote}-20261011.json`。首次本地检查早于控制服务退出，仍观察到控制规则；`m6-broker-cleanup-local-final-20261011.json` 是控制服务退出后的终态，无本次规则、测试地址或进程残留。两端现用 StreamLink 服务保持 Running。

Core、Service、Harness 和 native 的四个哈希在两端完全一致。本次未更改 Lucky、路由器、VMware、物理网卡或现用 0.3.2。没有发布新安装包。

## 完成范围与回滚

这是 M6 的一项热路径修正和测量工具，尚未完成出口 pacing、公平调度、全部质量指标、真实多 peer、独立公网、八设备、长时间串流及发布 Gate。不能以一方向 50 Mbps 通过代替整体验收。

回滚只需使用上一开发构建；现用安装与网络配置未变。实验模式仍需显式开启，不因本次性能修正自动升级部署。

## 后续采样：把排队与管道耗时分开

在 `491ffdf` 基础上增加 `CaptureQueueDiagnostics`：成功入队/出队数、未完成出队记账的单会话峰值、最大排队时间、排队超过 20 ms 次数、成功管道写入数/最大耗时/超过 16 ms 次数。使用主机单调时钟和固定个数的累计数值，worker 退出后仍保留；不记录业务内容、不扩容队列、不修改调度策略。排队峰值包含已由唯一消费者取出但尚未完成记账的一包，因此不等同于 Channel 缓冲区容量。管道计时是异步写调用到完成回调的时间，包含本机调度，不能独立解释为 native 的读取耗时。

新增观测的本机负载 `m6-broker-observation-load-20261011.json`：两个方向各一轮，约 49.92 Mbps、零报告丢失，p95 约 2.85/3.06 ms。生命周期 `m6-queue-observation-lifecycle-20261011.json` 三轮 66 检查通过，包括计数关系和 worker 释放后观测保留。MeshHarness Release 构建通过，零警告、零错误。

再次双机采样的环境、负载口径与上一轮相同，使用新的身份和源端口。`m6-queue-wintun-{local,remote}-20261011.json`：

| 指标 | Thinkbook 接收 | Akane 接收 |
|---|---:|---:|
| 实际接收 Mbps | 38.2656 | 49.9704 |
| 报告丢失 | 23.4617% | 0 |
| 所有者捕获包数 | 80286 | 104373 |
| 捕获队列丢弃 | 0 | 0 |
| 最大排队时间 | 3.3717 ms | 1.0301 ms |
| 最长管道写入 | 3.7393 ms | 0.2559 ms |
| 入队/出队/成功管道写入 | 均为 80286 | 均为 104373 |

两端都通过完整内层回显并正常关闭资源。Akane 注入 104423 包，而 Thinkbook 捕获只有 80286 包；该累计差额包含维护包，不能当成严格的业务丢失计数，但结合两端相反方向的对应计数，可以把本轮大部分差额定位到接收所有者计数之前。范围仍包含发送主机后续处理、旧底层隧道和接收驱动，现有证据无法再分离这些原因。没有据此宣称为运营商 QoS。

此前的 2735 次捕获队列溢出是保留的真实失败证据；这轮没有复现，不能仅凭新增观测就宣称已修复。当前没有证据支持继续扩大管道队列，先保留现有有界行为。独立公网负载与正式包质量 Gate 仍未完成。

本次完整环境哈希、清理分别在 `m6-queue-wintun-*.environment.json`、`m6-queue-cleanup-{local,remote}-20261011.json`。两端 Core/Service/Harness/native 哈希一致；本轮测试进程、规则、虚拟地址均已清理，现用服务仍 Running。
