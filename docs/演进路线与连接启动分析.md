# 后续演进与连接启动分析

## 2026-11-05：下一阶段以无独立协调服务器的最简串流为主线

状态：用户已确认方向，本轮仅记录；尚未据此修改程序、部署服务或执行新一轮验证。当前已发布版本为 1.0.5。

产品目标继续围绕大码率、低延迟的抗 UDP QoS 串流。下一阶段优先摆脱固定的独立协调服务器，同时推进已有可达入口、自主打洞两条连接路径，简化配对与自动连接。用户随后明确：没有 Lucky 等工具、没有现成入口或其他工具不能提供适用入口时，自主打洞同样是本阶段重点，不能将其排除在主线之外。Linux 平台适配随后推进，作为与 Windows 同等地位的普通串流节点；设备是否承担入口或协调角色由配置决定。

### 两条连接路径

- **已有可达入口：** 使用公网地址、端口映射、已打通的地址或其更新/订阅链接，直接申请加入并建立连接。入口不限于 Lucky。
- **自主打洞：** 用户无需先借助第三方工具打通入口，由 StreamLink 负责映射发现、候选地址交换、打洞时序、路径验证与后续保活恢复。仍需诚实报告 NAT/防火墙条件限制，不保证任意网络都能打通。

两种路径由用户明确选择。已有入口模式不自动切换到自主打洞，自主打洞不能抢占已经验证的健康连接；不得重新引入两类方法争用端口、候选或通道的问题。自主模式内部的候选调度也要明确资源归属与释放时机。

自主打洞需要双方获知候选地址并协调尝试时序。STUN 负责发现映射，不会自动完成对端发现与候选交换。无固定协调服务器的方向，是探索借助已有在线成员、可选引导节点或等价交换机制完成这些工作；具体发现机制仍待设计。双方都没有已知可达入口、也没有任何可联系的辅助节点或交换渠道时，不能声称能够凭空首次联系。引导节点交换连接信息与转发串流业务是两种职责；若某阶段仍依赖中心辅助节点，必须如实说明，不能仅改名后宣称已经完全免服务器。

### 最简使用流程

1. 选择连接路径：有现成入口时，游戏主机填写一次入口；没有时，使用 StreamLink 自主打洞，由软件发现和交换候选，不要求用户先提供打洞成功的地址。已有入口路线继续支持多地址及动态订阅。
2. 生成一份邀请，另一台设备粘贴并发起申请，由主机确认加入。邀请带入必要的网络身份、协议信息及所选路径需要的信息，避免重复填写；自主打洞所需的候选交换与时序由软件处理，具体引导机制待设计。
3. 自动分配虚拟 IP，供 Moonlight 使用；已有自定义设置按其原功能保留。
4. 获批后的设备身份与配对结果长期保存在本机。后续启动按所选路径恢复：已有入口路线自动解析并连接，自主打洞路线复核映射并在必要时重新打洞；不因最初邀请过期而要求重新配对。健康通道持续保活，不因固定轮次到期反复重打。

默认继续使用 FakeTCP＋HTTP，协议由用户明确选择，不自动回退 UDP。邀请中的协议与本机设置不一致时，应给出清楚的处理提示，不静默修改设置。邀请与成员发现属于运行信息，不得覆盖用户保存的设置。

### 最小改造范围与已有基础

- 优先复用现有无服务器配对、审批、加密直连和成员信息同步，收敛配置及错误反馈流程。
- 已有入口模式只连接已有入口，不启动 STUN、自动映射或自主打洞作为隐式回退。
- 自主模式重点改善映射发现、候选交换、双端时序、端口所有权、握手验证、资源回收与失败反馈；不把“提供了某个开关”视为已经能够自主打洞。
- 自主打洞必须验证用户所选的实际承载。普通 TCP 或 UDP 探测成功、STUN 获得公网地址，都不能直接当作 FakeTCP＋HTTP 已可用；继续验证原生握手、双向认证、完整数据包及业务质量。
- 获批成员之间直接交换必要的成员信息和签名入口公告，保持可用连接；业务不自动经其他设备或服务器中继。
- 入口地址更新服务与协调服务分开看待：用户可以继续使用 HTTPS 地址订阅；无服务器目标不要求取消这一可选地址来源。
- 已有入口路线首次联系需要可达入口；自主路线需要可用的发现/候选交换渠道，但不要求预先已打通业务入口。两者分别说明其实际外部依赖和失败原因。
- 成员管理权限先沿用现有规则。多管理员、任意授权成员审批及更复杂的分布式权限管理留待后续设计，不阻塞这一阶段。

本轮只读核对到的现有基础包括：`DirectPairInvitation` 携带签名的入口与申请信息；`JoinUiInvitation` 直接连接入口并等待批准；`DirectMeshDiscovery` 经认证直连交换成员表和入口公告。当前邀请签发仍由创建者执行。这些基础主要对应已有入口的无服务器路线，不能据此声称自主打洞已经摆脱协调依赖，也不等于新流程或公网场景已经验收。

### 下一轮验收重点

1. **已有入口路线在协调服务不可访问时仍能首次配对。** 从首次申请到批准、获得虚拟 IP、实际串流，均不需要独立协调服务；用户配置的可选 HTTPS 入口订阅可以正常使用。
2. **重启后自动恢复。** 覆盖单端及双端重启，保留已批准身份、虚拟 IP 和设置，自动重新解析与连接，无需重复邀请。
3. **创建者离线不拖断其余设备。** 三节点中，已授权且具备相互直连条件的 B、C 在创建者 A 离线后继续通信；单纯离线与主动删除网络、签名撤销授权分别处理。
4. **入口与恢复行为可靠。** 覆盖订阅变化、多个入口、临时解析失败、对端离线和重新上线；保留健康路径，避免持续密集重连、误报和设置丢失。
5. **以实际串流质量交付。** 核对真实 Moonlight/Sunshine 串流的目标及实际码率、延迟、丢包、冻结与恢复情况。Ping、回环或测试数量不能替代大码率实机效果。
6. **无第三方打洞工具时验证自主路线。** 不预填第三方打通的业务端点，由 StreamLink 实际完成映射发现、候选交换、双端尝试和所选承载的双向认证，记录实际 NAT 条件、辅助节点依赖、成功耗时与失败原因。协助建立连接的节点离线后，已有健康直连仍应维持；尚未消除的首次发现依赖要如实列出。
7. **模式互不争抢。** 验证已有入口模式不创建自主候选、自主候选不会抢掉健康路径，失败与取消后释放资源；拒绝未验证的入口与协议混用，不自动跨模式或跨协议回退。

验证先使用隔离实例，不为测试切断现用网络或停掉现用协调、STUN、HTTPS 地址更新服务；旧通道的迁移和退役另行处理。

### 后续范围

Linux 后续补齐普通节点所需的 TUN、路由、权限及后台服务，复用共同协议和组网核心，CLI 可以作为初期操作入口。先考虑一个基准发行版与 x64 通用运行包，再按需要扩展发行版安装包、ARM64 或 musl 构建。新抗 QoS 传输仍先做独立实机链路实验，不混入本阶段。

## 连接速度：已确认的等待与尚未定位的阶段

当前链路依次涉及启动服务、TCP STUN、路由器映射、HTTPS 元数据交换与入口协商、本地传输进程/虚拟网卡启动、udp2raw/EasyTier 握手及界面状态刷新。打洞成功、虚拟 IP 就绪、数据通道确认是不同时间点。

已确认：

- 原 `NetworkRunner` 每轮固定等待 5 秒，先发布公告，再读取对端并选入口；选定结果要等下一轮才会发布。
- 原协商循环直接等待 `StreamSession.Start`。本机初始化期间不继续发布和读取公告，创建端的慢初始化可能让另一端也晚启动。
- 本机已有日志中，18:44:35 到 18:45:10、18:48:07 到 18:48:37 分别为“协商入口”到“组件已启动”的约 35 秒和 30 秒。旧日志无法分辨这些时间是在防火墙、进程、虚拟网卡还是其他系统调用中消耗。
- TCP STUN 失败项按顺序尝试，每项 4 秒；已经优先使用上次成功的 STUN。不能把“增加更多服务器”直接等同于更快。
- 旧 UPnP SSDP 搜索等待 3.5 秒后才处理描述地址。失败后本机入口探测退避 45 秒；最外层连接异常退避 10 秒。
- 旧程序把 `dev_name` 放在 TOML 根层，而固定 EasyTier 2.6.4 的 `VirtualNicCtx::new` 读取 `get_flags().dev_name`；该设置实际被忽略，EasyTier 每次生成随机接口名。新版已移至 `[flags]` 并按网络/槽位固定名称。固定名称不等于持久复用网卡。
- 界面约 2.5 秒刷新一次状态，后台约 2 秒查询一次 EasyTier。界面出现“已直连”的时刻可能晚于实际数据通道可用。

只读检查：本机当时有 85 个接口，.NET 枚举接口约 98 ms、读取地址约 28 ms；单独执行 EasyTier core/cli 的 `--version` 约 248/95 ms。这些检查不创建虚拟网卡，不能证明实际网络初始化只需同样时间，也不足以解释上面的 30–35 秒。

### 本分支已完成

- 创建端选定入口后立即发布决定，再启动本地组件。
- 本地组件在独立任务中启动，协商循环继续交换公告。取消时等待初始化任务结束后再释放会话，避免释放仍在使用的对象。
- 未连接时轮询间隔 2.5 秒，已连接时保持 5 秒。两端每轮各 PUT+GET，常规连接中流量至多约 96 次/分钟，给部署中每网络 120 次/分钟的上限保留事件公告余量。没有把轮询直接降为 1 秒以致触发限流。
- 恢复超时从最近一次健康连接观察开始计算，避免长时间正常连接后一次临时失联就因旧启动时间触发立即重建。
- 在 STUN、路由器发现、租约、防火墙、进程启动、虚拟 IP、质量检测端口及实际握手处记录单阶段和累计耗时；计时使用单调时钟，日志中不加入密钥或配置内容。
- 抽出发现与会话接口，测试可模拟慢初始化，无需真实驱动和网卡。这只是后端边界的起点，并非已经移除 EasyTier。
- UPnP 响应边接收边处理，首个服务可用即试租约；慢请求期间继续缓存其他候选。取消/提前返回会结束接收，保留端口所有权保护与失败回退；拒绝异源描述/控制地址和 HTTP 重定向。
- 修正网卡名称位置，并显式设置空的 `stun_servers` / `stun_servers_v6`，停止 EasyTier 不需要的独立 STUN 探测。真实固定版本的 `--check-config` 验证两种配置；传输进程继续绑定本地回环端点。
- 界面连接期间每 750 ms 查询本地状态，连接后恢复 2.5 秒。这不是额外的公网协调请求，也不改变真实握手用时。

目前只证明减少固定等待、修正串行调度，以及本环境短测未退化；总体改善有限。没有宣称秒连、网卡持久复用、冷启动改善或统计性 P95 提升。

## 去掉 EasyTier：可行路径与包体积

直接调用官方签名 Wintun，在用户态接收和写入 IP 数据包，可以独立管理虚拟网卡和路由，不要求用户另装 EasyTier。Wintun 提供网卡读写 API；成员管理、认证、路由、MTU、心跳及连接恢复仍由应用实现。[Wintun 官方说明](https://www.wintun.net/)

建议先保持 udp2raw 数据传输，提供可切换后端：

```text
虚拟网卡 Wintun
    ↕ IP 数据包
StreamLink 设备身份、地址绑定、路由、封装与会话管理
    ↕ 本地数据报
udp2raw FakeTCP + HTTP 特征
    ↕ P2P
另一台设备
```

复用官方签名网卡驱动，自主实现用户态组网逻辑。自行开发内核驱动还会引入签名、兼容、系统崩溃和维护成本，对当前目标没有明确收益。

移除 EasyTier 相关内容可释放约 18.62 MiB 压缩体积，但还要加入替代后端；这不是最终包体积承诺。桌面与运行时仍需单独优化。没有为了变小而删除当前分发所需的许可证或源码。

最小替代后端先只支持双端 IPv4，保持虚拟地址、UDP 数据报边界及直连约束，使用成熟密码库实现每链路认证/加密，不自行发明密码算法。验收至少包括：源 IP 与设备身份绑定、拒绝伪造源地址、MTU/分片边界、乱序/丢包、断线恢复、退出清理、长期 50 Mbps 和 UDP/TCP 应用兼容。多播/广播发现应单独设计，不能当作三层 TUN 天然具备的功能。

## 多机组网

当前两台限制分布在 `DeviceProfile.Slot`、`NodeAnnouncement`、服务端 Registration.One/Two、入口选举、IP/对端名称计算、质量检测授权以及 GUI；把两个槽位放宽为更多数字不足以完成多机支持。

建议将“创建网络”解释为成员管理权限，网络成员具有独立长期身份和固定虚拟 IP。管理员签发短时邀请，逐台批准加入，支持撤销单设备。成员目录/成员凭据与每对设备的数据连接分离，连接表按设备对维护；每条链路独立选择可达入口、重连和显示状态。

默认仍不转发业务数据。若 A 与 B、A 与 C 都可直连，但 B 与 C 不具备可用 NAT 条件，应明确显示 B–C 不能直连，不能偷偷经 A 或 VPS 转发。创建网络的设备离线也不应自动断开其他已经建立的直连。

先以 3 台设备验收固定 IP、独立直连、入口变化、单节点离线不拖垮其余连接，再扩展规模。全连接 N 台有 N(N−1)/2 条设备对关系；连接可按需建立，不能让后台维护成本无界增长。节点凭据、撤销和密钥轮换要在推广多用户之前完成。

## 界面动效

保留清晰的“操作进行中/完成/失败”反馈，逐步加入约 100–180 ms 的按钮悬停/按下、导航指示和状态转换。动画只重绘相关小区域，窗口隐藏或驻留托盘时停止，遵从系统减少动画设置；不要重新引入每帧缩放整张背景的路径。

若需要持续的页面滑动、柔和过渡和复杂动效，可评估 WPF 或 Windows Composition；先做独立原型比较高 DPI 下的输入响应、滚动、CPU/GPU、内存和包体积。Windows Composition 可集成到现有 Win32/WinForms 窗口，但集成本身仍有开发成本。[微软 Visual layer 文档](https://learn.microsoft.com/en-us/windows/apps/develop/composition/visual-layer)

动效的验收应基于实际屏幕与输入响应，不把离屏 DrawToBitmap 测试直接解释为屏幕帧率。
