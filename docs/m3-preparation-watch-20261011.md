# M3：准备/启动分离与协调长轮询

本次实现是 M3 的一部分。SO 共同提名、正式新承载接线、全机控制包调度仍未完成；不表示 M3 Gate 通过。

## 原生 Ready/Start

`NativeAttachment.Launch(..., startImmediately: false)` 等到捕获/接收器 Armed 后返回。双方完成 Ready 后调用 `Start`。默认参数保留旧实验调用方式。

- Prepared 可接收 IPC 心跳，不发送 SYN。原生准备阶段最多 30 秒，不靠心跳无限延长。
- IPC 交换串行化；同一 attachment 的重复 Start 幂等。
- SO 的 8 秒仍从 native 收到 Start 计时，不把准备等待算入这 8 秒。MeshLink 认证/提名接线仍须使用剩余期限。
- Prepared 也可以撤销；确认进程退出后释放 native Lease 引用。
- 修复已 Dispose 的 `Process` 再查询退出状态触发异常的问题。

验证：`artifacts/prepared-so-20261011b.json`，30 轮、363 项检查。真实 C#/C++ 子进程和原生协议，回环测试收发后端；不使用 WinDivert，不代表 LAN/WAN。第一轮包含跨越心跳周期的 Prepared 等待和撤销，所有轮次包含双方 Ready 前零原始报文、重复 Start、旧 HTTP/bare 序号行为和实际业务回包。

首次运行在检查撤销后的退出状态时失败，记录于 `artifacts/prepared-so-20261011.json`；不是报文或 NAT 失败。

## 每设备一条协调长轮询

新增 `POST /v3/mesh/{network}/watch`。API 路径仍 v3，数据 meshProtocol 仍 4，watch 协议独立为 1；旧公告签名格式不变。

- 请求除网络 bearer 外，必须有成员签名，绑定成员、BootId、RequestId、服务端 epoch、游标及最长 45 秒有效期。
- 每设备一个等待者；全服务最多 64 个。重复请求、冒用成员、撤销后的请求被拒绝。
- 每网络最多 128 条变更索引，包含 directory/announcement。响应提供一次有界批次和最新完整快照；游标落后或服务重启时 reset。
- 服务端最多等待 25 秒，变更合并 100ms。客户端为该接口单独设置 35 秒，普通 GET/PUT 仍为 8 秒。
- 本机客户端拒绝第二个并发等待。正式 MeshRunner 使用此接口，最密 2.5 秒发起一次，HTTP 等待不阻塞原生恢复或公告 PUT。
- 只有明确的路由 404/405 才记忆回退到旧 GET；新版未注册网络返回 412，认证、预算、数据错误不会触发降级。
- 发布和长轮询共用每成员 48 次/分钟补充速率、8 次突发预算；已注册目录更新计入创建者账户。网络级 512 次/分钟仍由服务中间件限制。
- 取消和成员撤销唤醒并释放等待者。快照/公告仍由原有成员证书和签名校验，服务响应游标不替代认证。

当前 announcement 保活也产生索引，因为服务端不能解密判断端点是否变化。忽略自身发布的通知；成员间保活可能唤醒等待。高变化时客户端间隔和请求预算提供上限；尚未增加独立的候选/Attempt 控制事件。

## 本轮证据

- `artifacts/mesh-watch-20261011c.json`：23 项检查；八身份批量变更、成员签名/重放/撤销、64 等待者与短请求共存、取消回收、每设备突发上限、真实回环 HTTPS 的 25 秒等待和旧服务回退。
- `artifacts/mesh-connection-watch-20261011.txt`：44 项 TCP/正式 MeshRunner 连接检查。新增确认 Runner 实际选择长轮询接口；HTTP 阻塞期间子进程恢复和数据传输保持原有行为。
- `artifacts/mesh-regression-watch-20261011.txt`：40 项原有 MeshLink/签名/多成员/禁止转发回归。
- native/Core/Service/Discovery 构建通过，无编译警告。

HTTPS 测试最初因测试用 Windows 自签名私钥加载方式失败；改为内存 PFX 导出/重新加载，没有安装信任证书。随后一次全部协议检查通过但相对产物路径不正确，已改为明确绝对输出并完成整轮复测。这些失败不作为公网服务结果。

以上使用一台 Windows 上的隔离身份、回环 socket 和测试 HTTPS 服务。不是八台真机验收；没有升级现用服务、改公网协调域名配置或安装驱动。
