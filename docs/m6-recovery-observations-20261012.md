# M6：恢复的首包、稳定区间与确认时刻

基线 `200cee3`。本次为正式 `MeshRouter → MeshRunner` 增加恢复观测，覆盖兼容显式入口与受管 FakeTCP/UDP 路径，保留默认 PreferFakeTcp 和约 12 秒健康窗口。没有改变 HTTP、SEQ、加密或数据报语义，也没有把这项诊断当作 AutoQuality 选路依据。

## 计量口径

每成员维护一个本地恢复 episode：

- `FirstBusinessMs`：本机 IP 适配器实际接受的、来自所选路径的首个认证内层包。仅发送排队成功、握手、ping、未认证包或退役路径来包均不能产生这个值。
- `StableBusinessStartMs`：后来通过验证的业务观测区间起点；在确认前保持空值。
- `StableBusinessConfirmedMs`：至少连续 3 秒的本地业务进展、10 次同路径 nonce 往返，且无尚未解决的探测请求后记录。三个值用同一本机单调时钟，不能与另一台电脑的时间直接相减。
- 初次 episode 从 Router 注册该成员时开始，**不是用户点击启动或远端故障实际发生的时间**。稳定后观测到健康丢失、发送失败或路径改变会开始新 episode；检测延迟仍需另计。
- `PathId` 指当前所选路径；`FirstBusinessPathId` 单独保留首包来自的路径。未稳定时切换到新路径，不会把旧路径的 nonce 计入新路径证明。

需要持续业务才能得到 StableBusiness。确认前出现超过 1 秒没有收到业务、一个探测超过 1 秒没有匹配响应、发送拒绝或健康丢失，就重启稳定区间；首次成功时间仍保留，以暴露先通后断的情况。业务空闲只说明缺少连续证据，不直接宣告传输故障。高 RTT 或应用本来间歇发送时，可能无法取得这个面向低延迟负载的稳定观测。

确认只证明**本机观察到的业务进展与探测往返**。它不包含远端所有业务包的发送清单，不能证明业务零丢包、50Mbps 能力、单向时延或未来持续稳定；因此不会把 PathQualification 提升为 QualityObserved，不改变连接状态与路径选择规则。

## 调度与正式接线

开始收到业务后，未稳定的路径按 300ms 初值尝试恢复探测，最多四个在途 nonce。无业务时不生成快速探测，确认后停止快速探测，保留原健康检查。重试受已有全机维护预算约束，不另外创建 socket、接收者或线程。

受管 wireControl 原生路径在实际注入时计入 Maintenance；排队后被限额丢弃的帧不能产生成功证明。其他路径在发送前领取现有维护令牌。兼容路径的 ping 响应也纳入维护预算，避免新增探测的响应成为旁路；既有兼容原生封装及内核开销总账仍未全部完成。预算不够时记录 deferral 或超时，不能填造探测成功；八设备同时恢复的确认时间尚待多节点验收。

`MeshPeerStatus.Recovery` 携带结构化诊断；正式服务按 episode 各输出一次 FirstBusiness 和 StableBusiness 日志，后者包含区间起点与确认时间。主界面仍按真实连接健康显示状态，没有以一项恢复指标宣称串流质量已验证。日志不包含业务明文、配对码或密钥。

## 本地验证

提交与文件哈希见 `artifacts/m6-recovery-observations-receipt-20261012.json`。以下均不涉及正在运行的安装服务、驱动或网卡配置。

- `m6-recovery-router-final-20261012.json`：**188 检查**，其中 30 轮仅是纯状态生命周期验证；另含兼容/受管两个正式 Router 的真实回环 UDP、MeshLink、认证内层 IP 与内存适配器。丢失探测响应时，即使业务持续到达，也不能提前确认；后续稳定起点晚于首次业务时间。原路径迁移、提名、策略拒绝、同 tuple 冲突、旧密文重放和资源退出回归继续通过。
- `m6-recovery-runner-trace-20261012.log`：**66 检查通过**。正式服务回归，保留旧查询/映射生命周期检查，新增协调长轮询停滞期间的认证业务、状态字段和两类日志验证。
- `m6-recovery-native-final-20261012.json`：三实例中，所有者向两个 peer、两个 peer 向所有者分别进行聚合目标 50Mbps、20 秒顺序测试，记录实际 C++/管道/Router 的恢复字段与原生维护计账。raw I/O 和 IP 适配器为受控内存夹具，**不是真实 WAN、WinDivert 或 Wintun**；负载结果以 JSON 为准，不把完成退出等同于质量 Gate 通过。
- `m6-recovery-final-build-20261012.log`：最终核心/服务/界面 Release 构建零警告、零错误。打包脚本增加 ManagedPathTests，避免只跑旧兼容路径就生成候选。

本次最终原生负载两个方向约 **49.96Mbps**，统计丢失 **0**，本地同一主机计时的 P99 约 **4.31/4.19ms**。收到业务的四条有向路径分别获得恢复确认；仅发出业务而未收到内层业务的一侧不会因此获得虚假的 FirstBusiness。相比先前同轮回归 P99 2.21/2.67ms 有调度波动，本次未做隔离 A/B，不能把差异归因于诊断或宣称性能改善。仍需真实链路与持续迟到统计。

保留首次服务回归失败 `m6-recovery-runner-20261012.log`：新增持续业务检查改变测试时序，原测试在映射故障触发之后才读取公告 revision，可能读到已撤销的新公告，随后等待一个尚不需要产生的更高版本而超时。修正为故障触发**之前**取得基线；没有延长等待或放宽撤销检查。后续 `m6-recovery-runner-final-20261012.log` 已通过 66 检查，最终 trace 版本另存，避免覆盖失败记录。

## 剩余工作与回退

本次没有宣称黑洞恢复 ≤10 秒、备用切换 ≤3 秒或冷启动 ≤15 秒已经达标；12 秒健康判定尚未缩短。七邻居维护预算压力、八台真机、休眠/重启、实际切网、长时间业务及严格 NAT 验收仍待完成。没有实际业务时也不伪造 StableBusiness；完整的空闲 StablePath 诊断可继续补充。

本次源码修改默认带来有界恢复观测，但现用服务与旧候选包尚未替换。回退源码基线为 `200cee3`；后续候选仍需整包验证与版本回滚，不能只替换单个 DLL。
