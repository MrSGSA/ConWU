# 后续计划

下一步以大码率远程串流为目标，验证开发版新增的 TCP/HTTPS 承载，再决定默认策略与正式发布范围；保留当前 FakeTCP＋HTTP 路径和已经稳定的直连码流程。

## 普通 TCP

验证普通 TCP 作为可选外层承载的效果，重点是有可达入口或 NAT 较宽松的场景。需要评估排队、拥塞、抖动、断线恢复和输入响应；TCP 打洞的网络限制单独记录，不保证严格 NAT 成功。

开发版已接入真实 TCP 套接字、直连码、配对和配置继承、PKARR 协议校验及主从双向路由。已有网络不自动迁移；使用新协议需要两端升级并新建网络。继续验证真实公网容量、拥塞下的本地队列与丢包、断线恢复和串流体验。

## HTTPS

开发版已将 TCP＋TLS＋HTTP/1.1 WebSocket 接入 Mesh 路由和批准流程，HTTPS 身份使用持久公钥指纹绑定。`tests/ConWU.HttpsPoc` 保留早期独立原型。协议、配置继承、认证隔离及双向虚拟 IP 报文有真实套接字回归；尚不能据此认定公网抗 QoS 或 Moonlight 大码率串流效果。

实机测试以 Windows 台式为主机、笔记本为从机，Linux 服务器仅在必要时作管理跳板。使用独立端口和临时身份，按实际交付量和排空时间计量，分别报告功能是否通过、是否达到目标码率。EasyTier 路径和回环结果单独记录；继续用台式可达公网入口验证 50/100/150 Mbps、尾延迟和 CPU，再由实际 Moonlight 串流验收。

## 发现与稳定性

持续核对 PKARR 多网关缓存、入口变更、发布失败退避、重启后的序列水位和双向确认。公共发现失败时，保留仍健康的已认证通道。原生 DHT 客户端与更多发现后端需要先证明维护成本和收益；本轮不恢复内置 DDNS，也不加入业务中继。

自主打洞改进围绕候选准备、端口所有权和双方同步进行，不能混入已有入口模式抢占通道。网络退出、重新加入、并发保存和多网络隔离继续纳入受影响回归。

加入期间的后台状态读取已避开重复 SCM 可用性查询，前端区分“有效后台响应”和“可应用的新状态”，丢弃过期代次后立即补拉；保持原超时阈值。继续观察实机加入日志，慢请求记录阶段耗时，避免将网卡初始化慢、控制接口失联与对端直连状态混为一谈。

## 验证标准

比较不同码率下的实际吞吐、往返和尾延迟、卡顿及恢复时间、输入响应、CPU 与内存占用。覆盖地址变化、重连和多网络并行，区分回环、受控链路与真实公网。最终 Moonlight 串流体验由实际使用验证，不用短时合成测试替代。
