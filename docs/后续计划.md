# 后续计划

下一步以大码率远程串流为目标，探索更多抗 UDP QoS 的传输方式。先做独立实机链路验证，再决定是否集成到产品；保留当前 FakeTCP＋HTTP 路径和已经稳定的直连码流程。

## 普通 TCP

验证普通 TCP 作为可选外层承载的效果，重点是有可达入口或 NAT 较宽松的场景。需要评估排队、拥塞、抖动、断线恢复和输入响应；TCP 打洞的网络限制单独记录，不保证严格 NAT 成功。

当前界面的纯 TCP 是预留项，不能把旧 UDP 配置改名当作 TCP。集成时必须同步处理协议协商、直连码、入口标签、PKARR 公告、CLI 与持久设置，并明确旧网络如何迁移。

## HTTPS

`tests/ConWU.HttpsPoc` 保留 TCP＋TLS＋HTTP/1.1 WebSocket Upgrade 的独立原型。已做过协议拒绝与合成负载回环验证，尚未接入正式配对、TUN 或 Moonlight；公网测试未完成，不能据此认定抗 QoS 效果。

继续试验时使用独立端口和临时身份，按真实发送量计量。对照不同运行时、GC、队列和内存限制，记录吞吐与尾延迟，再做公网与真实串流验证。

## 发现与稳定性

持续核对 PKARR 多网关缓存、入口变更、发布失败退避、重启后的序列水位和双向确认。公共发现失败时，保留仍健康的已认证通道。原生 DHT 客户端与更多发现后端需要先证明维护成本和收益；本轮不恢复内置 DDNS，也不加入业务中继。

自主打洞改进围绕候选准备、端口所有权和双方同步进行，不能混入已有入口模式抢占通道。网络退出、重新加入、并发保存和多网络隔离继续纳入受影响回归。

## 验证标准

比较不同码率下的实际吞吐、往返和尾延迟、卡顿及恢复时间、输入响应、CPU 与内存占用。覆盖地址变化、重连和多网络并行，区分回环、受控链路与真实公网。最终 Moonlight 串流体验由实际使用验证，不用短时合成测试替代。
