# 后续计划

1.2.0 的功能与验证范围见[版本说明](releases/1.2.0.md)。后续以大码率远程串流为目标，继续验证 TCP/HTTPS 承载；保留当前 FakeTCP＋HTTP 路径和已经稳定的直连码流程。未采用的性能候选及临时原始数据保留在本地实验记录。

## 普通 TCP

验证普通 TCP 作为可选外层承载的效果，重点是有可达入口或 NAT 较宽松的场景。需要评估排队、拥塞、抖动、断线恢复和输入响应；TCP 打洞的网络限制单独记录，不保证严格 NAT 成功。

当前版本已接入真实 TCP 套接字、直连码、配对和配置继承、PKARR 协议校验及主从双向路由。已有网络不自动迁移；使用新协议需要两端升级并新建网络。继续验证真实公网容量、拥塞下的本地队列与丢包、断线恢复和串流体验。

## HTTPS

当前版本已将 TCP＋TLS＋HTTP/1.1 WebSocket 接入 Mesh 路由和批准流程，HTTPS 身份使用持久公钥指纹绑定。`tests/ConWU.HttpsPoc` 保留早期独立原型。协议、配置继承、认证隔离及双向虚拟 IP 报文有真实套接字回归；尚不能据此认定公网抗 QoS 或 Moonlight 大码率串流效果。

实机测试以 Windows 台式为主机、笔记本为从机，Linux 服务器仅在必要时作管理跳板。台式上行上限约 50 Mbps，实机按 20/35/45/50 Mbps 验证交付量、尾延迟、CPU 和恢复时间，再由实际 Moonlight 串流验收。使用独立端口和临时身份，按实际交付量和排空时间计量。高于 50 Mbps 的本机性能测试用于测量承载开销。

## 发现与稳定性

持续核对 PKARR 多网关缓存、入口变更、发布失败退避、重启后的序列水位和双向确认。公共发现失败时，保留仍健康的已认证通道。原生 DHT 客户端与更多发现后端需要先证明维护成本和收益；本轮不恢复内置 DDNS，也不加入业务中继。

自主打洞改进围绕候选准备、端口所有权和双方同步进行，不能混入已有入口模式抢占通道。网络退出、重新加入、并发保存和多网络隔离继续纳入受影响回归。

已有入口也在原通道失效时主动刷新，避免只等待普通订阅间隔。有已配对设备但未连通时，来源检查间隔上限为 30 秒，覆盖第三方工具稍后才更新地址的情况；健康连接仍按用户设置检查。Windows TXT 查询保留系统 DNS 策略，绕过本机答案缓存，不清空全机缓存或擅自更换 DNS。日志在候选变化时记录解析出的 IP 与端口，以区分旧邀请入口、订阅候选和实际认证通道。

重启恢复回归需覆盖本机先启动、对端稍后上线、入口端口变化、订阅晚于断线更新、无本机网络事件及无协调公告。使用保存的成员凭据自动恢复，验证完整报文交付、设置不变和资源回收；回环及模拟订阅结果与实机 DNS 传播、真实关机重启的结果分别记录。

加入期间的后台状态读取已避开重复 SCM 可用性查询，前端区分“有效后台响应”和“可应用的新状态”，丢弃过期代次后立即补拉；保持原超时阈值。继续观察实机加入日志，慢请求记录阶段耗时，避免将网卡初始化慢、控制接口失联与对端直连状态混为一谈。

将串流中断后的面板加载与传输恢复分别检查：关联两端链路健康、Windows 网卡事件、服务及界面进程生命周期、首次打开界面的阶段耗时。物理网络断开不能直接认定为进程崩溃；本机界面在外网不可用时仍应可打开并展示已有状态，后台暂不可用时应明确说明并自动恢复。覆盖网络抖动、地址重取、从托盘首次打开及重新打开场景；不通过重启日用服务或断开实机网络复现。

面板已汇总本机与各网络日志，并标注来源。新记录携带跨重启独立的事件标识和绝对时间，用于增量去重与排序，面板保留最近 500 条。旧格式日志继续处理窗口缩减、扩展和轮转。筛选、搜索、复制和导出使用相同记录集。累计拒绝计数仅在变化时再次输出。

## 对外协调

左侧“加入申请”下方为“对外协调”，页面沿用创建、加入网络的左右布局。左侧控制本机协调服务，并通过“本机协调设置”弹窗保存监听端口、可选证书和私钥。右侧列出最近 3 分钟内有已验证活动的设备，最多显示 128 台。普通设备设置与协调草稿分别保存。

设备活动由通过身份校验的配对、公告发布与发现请求更新。同一设备跨网络合并，关闭配对房间保留仍活跃的网络记录。公告中的设备名称保持加密，协调端缺少已观察名称时显示设备 ID。设备列表表示近期协调活动，具体串流状态由网络概览展示。

HTTPS 协调启用时可同时留空证书和私钥，软件使用本机管理的证书。设置保存后仍需要核对服务实际运行结果。用户配置的监听地址、反向代理与证书信任继续由设备设置保存。

## 首轮传输优化

真实 TCP 使用缓冲解析，兼容拆分的数据帧头与连续的数据帧。HTTPS 通过握手能力头协商批量数据报，单批最多 16 KiB、16 个数据报，继续支持原有单数据报的 WebSocket 对端。发送端仅合并已经排队的数据，直接发送独立的输入、控制报文。

参考 NATMap、Natter 的保活、查询与失败恢复机制，TCP/HTTPS 自主入口已拆开 STUN 观察和网关租约维护。STUN 断开、超时或事务校验失败后，保留监听端口与已建立通道，只在已配置服务中切换，并按 5–45 秒退避。健康服务继续复用，网络唤醒和手动重试可立即请求复查。源地址或路由变化时重新准备映射，通配 TCP 接收监听继续保留。UPnP 的 180 秒租约每 60 秒续期。

TCP/HTTPS 初始 STUN 发现采用同一接收端口上的受限并发：首选在 200 ms 内未取得候选时尝试后续配置，最多同时保留两路观察连接。选中后取消并等待其余连接退出，再用留下的连接复查事务和端点，之后才申请原有网关映射。快速响应的首选服务不额外建立观察连接。首选服务故意不回应的交替回环对照，候选准备中位数由约 2.5 秒降至 0.2 秒；它验证发现容错与资源所有权，不代表严格 NAT 穿透率。

当前真实 TCP/HTTPS 仍由主机准备入口、从机主动连接；双端内核 TCP 同时打开、源端口共用和相应信令调度继续作为后续独立实验。先核对 TCP 与 HTTPS 逻辑角色、连接竞态、重传及候选更新，再决定接入。FakeTCP 的原生同时打开路径与真实 TCP 分别验证；已有入口模式保持独立。

临时无效的观察会撤下直连码可用候选，恢复后同步更新候选与界面状态。实际入口仍由对端认证和连通性验证确认。

参考 Kestrel 的接收对象复用方式，已完成 UDP 接收地址复用实验。20–50 Mbps 回环样本的客户端分配量约下降 2.5%，交替对照中的 CPU 与尾延迟收益尚不稳定，暂留实验记录。下一步结合 CPU 与分配采样核对完整数据路径，再决定接入范围。

完整路由路径已缓存固定的网络头部，并复用单个发送泵的外层封装缓冲。共享接收器使用端点与网络的组合键，按缓存头部选择订阅，减少每包字符串和封装数组分配。20/35/45/50 Mbps 的 TCP、HTTPS 回环对照中，每包总分配量约下降 30%。35、50 Mbps 的 20 秒复测保持完整交付，输入队列至对端内存网卡写入的 P99 约 3.2–4.1 ms。CPU 与实际串流效果继续测量。

固定对端的内部 UDP 桥已完成独立对照，尚未采用。35/50 Mbps、两个方向的短时回环均完整交付，主机发送方向的分配量约下降 3.7%；延长到每轮 20 秒后，TCP 主机发送方向的候选 P99 中位数约 23.8 ms，原路径约 12.5 ms，候选 CPU 中位数也更高。因此保留原有收发与返回来源检查，仅补充本机回环目标的边界验证。对照使用相同测试程序集、核心库、运行时和正式功能开关，仅替换共享接收器所在服务程序集；不将分配量下降等同于串流性能提升。实验源码、可复现对照和否决原因保留在本地实验记录。

WinDivert 批量接收已有独立的只读回环捕获实验，精确匹配本轮持有的源与目标端口，不修改生产捕获路径或驱动配置。35/50 Mbps 的交替对照平均每次仍约一个包，尚未形成有意义的系统调用合并，暂留实验。该结果不覆盖真实网卡中断合并、原生加密或更高包率，不能据此否定所有批量收发收益。

对照验证同时记录交付码率、尾延迟、CPU、分配量、网络读写次数与是否协商批处理。回环结果与台式到笔记本的测量分别保存。混合架构 CPU 的控制实验可限定测试子进程使用相同的性能核，并记录掩码，实际串流仍需在真实链路验收。

首轮 Windows 与 Linux 回归已覆盖旧单数据报对端、拆包、合包、坏帧隔离、取消与端口释放。受控回环在相同运行库与性能核范围下完成 150/300 Mbps 对照。台式与笔记本通过 EasyTier 管理链路完成双向加密回显，50 Mbps 目标的 30 秒测试达到 48.2–48.4 Mbps。用户已确认实际上行约 50 Mbps，历史 100/150 Mbps 实机样本归入超额负载观察。继续核对带宽范围内的排队与本地桥背压，按实际串流效果决定发布范围。

仅扩大测试回显窗口到 4096 个报文时，超出已知上行容量的 100 Mbps 负载出现序号缺口。测试默认窗口仍为 512，后续在 20–50 Mbps 范围内观察拥塞恢复与输入延迟。NATMap 的保活机制、严格 NAT、FakeHTTP 握手伪装和 WinDivert 批量收发沿用下方的独立实验安排。

## GitHub 技术调研与实验顺序

以下是机制参考与待验证候选，不代表已集成或已经证明能改善真实公网串流。保持当前配对流程和三机安装版本；实验先独立进行，不增加业务中继，不自动回退 UDP，不恢复内置 DDNS。

| 方向 | 项目 | 借鉴内容与边界 |
| --- | --- | --- |
| 入口维护 | [Natter](https://github.com/MikeWang000000/Natter) | TCP/UDP 映射保活、失效重建、入口变化通知；主要依赖宽松 NAT，不保证严格 NAT 可达。 |
| TCP 映射 | [NATMap](https://github.com/heiher/natmap) | 同一端口 HTTP 保活与 STUN 查询、绑定模式减少转发路径；支持原生 Windows，先核对监听地址和端口复用要求。 |
| 双端同步 | [EasyTier](https://github.com/EasyTier/EasyTier/blob/main/easytier-core/src/connectivity/hole_punch/tcp.rs) | 同一映射端口同时连接、探测同步、候选管理；其 TCP 主动打洞也跳过对称型 NAT，不捆绑完整组网引擎。 |
| 候选管理 | [Pion ICE](https://github.com/pion/ice) | 候选收集、排序、连通性验证与失效处理；借鉴流程，不引入完整 WebRTC。 |
| 严格 NAT 实验 | [n4](https://github.com/MikeWang000000/n4)、[HyperDHT](https://github.com/holepunchto/hyperdht) | UDP 端口预测、多 socket 探测、地址来源验证与信令同步；成功依赖实际 NAT 行为，不能直接推导 TCP/FakeTCP/HTTPS 成功。 |
| 握手伪装 | [FakeHTTP](https://github.com/MikeWang000000/FakeHTTP) | 研究真实 TCP 建连时注入伪 HTTP/TLS 报文的收益。原版为 Linux NFQUEUE，Windows 需适配；伪 TLS ClientHello 不等于真正 TLS 加密。现有 FakeTCP 已有 HTTP 握手伪装，避免重复叠加。 |
| HTTPS 对照 | [wstunnel](https://github.com/erebe/wstunnel) | TLS＋WebSocket、保活及断线恢复，可作独立基准；HTTP/2 不预设为性能更优。 |
| TLS 指纹 | [uTLS](https://github.com/refraction-networking/utls) | 后期评估真实 TLS ClientHello 指纹；Go 与现有 .NET TLS 栈存在接入成本，不保证完整浏览器流量特征。 |
| FakeTCP 数据路径 | [Phantun](https://github.com/dndx/phantun) | 轻量封装、多核处理、缓冲及包分发；官方主要面向 Linux。[第三方 Windows 客户端](https://github.com/zcb617/phantun-client-win) 仅作为 WinDivert 移植参考，需另行验证。 |
| Windows 批处理 | [WinDivert](https://github.com/basil00/WinDivert/wiki/WinDivert-Documentation#8-performance) | 选择性过滤、批量收发与重叠 I/O，降低系统调用和内核切换；小批量与最大等待时间共同控制延迟。 |
| Linux 内核路径 | [Mimic](https://github.com/hack3ric/mimic) | eBPF/TC/XDP 转换 FakeTCP，可作 Linux 性能对照；需要较新内核及内核模块，暂不作为 Windows 主路线。 |
| .NET 数据路径 | [Kestrel Socket Transport](https://github.com/dotnet/aspnetcore/blob/main/src/Servers/Kestrel/Transport.Sockets/src/Internal/SocketConnection.cs) | 内存池、Pipelines、收发对象复用、背压及生命周期处理；按采样热点优化，不直接替换完整架构。 |
| 测试设施 | [patchbay](https://github.com/n0-computer/patchbay)、[Toxiproxy](https://github.com/Shopify/toxiproxy) | 构造 NAT、丢包、延迟和 TCP 故障；仅用于开发验证，不进入用户业务数据路径，仿真不能替代校园网实测。 |

后续顺序：

1. 建立台式到笔记本的性能基线，对比现有 FakeTCP＋HTTP、真实 TCP、真实 HTTPS；分别记录功能、持续交付码率、尾延迟、排队时间、CPU、内存分配及 GC。核对测试窗口和中间管理网络的容量，防止误判承载上限。
2. 参考 NATMap/EasyTier 完善 TCP 入口维护、端口共用、同步探测和失败重建。优先确保主机可达，由从机主动建立双向通道。
3. 独立验证真实 TCP＋握手伪装，与现有 FakeTCP＋HTTP、真实 TLS＋WebSocket 做同链路对照。参考 FakeHTTP 的报文处理，实验仅匹配 ConWU 测试流的五元组，检查 SEQ/ACK、重传、MTU、TTL 和业务字节完整性，再在 20–50 Mbps 范围内验证运营商实际效果。
4. 根据采样结果评估 WinDivert 批量收发、每包缓冲复用、减少 loopback 桥接、限制延迟的写入合批与背压；不靠扩大队列追求短时吞吐，不削弱身份认证与重放防护。
5. 严格对称 NAT 与 TLS 指纹作为后续实验。参考 n4 测量 NAT 端口分配是否可预测、两端同步误差和探测资源开销，继续使用 ConWU 身份校验与双向路径验证。TCP、FakeTCP 分别验证，记录成功条件与失败边界。PKARR 发布最新地址仍需结合双方探测时序。

FakeHTTP 机制已有独立的 Linux 网络命名空间实验。客户端与服务端之间设置两个路由节点，在内核 TCP 建连后、应用发送前注入校验和有效的伪 HTTP 报文。第一跳可见该报文并返回对应的 TTL 超时，后续节点未收到它，双方 128 KiB 应用数据的哈希一致。实验命名空间随结束清理。后续继续验证握手时序、路由变化、Windows 收发适配及真实 QoS 效果。

## 抗 QoS 新路线

2026-11-11 更新：本节记录 TCP/TLS 与 UDP 的抗 QoS 候选及独立实验安排。UDP 的 STUN 外观、有限随机填充和多通道已完成首轮独立实机验证，结果见下文；TCP/TLS 新候选继续保留研究计划。新增机制尚未接入程序或更新三机。QUIC／HTTP/3 不再推进，此前尝试仍受 UDP 打洞与限速影响；这不排除研究其他 UDP 封装与流量特征。不在 ConWU 增加外层 FEC，继续由 Sunshine 处理自身冗余与恢复。当前 HTTPS 承载是 TCP＋TLS＋HTTP/1.1 WebSocket。

LADR 是腾讯 START 云游戏的传输系统研究，当前只借鉴其优先使用 TCP 的多连接池与排队观测。论文的关键帧重发、过期帧放弃和编码码率调节依赖视频系统参与；ConWU 处理通用 IP 流量，无法直接照搬这些操作。不引入论文中的第三方代理角色，也不恢复已有入口模式的自主打洞或协议自动回退。

源码核对后的具体取舍：

- Cloak 的 [switchboard](https://github.com/cbeuw/Cloak/blob/master/internal/multiplex/switchboard.go)存在固定流映射与随机分发两种结构，可作为多连接调度参考；其实现会在部分子连接读写失败时结束整条会话，不能原样当作 ConWU 的故障隔离方案。
- WatTunnel 是较新的项目；本轮核对了连接轮换、填充预算及对应测试源码，未执行或采用其性能结论。当前轮换通过关闭一个池连接后重拨实现，ConWU 需要另做先建后切的交接。其[原始伪 SNI 注入](https://github.com/JohnWatsoon/WatTunnel/blob/606b00045a5b0132aed1999affbb3cd2fb28c5af/wat/desync_other.go)明确限制 Linux，不能因仓库列有 Windows 相关代码就认为所有伪装能力均支持 Windows。
- DPI 分段、伪包、TLS 包装等资料主要针对协议识别与封锁。是否能改变本线路的 QoS 分类属于待验证假设；针对所有 TCP 或用户总带宽的硬性上限，不能由这些机制保证突破。

### UDP 首轮独立实机结论

已完成台式到笔记本的公网 UDP 对照，EasyTier 仅传递 SSH 控制消息。单通道按 20/35/45 Mbps 的 IPv4 总发送预算测试，使用带 HMAC 认证的随机数据；不代表 ConWU 生产加密、虚拟网卡或 Moonlight 的测试结果。35 Mbps 下的有效载荷吞吐中位数如下：

| 模式 | 有效载荷 Mbps | 丢包率 | 有效轮数 |
| --- | ---: | ---: | ---: |
| 普通 UDP | 6.25 | 80.77% | 3 |
| STUN 外观 | 6.09 | 80.91% | 2 |
| STUN 外观＋0～44 字节随机填充 | 5.91 | 81.13% | 3 |

另用同一组预先建立并保活的通道，以 1→2→4→1 条的顺序，在总 20/35 Mbps 下分别重复三轮。总 35 Mbps 时，有效载荷吞吐依次约 6.33/6.34/6.40/6.36 Mbps，没有随通道数扩展。本机发送器已通过约 50 Mbps 单通道与 45 Mbps 多通道容量检查；两端生产服务、设置、身份和原直连网络保留。

本轮保留 24 个单通道和 24 个多通道有效实机样本。三个计划组因发现阶段未获取到映射而没有吞吐结果，单独排除；STUN 外观因此仅有两轮有效数据。发现超时的具体原因尚未定位，不能据此归因于防火墙或校园网。原始数据与说明保存在本地 `artifacts/udp-qos-lab/summary.md` 和 `summary.json`；可复现实验程序为 `scripts/Test-UdpQosLab.py`、`scripts/Test-UdpQosMultiFlow.py`。

补充定位已将接收端换为独立 Linux 服务器，普通 IPv4 UDP 仍出现相同平台。三种固定包长的接收 IP 吞吐约 7.17～7.55 Mbps，接收包数约 731～2744 包/秒，更符合带宽型约束。同一台式通过现有 FakeTCP＋HTTP 网络发送时，有效载荷接收约 32.48 Mbps、丢包约 0.04%，说明当前总上行能力高于普通 UDP 的平台。cFosSpeed 临时开关对照未改变该平台，之后已恢复原值；Windows 各层计数未看到约八成报文在受观测发送栈中被削减。

用户确认出口为 BE5100 拨号、光猫桥接且未启用手动 QoS。路由器上报私网 WAN 地址，与实际公网源地址不同，说明还有上游 IPv4 NAT。UPnP 字节计数已停在 32 位上限，包计数存在批量跳变，不能代替物理 WAN 抓包。因此仍未锁定 BE5100、光猫或运营商接入/CGNAT 中的具体执行点；下一步定责需要 WAN 实际报文或用户现场准备后的直拨对照。详细证据保存在本地 `artifacts/udp-qos-lab/localization/summary.md`；生产设置、身份、证书和服务进程均已核对保留。

当前不集成 STUN 外观、有限填充或多 UDP 通道，也未否定其他 UDP 方法。真实 DTLS、连接内更宽范围的动态包长/时序变化、完整 AmneziaWG 机制、时间上的端口轮换与受控 QoS 分类实验继续保留为未验证候选；TCP/TLS 的独立研究计划保持不变。IPv4/IPv6 对照尚未完成，当前只有台式检出全局 IPv6，笔记本和服务器没有相应的受控接收条件。

### 暂不推进的路线

- 不推进 QUIC／HTTP/3 或 Hysteria 传输本身，不叠加外层 FEC。AmneziaWG 的报文混淆和 UDP 端口轮换仅作为上表中的独立机制实验，不引入这些项目的整套传输或组网体系。
- [TCP Brutal](https://github.com/HyNetworks/tcp-brutal)目前是 Linux 内核模块，不能直接改善 Windows 台式主机发出的 TCP。强制速率与丢包补偿也需要适配实际容量，不作为当前 Windows 主路线。
- [Tonel](https://github.com/sabify/tonel)虽使用 multi-stream TCP 的描述，但其文档明确保留数据报语义并避开重传／流控，属于与 FakeTCP 相近的方向，不能当作已经实现多条真实 TCP 的证据。
- MASQUE／CONNECT-UDP 是 HTTP 数据报隧道协议的标准参考，其标准角色包含代理。ConWU 若借鉴帧格式，仍由两端直接承载，不加入业务中继，也不把 H2 Capsule 上的可靠字节流称为无队头阻塞数据报。

### 后续独立实验安排

1. **隔离与基线**：使用独立测试程序、端口和临时身份，保持三机现有安装、设置和日用网络。真实网络以 Windows 台式为主机、笔记本为从机，服务器仅在必要时作管理跳板，不充当业务中继。先分别确认 TCP 与 UDP 入口可达，再记录普通 UDP、现有 FakeTCP＋HTTP、真实 TCP、真实 HTTPS 的基线；不能假设同端口的 TCP 映射也可承载 UDP。
2. **TCP/TLS 组**：固定主机入口，比较 1/2/4 条真实连接；随后分别验证有限握手变换、先建后切的连接轮换、WebSocket／HTTP/2。TLS 指纹、有限填充和其他握手包装列为后续；每次只改变一个因素，连接池与单流分条发送分别评估。
3. **UDP 组**：优先比较普通 UDP 与 STUN 外观，再分别增加有限包长变化或初始报文；之后在入口条件满足时比较源端口轮换、目标端口分散。DTLS 外观与有状态 DPI 干扰在源码核对及完整性检查后再排期。UDP 组独立运行，不作为生产协议的自动回退。
4. **受控条件**：分别构造应用特征分类限速、单流／端口限速、全 UDP 限速、随机／突发丢包和满载排队。记录控制规则、丢包模型及路由条件，使用全 UDP 限速作为外观变化的边界对照；不能用普通丢包实验代替抗 QoS 验证。
5. **负载与指标**：主机上行约 50 Mbps，主要比较 20/35/45 Mbps，50 Mbps 用作满载压力。封装、填充、重传、伪包及额外握手开销均计入总线速预算，同时单独报告有效交付码率。记录 P95/P99、交互小包延迟与超时、丢包、乱序、重复、CPU、内存分配、排队和断线恢复时间。
6. **重复与验收**：相同链路、有效载荷、认证和 MTU 约束下，每组至少三轮交替基线与候选，持续时间覆盖疑似限速触发窗口，区分预热、稳定传输和排空。先验证字节完整性、身份隔离、取消与端口释放；受控实验有稳定收益后，再安排台式到笔记本的公网对照。真实串流结论由用户使用 Moonlight 验收，不能用回环峰值或项目自报吞吐替代。

## 验证标准

比较不同码率下的实际吞吐、往返和尾延迟、卡顿及恢复时间、输入响应、CPU 与内存占用。覆盖地址变化、重连和多网络并行，区分回环、受控链路与真实公网。最终 Moonlight 串流体验由实际使用验证，不用短时合成测试替代。
