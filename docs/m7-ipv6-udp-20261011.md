# M7：原生外层 IPv6 UDP 接入

后续原生 FakeTCP IPv6 实现与独立验证见 [M7 原生 IPv6 FakeTCP](m7-ipv6-native-20261011.md)。下文保留本提交发生时的状态与测试边界。

从 `8c98840` 继续。本次接入的是 `UDP_DIRECT` 外层 IPv6，内层虚拟 IPv4 地址保持不变；现有 udp2raw FakeTCP+HTTP 的外层仍为 IPv4。本次不能作为 M7 全部完成或扩大校园网 NAT 覆盖的证明。

## 产品行为与兼容

- 新配置 `UdpIpv6=false`。设置页增加默认未勾选的 IPv6 UDP 备用选项，后台通过 `UdpIpv6Version=1` 声明支持。只有实验 TCP+UDP、允许 UDP 降级和优先 FakeTCP 策略同时满足时可以勾选。保存沿用既有重连行为。
- 保留 `TraversalProfile.UdpDirect=3`，没有新增旧客户端无法识别的 profile。加密、签名公告中增加可选 `MeshTraversalCapabilities.UdpIpv6`；缺省为 0。
- 协调服务在 watch snapshot 增加 `UdpIpv6=1`，表示能验证和转交 IPv6 候选。旧服务缺少字段时为 0；客户端不会向其发送 IPv6 候选。服务仅交换控制信息，不承载业务。
- 三方能力齐全、且本机存在可用原生 IPv6 时，发起者在每个机会窗的首个 UDP 轮次优先收集 IPv6。响应者必须遵循已认证 Offer 的地址族。Ready/Start 的候选对地址族必须一致，IPv6 端点仍在成员签名范围内。
- IPv6 收集最多先使用 3.5 秒，未取得可用候选则在原来 12 秒收集期限内继续 IPv4。若已经公布 IPv6 后实际连通检查失败，下一轮使用 IPv4，不重新开启 60 秒机会窗或增加每方法两轮限额。
- IPv4 映射的普通/网关交替状态不被 IPv6 收集推进。因此“首轮 IPv6 检查失败、第二轮 IPv4”的首次机会窗使用普通 IPv4；显式映射仍依赖后续已有轮次。没有承诺在两轮内尝试三种方式。
- 旧客户端忽略加密公告中的新增字段，不需要重新解释签名明文。此次旧端/旧服务测试是能力缺失模拟，并非运行旧发布二进制的混合版本实测。
- UDP 路径继续标记为降级、质量待验证；不会抢占健康 FakeTCP，不因空载延迟低就声称适合串流。

## 地址、资源与收发

`Stun` 新增显式地址族解析及 `[IPv6]:port` 输入，IPv6 XOR-MAPPED-ADDRESS 使用 cookie + transaction ID 的 128 位掩码。原 IPv4 调用者默认只接收 IPv4 属性，避免把新的解析能力错误套进现有 TCP helper。

`TraversalSocket` 使用 AF_INET6、V6ONLY、独占端口，并设置 Windows `IPV6_DONTFRAG`。接收循环使用 IPv6Any 接收地址。实际 socket 从反射、SLP2、完整负载检查到 Active 引用持续保留；地址族不匹配的反射结果、候选或新来源不能进入同一个 socket 的候选表。没有把 socket 关闭后按端口数字重建。

`Ipv6Direct` 的生产规则要求原生全局单播、可用的物理 Ethernet/Wi-Fi 源地址、Preferred DAD 状态及至少 30 秒地址有效/首选寿命。Prepare 再次查询实际路由，要求与持有源地址一致。排除 link-local、scope、ULA、IPv4-mapped/compatible、组播、文档地址、6to4/Teredo 和识别到的虚拟组网出口。全局范围采用保守策略，可能拒绝部分特殊地址，不宣称完整实现所有 IANA 地址政策。

真实 IPv6 有状态防火墙仍需双向认证检查。存在全局地址或 STUN 成功都不直接晋升路径。此轮不改任何网卡 MTU、路由、Windows IPv6 配置或防火墙。

资源仍使用现有 `TraversalResources` 全机账本；同 socket Active 引用仍占额度。用于查路由的临时 UDP socket 仍沿用既有实现，完整进程资源账本是 M3 未完成项，不能据本次声称全部 socket 已计账。

## PMTU：保留未通过的证据

内层 1280 字节 + MeshLink 64 字节 = 1344 字节 UDP payload。IPv6 固定头 40 + UDP 8 后是 **1392 字节外层 IP 包**，不能套用 IPv4 的 1372 字节，也不能假定 IPv6 最小 MTU 1280 足够。

首次测试设置单 socket `IPV6_USER_MTU=1280`，预期 1344B SendTo 返回 MessageSize；实际没有报错。原始失败保存于 `artifacts/m7-ipv6-udp-initial-pmtu-20261011.json/.log`，174 项前置检查完成后停止。

后续记录同时读取到 USER_MTU=1280、DONTFRAG=1，但回环仍接受大包。本次没有抓取并解释线上的 IPv6 分片行为，因此 `wirePmtuVerified=false`。不能把回环收发成功或选项读回值等同于公网不分片证明。

另增加受控 socket 的 MessageSize 注入：小认证包通过，完整数据报发送失败时，正式检查返回 `mtu-too-small`，不晋升路径。它验证失败处理逻辑，并非物理 PMTU。未来真实路径若不足 1392B，需要明确失败或实现单独协商的更小内层 MTU，不能偷偷分片后标记通过。

## 未完成与回滚

M7 仍需原生 FakeTCP IPv6：`native_backend.cpp` 明确限制 AF_INET，`native_attach.cpp` 的 ABI 1 描述符固定 IPv4，受管 WinDivert 捕获/校验和/分流也需端到端扩展。不能通过本次 UDP IPv6 能力位让对端误认为已经支持 FakeTCP IPv6。PCP/NAT-PMP 主动通知等上一轮未完成项继续保留。

关闭 IPv6 UDP 备用并保存可回到原来的 IPv4 候选收集，保持 FakeTCP 优先和 UDP 独立许可。版本回退基线为 `8c98840`；停止候选版本并等待其路径清理后再启动基线。新增字段缺省为关闭，没有数据库迁移。旧协调服务仍可继续服务 IPv4 客户端；新服务对旧客户端不要求新增字段。本轮没有部署协调服务、替换已安装软件或改变现用配置。

参考：[RFC 5769 IPv6 固定向量](https://www.rfc-editor.org/rfc/rfc5769.html#section-2.3)、[Microsoft IPv6 socket 选项](https://learn.microsoft.com/en-us/windows/win32/winsock/ipproto-ipv6-socket-options)。本机 SDK `ws2ipdef.h` 同时核对 DONTFRAG=14、USER_MTU=76。
