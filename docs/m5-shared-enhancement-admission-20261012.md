# M3/M5：TCP 与 UDP 增强任务共享调度

基于 `59027bc`，把正式 TCP 校准、预测和内部 UDP 概率探索接到同一个受管服务进程的高成本任务调度器。原校准实现会跨越整个 20 窗收集过程持有名额，连正常 31 秒采样间隔也不释放，其他预测任务可能因此长期拿不到机会。

## 实现

- `TraversalResources.Shared.Enhancements` 统一持有一个运行名额和最多 16 个等待项。TCP 校准与预测使用该实例；UDP 探索使用其所属同一资源账本的实例。测试模拟不同机器时明确使用不同账本，不把多个独立预算冒充单机总预算。
- 等待按 FIFO 交接，新来的任务不能越过已有队列。排队阶段不创建新的源 socket、helper 或捕获句柄。取消等待、取消与交接同时发生、队列已满、持有者多次释放均有明确处理。
- 校准每个采样窗口领取一次名额，源端点、捕获和观察操作结束后释放，再执行服务器要求的采样间隔。20 窗、留出验证、干扰观察、31 秒生产间隔、15 分钟总期限均保留。
- 已有业务路径返回时，监测覆盖排队、helper 打开、捕获准备、STUN 和原生观察阶段。被中断的窗口不参与训练；已有 helper/Active 的所有者不受影响。
- 正式 TCP 预测在共享队列等待，不再因另一个增强任务占用就立即消耗一次失败机会。排队仍受既有 Runner 机会窗和取消控制；取得名额后才等待协调额度并申请实际源。原两秒首次预测发包准入、八秒整轮期限及路径内认证保持不变。
- UDP 准备对象在扩池和打开源之前取得同一名额；异步 `Create` 可以公平排队，获准后将同一个名额转交给准备对象，不重复领取。实际向对端发过检查、但整轮未得到合格路径时，记录该网络/成员对/本地出口代次的五分钟冷却。取消、未启动准备、未实际探测的准备故障不制造 NAT 失败。冷却在排队交接时再次检查，已经等候的旧请求不能绕过刚发生的失败。
- UDP 冷却不会应用到 TCP。新本地出口代次独立评估；同代次凭“新可靠证据”提前解除冷却尚无生产证据提供者，因此当前不提供绕过入口。
- `SessionStatus.EnhancementAdmission` 报告正在执行的方法、等待数/峰值、领取和退出统计，以及实际调度排队耗时。它不是线上发包计数，也不包括后续 HTTP 等待或握手耗时。`Cancelled` 记录从等待队列撤掉的请求；已经领取后的取消由操作生命周期管理。

共享实例位于受管服务进程内，沿用单个正式服务及既有端点所有权约束；不会把互不相关的独立测试进程统计到一起。此改动没有增加 TCP/UDP 源配额、发包速率或业务重传，也没有修改 FakeTCP/HTTP profile。界面没有自动启用实验方法。

## 验证

| `m5-enhancement-admission-final-20261012.json/.log` | 31 检查：七个混合 TCP/UDP 等待者的 FIFO、16 项队列上限、200 次取消/交接竞争、真实 UDP 准备的跨协议互斥、异步排队/取消/转移与资源归还；五分钟冷却用受控单调时钟验证，不声称实际等待五分钟。 |
| `m5-enhancement-calibration-20261012.json/.log` | 43 检查：正式工厂的完整 20 窗及生命周期；实际独占回环 TCP helper、原始 SYN 构造，观察/NAT 为内存夹具。新增排队期间业务恢复无额外 helper、生产间隔内真实 UDP 准备可取得同一个全局名额。 |
| `m5-enhancement-prediction-runner-20261012.json/.log` | 20 检查：正式 TCP 预测在 UDP 名额后等待且不提前开源、队列取消、稳定端两种角色各一轮实际 C++/HTTPS/Runner 连接、原期限结束后的完整双向业务，以及稳定映射变化时零预测对等 SYN。NAT/IP 与预注入校准训练数据为明确的夹具。 |

| `m5-enhancement-udp-smoke-final-20261012.json/.log` | 同资源 UDP 机制的模型与 Windows 回环各一轮、真实 Router/MeshLink 提名与完整双向内层包。 |
| `m5-enhancement-service-regression-20261012.log` | 71 项原 TCP/组网服务回归；新增默认兼容模式报告空闲增强账本而不产生探测。 |
| `m5-enhancement-app-build-final-20261012.log` | App/Core/Service Release 构建通过，零警告、零错误；两份验证脚本语法检查通过。 |

20 窗校准得到 20 个独立源、141 个 SYN、47 个夹具确认的目的映射及 60 次控制调用，10 个留出窗均被原两端口模型覆盖。本轮仅把该用例的采样间隔置零，生产 31 秒间隔由独立生命周期用例验证，不把测试用时当成公网校准速度。

两轮正式预测从 Runner 开始到两端连接分别约 27.725、26.589 秒，包含先失败的普通候选和协调额度等待，不是纯握手时间，也不作为性能改善的对照实验。本轮证明调度接入后原预测流程仍成立，未证明公网严格 NAT 成功率提高。

Local/Package 验证脚本加入共享调度测试。完整 Local、完整打包、公网、驱动和现用服务未在本轮运行；本轮产物不会替换当前 `a24f657` 安装候选。

## 剩余工作

UDP 概率探索仍缺稳定端资格的生产证据、双方签名能力/目标授权、正式候选收集与 Runner 接入、以及健康合格路径禁止启动的产品侧准入。此次共享调度不是这些条件的替代。真实多设备公平性、真实 NAT、物理 WinDivert/Wintun 和 M9 发布 Gate 继续保持未完成。
